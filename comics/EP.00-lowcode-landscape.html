EP.00 五个工具箱，先选对再动手 ​

对应章节：guide/00-lowcode-landscape

剧情回顾 ​

  1. 困境：标签君接到「做一个运营后台」的需求，选型会上大家凭感觉报产品名，三周后页面能点却改不动。
  2. 揭秘：码叔指出低代码不是一个大品类，而是五类形态：Schema 驱动、表单模型、编排引擎、页面搭建器、自由画布。
  3. 实证：像素酱用四个问题缩小范围——页面结构稳定吗、表单联动复杂吗、需要非开发者编排吗、需要像素级自由布局吗。
  4. 结案：码叔给出行动准则：七个 lab 先逐个跑通最小闭环，再谈选型；只看官网 demo 不看版本，是最常见的坑。

知识点拆解 ​

第一格：选型靠拍脑袋的代价 ​

「上个低代码」不是需求，只是手段。需求真正要描述的是：页面由谁维护、数据从哪里来、多久改一次、改动时谁来承担回归成本。缺少这四个描述，选型会退化成产品名投票。

漫画里的代码芯片写了三行真实后果：需求是 30 个页面加复杂表单，选型会只报了产品名，三周后页面能点但改不动。改不动的根因通常不是产品弱，而是页面结构、数据协议和团队能力没有对齐。

对应正文：低代码全景与选型维度。

第二格：五类形态的边界 ​

  • Schema 驱动：用 JSON 描述页面，代表是 amis，适合中后台 CRUD。
  • 表单领域模型：字段是一等公民，代表是 Formily，适合复杂联动与校验。
  • 可视化编排引擎：设计器、渲染器、物料、插件一整套，代表是 lowcode-engine。
  • 页面搭建器：编辑器与运行时分离，代表是 tmagic-editor，偏运营页面。
  • 自由画布：直接操作 DOM/CSS，代表是 GrapesJS，自由度高但工程约束弱。

形态决定产物：JSON、字段树、节点树、页面 Schema、HTML/CSS。产物决定 diff 与回滚方式，也决定团队要补哪些工程能力。

第三格：四个问题定方向 ​

Q1 页面结构稳定、以 CRUD 为主 → 优先 Schema 驱动。
Q2 表单联动与异步校验是核心 → 优先字段模型。
Q3 要让非开发者长期搭建 → 才考虑完整设计器。
Q4 要像素级自由布局并导出 HTML/CSS → 才考虑自由画布。

四个问题的作用是排除，不是直接给答案。排除之后，再用最小 demo 验证安装、构建、扩展三个动作是否顺畅。

第四格：先跑通，再选型 ​

七个 lab 对应七种验证：amis、Formily、lowcode-engine、tmagic-editor、GrapesJS、capstone、mini-lowcode。每个 lab 都有独立的 package.json 与 lockfile，按章推进，不一次性装完。

验收标准只有三条：能装、能跑、能改。能装说明版本组合可用；能跑说明入口和资源完整；能改说明扩展点真实存在。三条都满足，再谈团队推广。

坑点清单 ​

  1. 只看官网 demo，不看版本：低代码产品 API 跨版本变化大，demo 能跑不代表你锁定的版本能跑。
  2. 把所有低代码都当同一类：拿 amis 去拼像素级自由布局，或拿 GrapesJS 去做复杂表单联动，都会付出额外成本。
  3. 一次性安装七个工程：版本、网络、配置问题混在一起，排错成本成倍增加。
  4. 忽略产物形态：只看搭建时快不快，不看产物如何 diff、如何回滚、如何被其他系统消费。

自测 ​

1. 低代码的五类形态分别对应什么产物？

Schema 驱动对应 JSON 页面配置；表单领域模型对应字段树与响应式规则；可视化编排引擎对应带物料协议的节点树；页面搭建器对应可被运行时解释的页面 Schema；自由画布对应 HTML/CSS 结构。产物形态决定了版本管理、diff 和回滚方式。

2. 为什么「上个低代码」不能直接作为选型依据？

因为它只描述了手段，没有描述约束。真正决定选型的是页面维护者、数据来源、改动频率、回归成本。缺少这些信息，比较功能列表没有意义，最后容易选到「 demo 好看但维护困难」的产品。

3. 七个 lab 的验收标准为什么是「能装、能跑、能改」？

能装验证版本组合与 lockfile 可用；能跑验证入口、样式资源、运行时完整；能改验证扩展点（自定义组件、插件、物料）真实存在。三条覆盖了从环境到扩展的最小闭环，比「页面能打开」更接近真实使用。
