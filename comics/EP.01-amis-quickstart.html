EP.01 半天搭完 CRUD，协议先对齐 ​

对应章节：guide/01-amis-quickstart

剧情回顾 ​

  1. 困境：运营要三十个后台页面，研发只有两个人；手写一个页面两天，交付后文案再改八轮，前端一直在排队。
  2. 揭秘：码叔指出重复的不是业务，而是页面结构；amis 用一棵 JSON 树描述 page、crud、filter、columns，结构交给 Schema，数据交给 fetcher。
  3. 实证：像素酱给出正确顺序——先定字段、状态与响应结构，再写 Schema，最后用增删改查四条链路验收。
  4. 结案：码叔强调先跑通最小闭环，再谈批量、导出与权限；响应里缺 status，表格会以空白的方式失败。

知识点拆解 ​

第一格：被浪费的是结构编写时间 ​

一个标准 CRUD 页面包含表格、筛选、分页、弹窗、表单校验、请求封装、错误提示与加载态。业务不同，这些结构的形状却高度相似。手写的问题不是「写不出来」，而是「每次都要重写一遍，且细节不一致」。

amis 的切入点就是这部分重复结构。它不替代业务代码，也不负责后端，只把页面的「骨架」抽象成 JSON。理解这个边界，才不会期待它顺手解决权限、审批流和数据建模。

对应正文：从一个真实问题说起。

第二格：Schema 是一棵树 ​

page 是最外层容器，crud 是组合渲染器，它内部再拆成 api、filter、columns、headerToolbar 四个插槽。你写的不是「一个表格组件」，而是一份页面结构描述。

数据边界由 env.fetcher 提供。amis 只规定请求配置和响应形状，不绑定 axios 或 fetch。这样 Schema 可以在测试环境接内存 fetcher，在生产环境接真实请求，页面配置不用改。

第三格：先定协议，再写 Schema ​

漫画里的四步顺序值得抄下来：

  1. 定字段：orderNo、customer、amount、status、createdAt；
  2. 定响应：{ status: 0, data: { items, total } }；
  3. 写 Schema：crud + filter + 弹窗表单 + 操作列；
  4. 验收：新增、编辑、删除、查询四条链路都能走通。

顺序反了，常见后果是 Schema 写完才发现字段名对不上，然后同时改 Schema、fetcher 和后端，返工翻倍。

第四格：最小闭环优先 ​

第一个版本不需要批量导入、导出 Excel、权限控制。先把「能查、能增、能改、能删」跑通，再按需求加功能。每加一个功能，都回到同一个验收清单：数据是否刷新、错误是否提示、分页是否还正确。

坑点清单 ​

  1. 响应缺 status：amis 认为请求失败，表格空白但不一定报错。
  2. 列表字段不叫 items / total：crud 拿不到数据，需要 adaptor 转换。
  3. 忘记 primaryField：编辑和删除无法定位行，翻页后必错。
  4. 表达式写复杂业务：显隐和禁用适合表达式，多字段计算与异步校验不适合。
  5. 用 latest 安装：amis 小版本之间也可能有 Schema 差异，锁定精确版本。

自测 ​

1. amis 的 `crud` 为什么不是普通表格组件？

因为它是组合渲染器：内部创建数据域、发起列表请求、渲染筛选表单、表格、分页与批量操作。Schema 里的 api、filter、columns、headerToolbar 分别对应数据、查询、展示、操作四个插槽。理解这一点，才能知道字段该写在哪一层。

2. 为什么 fetcher 的返回值必须包含 `status` 与 `data`？

amis 按 { status, msg, data } 判断请求是否成功，并从 data 里取列表。缺少 status 时可能被当成失败；缺少 data 时列表为空。真实后端字段不同，应该在 adaptor 里转换，而不是改 Schema 去迁就接口。

3. 第一个 CRUD 页面应该先做哪些功能？

先做查询、分页、新增、编辑、删除五件事，并保证写操作后列表自动刷新。批量操作、导出、权限、审批流都放在最小闭环之后。每加一个功能都用同一套验收动作回归，避免「功能加了、基础链路坏了」。
