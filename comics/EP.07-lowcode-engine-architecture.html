EP.07 设计器不是画布，是五层各司其职 ​

对应章节：guide/07-lowcode-engine-architecture

剧情回顾 ​

  1. 困境：标签君把拖拽、渲染、属性面板写进同一个 Editor.tsx，第一版能跑；等他加撤销、加协作、加自定义物料时，发现每个需求都要改内核。
  2. 揭秘：码叔把设计器拆成五层——engine 管生命周期，designer 管节点树与选中态，simulator 用 iframe 做真实渲染，material 管组件元数据，plugins 承载平台业务。
  3. 实证：像素酱按「先注册插件，再 init」的顺序启动引擎，先 setAssets 再 importSchema，画布第一次渲染就没有报错。
  4. 结案：码叔让三栏闭环跑通——大纲能选中节点，画布能渲染订单卡片，右栏能改「卡片标题」。

知识点拆解 ​

第一格：一个组件为什么会长成内核 ​

把画布、属性面板、拖拽逻辑写在一个组件里，短期是最省事的写法。问题出现在第二次需求变更：撤销需要记录节点历史，协作需要感知选中态，自定义物料需要一份组件描述。三件事都指向同一份运行时状态，而这份状态被锁在组件内部，外部只能通过回调去改。

漫画里的代码芯片不是反面教材，而是很多低代码原型的真实起点。它的问题不是「代码丑」，而是没有边界：渲染、状态、扩展点混在一起，任何新能力都只能往内核里塞。低代码引擎的第一课，就是把这份状态拆出去，让每一层只暴露必要的接口。

对应正文：原理拆解。

第二格：五层各自管什么 ​

  • engine：启动、插件注册、init 生命周期，以及全局配置。
  • designer：节点树、选中态、拖拽、撤销栈，是编辑行为的核心。
  • simulator：把 schema 渲染进 iframe，保证编辑态与运行态隔离。
  • material：组件元数据、Setter、资源包，决定「有哪些组件可用」。
  • plugins：平台自己的业务能力，例如保存、预览、出码、权限。

依赖方向是单向的：plugins 依赖 engine 提供的上下文，engine 调用 designer 与 simulator，designer 读取 material。反过来让 material 去依赖 plugins，或者让 simulator 直接改 designer 的节点树，都会让边界失效。边界一旦失效，后面每加一个功能都要先猜「这段逻辑到底该放哪」。

第三格：启动顺序为什么重要 ​

引擎的启动可以概括为三步：注册插件、初始化插件、调用 engine.init(container)。插件在 init() 里做的事情，通常包括设置 scenario、注入物料、导入初始 schema、往骨架里加面板。

顺序不能随意调换。setAssets 必须在 importSchema 之前，因为导入 schema 时引擎要按 componentsMap 解析组件；如果物料还没注册，画布会先报「不是 React 组件」。同理，业务插件如果依赖初始化插件写入的 schema，就要在 meta.dependencies 里声明依赖，让引擎按拓扑顺序初始化。

第四格：最小闭环的三栏 ​

判断一个设计器是否真的跑起来，不看它有多少按钮，而看三栏是否对得上：

  1. 大纲能列出 Page → Card → Input/Button 的层级；
  2. 画布能渲染出真实组件，而不是一行占位文字；
  3. 设置器在选中 Card 后出现「卡片标题」这类属性。

只要这三栏能联动，后面接物料、接插件、接保存才有意义。漫画最后一格用 componentsMap 与 componentsTree 做收尾：前者回答「组件从哪来」，后者回答「页面长什么样」，缺一个都跑不通。

坑点清单 ​

  1. 把 UMD 脚本顺序当无关紧要：React、ReactDOM、PropTypes、Next、engine-core、engine-ext 的顺序错了，页面只会白屏。
  2. 先 importSchema 再 setAssets：画布会报组件不存在，因为解析 schema 时还没有物料。
  3. 把组件元数据塞进 packages[].components：引擎只读顶层 components，放错层级会报 Cannot read properties of undefined。
  4. 在同一个页面重复 engine.init：一个页面只能有一个引擎实例，切换章节应整页刷新。
  5. 直接改 node_modules 里的 CSS：样式应通过主题包或覆盖层处理，改依赖会在下次安装时丢失。

自测 ​

1. engine、designer、simulator 三层的职责边界是什么？

engine 负责启动、插件注册与全局生命周期；designer 负责节点树、选中态、拖拽与撤销等编辑行为；simulator 负责把 schema 渲染进 iframe，隔离编辑态与运行态。三者通过引擎上下文通信，而不是互相直接引用。

2. 为什么必须先 `setAssets` 再 `importSchema`？

importSchema 会按 componentsMap 解析每个节点对应的真实组件。如果物料尚未注册，解析不到组件，画布就会报「不是 React 组件」。所以物料注入必须发生在 schema 导入之前。

3. 三栏闭环具体指哪三栏，如何验证？

大纲、画布、设置器。验证方式是：大纲里能看到 Page → Card → Input/Button；画布上能渲染出真实卡片与按钮；选中 Card 后右栏出现「卡片标题」等属性。三栏能互相联动，才算设计器真正跑通。
