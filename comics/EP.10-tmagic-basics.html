EP.10 左右互搏：编辑器和画布是两个独立进程 ​

对应章节：guide/10-tmagic-basics

剧情回顾 ​

  1. 困境：标签君把编辑器和画布写成一个 Vue 组件，结果 Monaco 的 chunk 把整个应用塞到 8 MB，画布还被 element-plus 的样式污染；改一个按钮布局，画布上选中框的坐标全乱了。
  2. 揭秘：码叔指着 index.html 和 runtime.html 两个入口说：拆成父子进程。设计器在主窗口、画布在 iframe，中间用 window.magic 传 DSL 和坐标。
  3. 实证：像素酱跑起 lab，把 DSL 推过去时画布里的 Page 组件立刻渲染出来；拖拽一个 button，iframe 里自动多了一个 DOM 节点。
  4. 结案：码叔收束到「拆成两个 HTML 不是功能需求，是工程隔离需求」——样式隔离、体积隔离、运行时隔离，一个都不能少。

知识点拆解 ​

第一格：大组件不是解决方案 ​

你可能觉得"Vue 组件能嵌套，把画布写成 <Editor><Canvas /></Editor> 不就行了？"。实际上这会带来三个工程问题：

  1. 样式污染：编辑器引入 element-plus、Monaco、moveable，这些库的全局样式会影响画布（比如 canvas 里写 .button { color: red }，被 element-plus 的 .el-button 覆盖）；
  2. 体积膨胀：Monaco-editor 本身就有 2 MB 压缩前，画布根本不需要 Monaco；
  3. 坐标计算：画布需要 position: absolute 的自由布局，如果和设计器混在同一个 DOM 层级，getBoundingClientRect() 的 offset 会被外层容器稀释，选中框永远对不准。

iframe 完美解决这三个问题——独立 DOM、独立打包、独立坐标系统。

对应正文：从一个真实问题说起。

第二格：window.magic 是唯一的桥 ​

两个进程之间唯一"共享"的就是 iframe 里的 window.magic 对象。它由 @tmagic/stage 注入画布进程，包含以下关键方法：

方法调用方职责
onRuntimeReady(callbacks)画布编辑器会推 DSL 过来前先等你把回调挂上
updateRootConfig(dsl)编辑器把完整 MApp DSL 推给画布
updatePageId(id)编辑器切换当前渲染的页面
select(nodeId)编辑器选中某个组件（画布返回元素）
onPageElUpdate(el)画布页面根节点渲染完后回传给编辑器

画布进程的 useEditorDsl() Hook 内部会自动调用 window.magic?.onRuntimeReady(...)，所以运行时不需要手动写这堆 boilerplate——但你得知道它在干什么。

第三格：DSL 链路 ​

编辑器 dsl ref
  ↓ updateRootConfig(dsl)
window.magic（iframe.contentWindow）
  ↓ useEditorDsl 内部处理
root.value = reactive(dsl)
  ↓ computed pageConfig = root.items[curPageId]
Page 组件 :config="pageConfig"
  ↓ Vue 渲染
真实 DOM 节点
  ↓ onPageElUpdate(el)
编辑器画选中框

整条链路是响应式的——中间任何一个节点改了 DSL，画布重新渲染；画布元素位置变了，onPageElUpdate 重新被调。

第四格：能跑是第一位 ​

不要一开始就想"我要手写一个类似 magic 的通信协议"。tmagic 已经把这件事做死了——window.magic 是 stage 包在 iframe 里注入的，你唯一要做的是：

  1. runtime/main.ts 创建 TMagicApp({ platform: 'editor' })；
  2. runtime/App.vue 里 const hook = useEditorDsl()；
  3. 编辑器 App.vue 里给 <TMagicEditor :runtime-url="..."> 传正确地址；

lab 已经把这三件事都写好了，跑起来以后你再看代码，每一行都有意义。

逐格解读 ​

第一格：为什么不能把画布写成组件 ​

画面：标签君在一个 8 MB 的 Vue bundle 前发呆，画布被 element-plus 的按钮样式污染，选中框偏移 30px。码叔从口袋掏出两个独立 HTML 文件。

台词：

码叔：「你写的是一个组件，画布是另一个进程。进程之间只有 iframe 能隔离样式和体积。」

第二格：window.magic 是桥 ​

画面：两个浏览器窗口（父窗口 & iframe）之间画一条带 window.magic 标签的线，updateRootConfig 和 onPageElUpdate 箭头双向。

台词：

像素酱：「哦…原来它不是 Vue 的 props 透传！」 码叔：「props 是同一棵树里的数据流；跨进程只能靠全局对象 + 函数回调。」

第三格：推 DSL ​

画面：编辑器左侧拖了一个 button，DSL 对象变了；iframe 里立刻出现了新的 button DOM 节点；画布下方 Console 里是 [tmagic-runtime] pageConfig updated。

台词：

像素酱：「这就是『所见即所得』——编辑器改 DSL，画布自动重渲染。」

第四格：能跑就行 ​

画面：标签君在看 src/main.ts（Monaco workers + editorPlugin + adapter），画布右下角有一个小小的 debug-bar：pageConfig.id: page_xxx。

台词：

码叔：「能跑 > 能读 > 能扩展。先让这页出来，再想为什么。」

坑点清单 ​

  1. Monaco 顺序错了，code editor 永远空白 — MonacoEnvironment 必须在 app.use(editorPlugin, adapter) 之前配。顺序颠倒 Monaco 初始化时找不到 worker 会静默失败，控制台也不报错。
  2. runtimeUrl 写成了绝对路径 + 端口硬编码 — 用 new URL("/runtime.html", location.href).toString() 自动适配当前 host；dev 模式 Vite 同域下直接写相对路径也可以。
  3. propsConfigs 没配，右侧面板无字段 — 每注册一个新 type 就去 configs/props.ts 加一条 propsConfigs[type] = [...]；否则编辑器不知道该 type 有哪些表单字段可改。
  4. runtime.html 独立打开时画布空白 — 这是正常的；独立打开没有编辑器推送 DSL，useEditorDsl() 会一直等。加 ?localPreview=1 让 runtime 读 localStorage 里的预览 DSL，或让它跑在 iframe 场景。
  5. updateRootConfig 推了 DSL 但画布没渲染 — 检查 platform 是否是 "editor"（让 core 进入编辑模式），以及 runtime 是否真的挂载了 Vue app。App.vue 里 pageConfig 是 undefined 就说明 DSL 没进来。
  6. 画布渲染完了但选中框对不准 — 画布根节点渲染完必须调 magic.onPageElUpdate(root)，否则 stage 拿不到元素坐标，编辑器画的选中框永远偏。

自测 ​

1. tmagic-editor 为什么要拆成两个 HTML 文件（index.html + runtime.html）？三个核心工程诉求是什么？

拆成双进程的三个理由：样式隔离、体积隔离、坐标隔离。

  • 样式隔离：编辑器引入的 Monaco / element-plus / moveable 等全局样式不能污染画布；iframe 天然自带 DOM 沙箱。
  • 体积隔离：Monaco-editor 本身就有 ~2 MB（gzip），画布根本不需要；双入口 build 让 runtime 产物独立于编辑器，画布只装真正需要的运行时。
  • 坐标隔离：画布需要 position: absolute 的自由布局；如果和编辑器混在同一 DOM 层级，getBoundingClientRect() 的 offset 会被外层容器稀释，选中框永远对不准。

iframe 是工程权衡后的选择，不是功能限制。理论上用 Shadow DOM 也能实现样式隔离、用 Code Splitting 实现体积隔离、手动计算多层 offset 解决坐标——但复杂度远高于拆进程。

2. MonacoEnvironment 为什么必须在 app.use(editorPlugin) 之前配？顺序颠倒会发生什么？

Monaco-editor 在第一次调用 create(...) 时就会立即读取 globalThis.MonacoEnvironment.getWorker 来初始化 workers。如果此时 MonacoEnvironment 还没设置：

  • Monaco 会 fallback 到默认的 worker URL（./vs/base/worker/workerMain.js），在 Vite dev 服务器上找不到这个路径；
  • 报错不会直接抛出来——Monaco 的错误处理会吞掉它，返回一个"不工作的 Monaco 实例"；
  • 表现就是：左侧 / 右侧面板里所有需要 code editor 的位置（code action 编辑、数据源 code block、schema 查看）都是空白输入框，没有任何提示。

修复就是在 src/main.ts 最顶部、import editorPlugin 之后、app.use(editorPlugin, adapter) 之前配好 MonacoEnvironment。官方 playground 也是这么写的。

3. 从 src/runtime/App.vue 的视角，描述 DSL 从编辑器推到画布渲染的完整链路。中间经过哪几层响应式包装？

链路分 6 步，每一步都有响应式包装：

  1. 编辑器 TMagicEditor v-model 的 dsl ref 变化 → 通过 stage 推给 iframe；
  2. window.magic.updateRootConfig(dsl) 被调用 → @tmagic/vue-runtime-help 的 useEditorDsl() 内部拿到 config 对象；
  3. root.value = reactive(config) → Vue 把完整 MApp 包成 reactive 对象；
  4. pageConfig = computed(() => root.items[curPageId]) → 计算出当前页面；
  5. <component :is="pageComponent" :config="pageConfig"> → Vue 响应式渲染 Page 组件；
  6. Page 组件内部递归渲染 items 数组里的每个子组件，直到真实 DOM 出现在 iframe 画布。

每层之间用 Vue 的 reactive / ref / computed 连接，任何一层数据变化都会自动向上冒泡到真实 DOM。这也是为什么"所见即所得"能工作——编辑器侧拖组件、改属性，DSL 变化经 updateRootConfig 一路冒到 iframe，画布自动重渲染。
