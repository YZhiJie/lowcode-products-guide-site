EP.12 自由画布的代价 ​

对应章节：guide/12-grapesjs-basics

剧情回顾 ​

  1. 困境：标签君把 GrapesJS 当成"想怎么拖就怎么拖"的玩具，随手拖一堆 div 进去，结果导出的 HTML 是 div 套 div 的"div 地狱"，没有语义化标签、样式全是内联。
  2. 揭秘：像素酱点出 GrapesJS 五大模块——Blocks（能拖什么）、Components（画布有什么）、Styles（CSS 怎么存）、Storage（数据存哪）、Commands（能执行什么）。
  3. 实证：注册 Section / Text / Button / Image 四个 Block，从左侧拖入画布，点"导出"按钮拿到 editor.getHtml() + editor.getCss()。
  4. 结案：码叔收束到「自由不等于无约束」——Storage 自动存 localStorage、Styles 走 CSSOM、导出要在 load 之后。

知识点拆解 ​

第一格：自由画布的困境 ​

GrapesJS 的画布直接操作 DOM——拖进去的每个元素都是真实 HTML 节点。这意味着：

  • 没有 Schema 约束，运营可以拖任意嵌套结构；
  • 没有组件协议，所有组件都是通用 div + 内联样式；
  • 没有字段模型，表单值要自己从 DOM 收集。

"自由"的代价是导出的 HTML 质量完全取决于使用者的前端素养。如果不做约束，拖出来的页面会是维护噩梦。

第二格：五大模块 ​

模块职责API
Blocks左侧可拖入模板editor.Blocks.add(id, {...})
ComponentsDOM 模型层editor.Components.addComponent(...)
StylesCSS 规则管理editor.Styles.getAll()
StorageManager持久化editor.store() / editor.load()
Commands可执行操作editor.runCommand('get-html')

五大模块通过事件总线通信。你不需要直接操作 DOM——所有修改走 Components 模型层，GrapesJS 负责同步到 iframe。

第三格：Block 注册与导出 ​

ts
editor.Blocks.add("button", {
  label: "Button",
  category: "Basic",
  content: { type: "button", content: "Click me", styles: "..." },
});

content 可以是字符串 HTML 或组件对象。组件对象能指定 type、styles、traits 等。

导出：

ts
const html = editor.getHtml(); // 画布 body 内 HTML
const css = editor.getCss(); // CSS 规则

第四格：存储与导出时机 ​

StorageManager 默认存 localStorage。autosave: true 自动存，autoload: true 自动读。lab 里手动在 component:update 事件调 editor.store()。

getHtml() / getCss() 必须在 editor.on('load') 之后调，否则画布还没渲染完。

坑点清单 ​

  1. CSS 必须引入：grapesjs/dist/css/grapes.min.css 不引入的话面板样式丢失但不报错。
  2. 不要直接操作 iframe DOM：通过 Components 模型层修改，直接操作 DOM 会导致模型视图不一致。
  3. Block 的 styles 全局注入：多次拖入会注入多次相同 CSS 规则，建议用类名隔离。
  4. getHtml 要在 load 之后：编辑器初始化是异步的，用 editor.on('load', ...) 确保就绪。
  5. StorageManager 的 key 要隔离：不同章节用不同 localStorage key，避免互相覆盖。

自测 ​

1. GrapesJS 和 tmagic-editor 的画布最本质的区别是什么？

GrapesJS 的编辑器和画布是单进程——编辑器持有 iframe 的 contentDocument，直接在里面操作 DOM，不需要 DSL 同步。tmagic-editor 是双进程——编辑器在父窗口、画布在 iframe 跑独立 runtime，通过 window.magic 通信传 DSL。

单进程的好处是简单（没有通信开销、没有 DSL 序列化），代价是编辑器和画布共享 JS 上下文、样式隔离靠 iframe 天然沙箱。双进程的好处是完全隔离（编辑器包不影响画布、画布可以独立部署），代价是通信复杂、要维护 DSL 同步。

2. Block 的 content 字段有哪两种形式？各自适用场景？

两种形式：

  • 字符串 HTML：content: '<div class="card">...</div>'。简单直接，适合静态内容、不需要 trait 的场景。
  • 组件对象：content: { type: 'button', content: 'Click', styles: '...' }。可以指定组件 type、内联样式、traits 等，适合需要自定义属性面板的组件。

字符串形式拖入后就是纯 DOM，没有业务语义；组件对象形式可以挂 trait，让右侧面板出现定制字段。

3. 为什么 GrapesJS 不适合做中后台表单？

三个原因：

  1. 没有表单字段模型：每个 input 是独立 DOM 节点，没有统一的字段值管理和校验机制。amis/Formily 有 Field 模型，能声明式校验、联动。
  2. 字段联动要手动写 JS：省市区联动在 GrapesJS 里要写 onChange 事件处理 DOM，amis 用 source + autoFill 声明式搞定。
  3. 提交序列化困难：要遍历 DOM 收集 input 值，无法像 Schema 驱动那样直接 JSON.stringify(schema.data)。

所以 GrapesJS 适合营销落地页、邮件模板这种"视觉为主"的场景，不适合中后台表单。
