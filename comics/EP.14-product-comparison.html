EP.14 五强横评：没有银弹 ​

对应章节：guide/14-product-comparison

剧情回顾 ​

  1. 困境：标签君接到「客户运营后台」需求，面前摆着 amis / Formily / lowcode-engine / tmagic-editor / GrapesJS 五个产品，功能清单各有千秋，不知道选哪个，陷入选型焦虑。
  2. 揭秘：像素酱掏出一张选型决策树——别比功能清单，先问自己三个问题：表单还是页面？自由还是约束？是否需要跨端？三问答完，选型范围立刻从 5 个缩小到 1-2 个。
  3. 实证：拿同一个「客户运营后台」需求，分别用五个产品实现一遍——amis 半天搭完 CRUD 最快、Formily 复杂表单联动最强、lowcode-engine 物料插件最灵活、tmagic-editor 一套 DSL 跨端最好、GrapesJS 自由画布最自由。
  4. 结案：码叔一锤定音——没有银弹，只有最适合场景的选型。amis 打中后台、Formily 打复杂表单、lowcode-engine 打深度定制、tmagic 打 H5 活动页、GrapesJS 打营销落地页。

知识点拆解 ​

第一格：选型焦虑的本质 ​

选型焦虑不是因为产品少，而是因为产品太多且各有所长。五个产品都能做「客户运营后台」，但开发效率、扩展空间、跨端能力、维护成本完全不同。如果不先定义场景边界，就会在功能清单里迷失。

选型的第一步不是看产品功能，而是定义需求边界：表单还是页面？单端还是多端？运营自服务还是研发交付？边界清楚了，候选产品自然就少了。

第二格：选型决策树三问 ​

问题分支推荐方向
Q1 表单还是页面？表单为主Formily / amis
Q1 表单还是页面？页面为主进入 Q2
Q2 自由还是约束？要自由画布GrapesJS
Q2 自由还是约束？要 Schema 约束进入 Q3
Q3 是否跨端？PC + H5 + 小程序tmagic-editor
Q3 是否跨端？单端 PCamis / lowcode-engine

三问的本质是逐级收敛：先按交付形态收敛（表单/页面），再按编辑范式收敛（自由/约束），最后按端能力收敛（单端/跨端）。每一问砍掉一半候选，三问之后就剩 1-2 个。

第三格：五强实证对比 ​

产品优势短板
amisJSON 配置半天搭完 CRUD，上线最快灵活性差，定制组件成本高
Formily表单联动、校验、字段模型最强只做表单，页面搭建要自己拼
lowcode-engine物料 + 插件体系，扩展空间最大上手成本高，需要自研物料
tmagic-editor一套 DSL 出 PC + H5 + 小程序生态偏腾讯系，社区资料少
GrapesJS自由画布，落地页排版最自由没有表单模型，不适合中后台

关键洞察：没有全能产品。每个产品都在某一个维度做到极致，同时在另一个维度妥协。选型就是选取舍——你愿意为哪个维度买单、愿意牺牲哪个维度。

第四格：场景选型映射 ​

  • amis → 中后台系统：CRUD 密集、追求上线速度、运营配置为主。
  • Formily → 复杂表单场景：联动多、校验重、字段多，表单是核心交互。
  • lowcode-engine → 深度定制化：有研发资源、要自研物料和插件体系。
  • tmagic-editor → H5 活动页：多端投放、一套 DSL、运营频繁上线。
  • GrapesJS → 营销落地页：自由排版、视觉为主、运营自服务。

记住一句话：选型 = 场景匹配，不是技术崇拜。别问"哪个产品最好"，要问"这个场景最需要哪个能力"。

坑点清单 ​

  1. 只看功能清单不看场景：五个产品功能列表都很长，逐项对比永远选不出来。先定场景再看功能，场景不匹配的功能再强也没用。
  2. 低估自研成本：lowcode-engine 灵活但需要自研物料和插件，没有 2-3 个前端长期投入很难跑通。团队人手不足时，amis 的"开箱即用"反而更划算。
  3. 跨端需求想当然：tmagic-editor 的跨端是"一套 DSL 多端渲染"，但端能力差异大的组件（如地图、视频）仍要写多端适配。不是写一次就真的到处跑。
  4. GrapesJS 用于中后台表单：GrapesJS 没有表单字段模型，联动和校验要手动写 JS，提交要遍历 DOM 收值。中后台表单用 amis/Formily 效率高一个数量级。
  5. 把 amis 当万能：amis 适合标准 CRUD，但定制交互（如复杂拖拽、自定义布局）要写自定义组件，成本不比自研低。超出标准场景时要及时换方案。
  6. 忽视生态和社区：tmagic-editor 资料偏腾讯系，GrapesJS 是英文社区，amis 中文社区最活跃。遇到问题时，社区活跃度直接决定排障速度。

自测 ​

1. 为什么说选型决策树的三问是"逐级收敛"而不是"并列筛选"？

因为三个问题有依赖关系，必须按顺序问：

  1. 先定交付形态（表单还是页面）——这是最粗的粒度，直接砍掉一半候选。表单为主的场景，GrapesJS 这种自由画布基本不用考虑；页面为主的场景，Formily 这种纯表单引擎也不合适。
  2. 再定编辑范式（自由还是约束）——确定是页面后，再问运营要自由拖拽还是要 Schema 约束。自由拖拽选 GrapesJS，要约束就进入第三问。
  3. 最后定端能力（单端还是跨端）——确定要约束后，再问是否需要跨端。跨端选 tmagic，单端选 amis 或 lowcode-engine。

如果并列筛选，会出现"表单但要跨端"这种矛盾组合，反而选不出来。逐级收敛保证每一步都在缩小范围，不会出现死胡同。

2. 同一个"客户运营后台"需求，为什么 five 个产品都能做但体验天差地别？

因为"能做"和"做得好"是两回事：

  • amis：JSON 配置半天搭完，上线快，但定制交互要写自定义组件。
  • Formily：表单部分极强，但列表、看板等页面元素要自己用 React 拼。
  • lowcode-engine：灵活度最高，但物料和插件要自研，前期投入大。
  • tmagic-editor：一套 DSL 出多端，但 PC 端中后台的复杂交互不如 amis 顺手。
  • GrapesJS：自由排版，但表单联动和数据提交要手动处理。

差异的根源是每个产品的设计目标不同：amis 目标是"快速交付标准中后台"，Formily 目标是"管好复杂表单"，lowcode-engine 目标是"搭建可定制的搭建平台"，tmagic 目标是"多端投放"，GrapesJS 目标是"自由视觉搭建"。目标不同，能力侧重就不同。

所以选型不是找"能做的"，而是找"做得最顺手的"——同一个需求，用错产品就是事倍功半。

3. 如果团队只有 1 个前端，要做一个带复杂表单的中后台，该怎么选？

推荐 amis，理由：

  1. 人少优先开箱即用：lowcode-engine 需要自研物料和插件，1 个人撑不起物料生态；GrapesJS 要自己管表单联动和数据提交，中后台场景下工作量大。amis 开箱即用，JSON 配置就能搭 CRUD，1 个人能扛住。
  2. 复杂表单 amis 能覆盖 80%：amis 的表单组件联动（source、autoFill、visibleOn）能覆盖大多数中后台表单场景，虽然不如 Formily 灵活，但够用。
  3. 如果表单真的极其复杂（如动态字段、跨字段校验、自定义渲染），可以在 amis 里嵌入 Formily 作为自定义组件——amis 管页面骨架和数据，Formily 管复杂表单局部。这是大厂常用的组合拳。

不推荐 lowcode-engine 的原因：1 个前端要同时做物料、插件、设计器、渲染器，半年都跑不通 MVP，业务等不起。
