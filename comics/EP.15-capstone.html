EP.15 从选型到上线 ​

对应章节：guide/15-capstone

剧情回顾 ​

  1. 需求评审：标签君拿到「客户运营后台」需求，面前摆着 amis / Formily / lowcode-engine / tmagic-editor / GrapesJS 五个产品，不知道该选哪个。
  2. 架构拆解：像素酱把需求一拆二——列表和概览页交给 amis，复杂表单交给 Formily，中间用 React Router 串联，数据统一存 localStorage。
  3. 编码实证：同一界面里，amis 的 CRUD 表格和 Formily 的联动表单共存于同一个 DOM，没有 iframe 隔离，互不干扰。
  4. 上线复盘：码叔一锤定音——组合拳比单打独斗强；选型不是选一个，而是按场景组合。

知识点拆解 ​

第一格：选型焦虑不等于没有答案 ​

五个产品都能做「客户运营后台」，但每个产品只擅长其中一部分。amis 擅长 CRUD 列表，Formily 擅长复杂表单，lowcode-engine 擅长深度定制，tmagic 擅长跨端，GrapesJS 擅长自由排版。

关键认知：选型不是「选一个最强的」，而是「按场景拆分，每个场景选最合适的」。一个项目里用多个低代码产品是正常且推荐的做法。

第二格：架构拆解 = 按能力边界切分需求 ​

把「客户运营后台」拆成三块：

模块负责产品理由
列表页 / 概览页amisSchema 配置半天搭完 CRUD，上线速度最快
复杂表单（联动 + 校验）Formily领域模型对表单抽象最彻底，联动校验能力最强
页面串联 / 数据存储React Router + localStorage轻量路由串联两个产品的运行时，数据本地持久化

为什么用 React Router 串联：amis 和 Formily 都是 React 组件库，可以在同一个 React 应用里共存。用 React Router 做页面级路由，列表页用 amis 渲染，表单页用 Formily 渲染，不需要 iframe 隔离。

为什么用 localStorage：capstone 是前端演示项目，不需要后端。用 localStorage 存客户数据，amis 的表格和 Formily 的表单都读写同一份数据，实现真正的「同一数据源」。

第三格：同一 DOM 共存，无 iframe 隔离 ​

组合拳的核心是同一 DOM 共存：

  • amis 的 CRUD 组件和 Formily 的 Form 组件挂载在同一个 React 应用的不同路由下；
  • 两者共享同一个 localStorage 数据源；
  • 没有 iframe，没有跨域通信，组件之间可以直接通过 React 状态或全局 store 通信。

对比 iframe 方案：如果用 iframe 嵌入 amis 页面，表单和列表之间的数据同步要走 postMessage，复杂且易错。同一 DOM 方案直接读写同一份数据，简单可靠。

第四格：组合拳比单打独斗强 ​

方案优势劣势
单一 amis上线快、Schema 统一复杂表单联动弱、定制难
单一 Formily表单最强列表/概览要自己写
amis + Formily 组合各取所长、无 iframe 共存需要两套 Schema、两套心智

结论：组合拳的开发效率和最终效果都优于单打独斗。代价是需要理解两套产品的 API，但这个代价远小于「强行用一个产品做所有事」的返工成本。

选型的最终心法：选型不是选一个，而是按场景组合。

坑点清单 ​

  1. 强行用一个产品做所有事：用 amis 做复杂表单联动，表达式写起来极其痛苦；用 Formily 做列表，要自己拼表格组件。按场景拆分才是正解。
  2. 用 iframe 嵌入而不是同一 DOM：iframe 会导致数据同步走 postMessage、样式隔离、高度自适应等一堆问题。amis 和 Formily 都是 React 组件，直接在同一个应用里渲染即可。
  3. 两套数据源不同步：amis 读 localStorage，Formily 写 localStorage，如果读写时机不一致会出现数据脏读。最好封装一个统一的数据访问层，两个产品都调用它。
  4. 忽视路由设计：列表页和表单页之间的跳转、编辑态回显、新建态清空，都要在路由层面设计好。否则用户体验割裂。
  5. localStorage 容量限制：localStorage 通常只有 5MB，存大量客户数据会超限。生产环境要接后端 API，localStorage 只适合演示或轻量场景。
  6. Schema 不一致导致维护困难：amis 用 JSON Schema，Formily 用自己的字段模型，两套 Schema 没有共享。如果业务字段变了，要改两处。可以考虑用一个中间模型层统一描述字段，再分别生成两套 Schema。

自测 ​

1. 为什么「客户运营后台」要用 amis + Formily 组合，而不是只用其中一个？

因为需求里同时包含两类差异很大的场景：

  • 列表 / 概览页：CRUD 密集、结构标准，amis 的 JSON Schema 半天就能搭完，上线速度最快。
  • 复杂表单：联动多、校验重、字段多，Formily 的领域模型（Field、reactions、异步校验）是五个产品里最强的。

如果只用 amis，复杂表单的联动和校验要写大量自定义表达式，痛苦且易出错；如果只用 Formily，列表和概览页要自己写 React 组件，失去了低代码的效率优势。

组合使用让每个产品待在自己的「甜蜜区」，整体效率最高。

2. 同一 DOM 共存相比 iframe 嵌入，优势体现在哪里？

同一 DOM 共存的优势：

  1. 数据同步简单：amis 和 Formily 读写同一份 localStorage（或全局 store），不需要 postMessage 跨 frame 通信。
  2. 样式统一：共享同一套 CSS 变量和主题，不会出现 iframe 内外样式不一致。
  3. 组件可互操作：可以在 Formily 表单里嵌入 amis 的渲染组件，或在 amis 页面里嵌入 Formily 表单，无需通信桥接。
  4. 性能更好：少一个 iframe 进程，内存和启动开销更低。

iframe 方案的唯一优势是「隔离」——两个产品的运行时互不影响。但 amis 和 Formily 都是成熟的 React 库，冲突概率很低，同一 DOM 共存完全可行。

3. 除了 amis + Formily，还有哪些常见的低代码组合拳？分别解决什么问题？

常见组合：

  • amis 页面 + Formily 表单（本章方案）：中后台系统，列表用 amis、复杂表单用 Formily。
  • lowcode-engine 设计器 + tmagic-editor 运行时：用 lowcode-engine 搭建设计器，导出的 Schema 交给 tmagic 做跨端渲染（PC + H5 + 小程序）。
  • GrapesJS 落地页 + amis 后台：营销落地页用 GrapesJS 自由排版，运营后台用 amis 管内容。
  • amis + GrapesJS：标准中后台页面用 amis，特殊视觉页用 GrapesJS 单独做。

组合的核心原则是按场景切分：每个产品待在自己擅长的场景，用轻量胶水（React Router、数据层、事件总线）串联，避免让一个产品做它不擅长的事。
