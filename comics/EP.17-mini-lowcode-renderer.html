EP.17 递归渲染的魔法 ​

对应章节：guide/17-mini-lowcode-renderer

剧情回顾 ​

  1. Schema 树：一棵 page → container → text/button 的 Schema 树摆在像素酱面前，她要把它变成真实页面。
  2. 递归渲染：像素酱演示 render(node) 函数——里面调 render(child)，像套娃一样一层层往里钻。
  3. 表达式替换：标签君看到 Schema 里的 $&#123;&#123; name &#125;&#125; 被替换成了「张三」，惊讶数据里的表达式居然能在渲染时求值。
  4. 终止条件：码叔提醒——递归必须有终止条件（children 为空时停止），否则无限套娃导致栈溢出。

知识点拆解 ​

第一格：Schema 是树，不是列表 ​

Schema 的核心结构是递归树：每个节点都有 type、props，可能有 children。children 里的每个元素又是一个完整的 Schema 节点。

page
├── container
│   ├── text
│   └── button
└── container
    └── ...

Renderer 面对的不是一个扁平列表，而是一棵任意深度的树。这决定了 Renderer 的实现方式必须是递归。

第二格：递归函数的结构 ​

递归渲染函数的结构非常简洁：

ts
function render(node: SchemaNode): VNode {
  const component = resolveComponent(node.type);
  const children = (node.children || []).map(render);
  return h(component, node.props, children);
}

三个步骤：

  1. 根据 node.type 找到对应的组件实现；
  2. 递归渲染所有子节点，得到子 VNode 数组；
  3. 用 h() 把当前组件和子节点组装成 VNode。

这个函数之所以能工作，是因为 Schema 的结构是递归的，render 的结构也是递归的，两者同构。

第三格：表达式求值 ​

Schema 的 props 里可以写表达式 $&#123;&#123; name &#125;&#125;。Renderer 在渲染前会遍历 props，遇到 $&#123;&#123; &#125;&#125; 包裹的表达式，就用**上下文（context）**里的数据求值替换。

上下文: { name: "张三" }
Schema:  { text: "${{ name }}" }
渲染后:  { text: "张三" }

表达式求值的本质是：把数据里的字符串模板，用运行时上下文替换成实际值。这让同一份 Schema 可以渲染出不同的内容（数据驱动的体现）。

第四格：递归的终止条件 ​

递归必须有终止条件，否则会无限调用自己，最终栈溢出（Stack Overflow）。

Renderer 的终止条件是：node.children 为空（或不存在）。此时不再递归调用 render，直接返回叶子节点的 VNode。

ts
function render(node) {
  // 终止条件：没有子节点
  if (!node.children || node.children.length === 0) {
    return h(component, node.props);
  }
  // 递归
  const children = node.children.map(render);
  return h(component, node.props, children);
}

没有终止条件的递归 = 死循环 = 栈溢出。

坑点清单 ​

  1. 忘记终止条件：递归函数最常见的 bug 就是没有终止条件，导致栈溢出。写递归前先想清楚「什么时候停」。
  2. 循环引用导致无限递归：如果 Schema 里出现循环引用（A 的 children 包含 A），递归会无限进行。需要做环检测或限制最大深度。
  3. 表达式求值的沙箱问题：直接 eval 表达式有安全风险，应该用 new Function 或专门的表达式解析器，限制可访问的变量。
  4. 上下文丢失：递归时要把上下文（数据、作用域）正确传递给子节点，否则表达式找不到变量。
  5. 组件注册缺失：resolveComponent(node.type) 如果找不到组件，应该降级渲染而不是崩溃。
  6. props 里的表达式和字面量混淆：要区分 "$&#123;&#123; name &#125;&#125;"（表达式）和 "&#123;&#123; name &#125;&#125;"（普通字符串），用 $&#123;&#123; &#125;&#125; 作为表达式标记。

自测 ​

1. 为什么 Renderer 必须用递归实现，而不是循环？

因为 Schema 是递归树结构——每个节点的 children 又是一组完整的 Schema 节点，深度可以是任意的。

循环只能处理扁平结构（一层），而递归能天然匹配树的嵌套结构。render 函数的逻辑和 Schema 的结构同构：节点有 children 就递归处理 children，没有就停止。

如果用循环处理树，需要自己维护一个栈来模拟递归，代码反而更复杂。递归是处理树结构最自然的方式。

2. Renderer 里的表达式 `${{ name }}` 是怎么被替换成「张三」的？

分三步：

  1. 识别表达式：Renderer 遍历 props，发现值是 "$&#123;&#123; name &#125;&#125;" 格式的字符串；
  2. 解析表达式：取出 &#123;&#123; &#125;&#125; 里的表达式 name，在上下文（context）里查找 name 的值；
  3. 替换：用上下文里的值（"张三"）替换整个 $&#123;&#123; name &#125;&#125;。

上下文通常包含页面的数据对象、当前节点的 props、全局变量等。表达式求值的本质是「数据 + 模板 = 最终值」，这也是「数据驱动视图」的体现。

生产级实现会用专门的表达式解析器（如 jsep），而不是简单的字符串替换，以支持复杂表达式（算术、逻辑、函数调用）。

3. 递归渲染如果没有终止条件会发生什么？怎么避免？

没有终止条件的递归会无限调用自己，每次调用都会在调用栈上压入一帧，最终超出栈的容量限制，抛出 Stack Overflow 错误，页面崩溃。

避免方法：

  1. 明确终止条件：Renderer 的终止条件是 node.children 为空，此时直接返回叶子 VNode，不再递归；
  2. 环检测：如果 Schema 可能存在循环引用（A → B → A），需要在递归时记录已访问的节点路径，遇到重复节点就停止；
  3. 最大深度限制：设置一个最大递归深度（如 100），超过就报错，防止异常 Schema 导致崩溃。

核心原则：写递归前先想清楚「什么时候停」。
