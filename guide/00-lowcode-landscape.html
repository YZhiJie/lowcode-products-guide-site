第 00 章 · 低代码全景：五个工具箱，先选对再动手 ​

前置章节：无。这是整套教程的起点。
所需环境：Node 22 LTS + pnpm 9.15.4，macOS / Linux / Windows（WSL2）均可。
难度：★☆☆
本章交付物：一张选型地图、一份 7 个 lab 的安装矩阵、一个能跑起来的文档站、一套统一的验收命令。

欢迎来到这套低代码教程。接下来你会接触五个定位完全不同的产品，再加一个从零写起的教学级引擎。它们都能被叫作「低代码」，但解决的问题并不相同。本章不急着讲 API，而是先把地图铺开：低代码有哪些形态、每个形态对应什么产品、你的需求应该落在哪一格。

本章你将获得 ​

读完本章，你应该能回答三个问题：

  1. 面对一个「做个后台」的需求，如何判断该用 Schema 驱动、表单模型、编排引擎还是自由画布？
  2. 七个实验室分别验证什么能力，安装和启动命令是什么？
  3. 这套教程的两卷如何衔接：产品实战卷解决「怎么用」，进阶卷解决「怎么造」。

低代码并不是一个产品品类，而是一组用配置、模型或可视化操作替代重复编码的手段。手段不同，适用边界就不同。把边界搞错，低代码就会从「提效工具」变成「维护负担」：页面看起来半天就搭完了，但改一个字段要翻三层配置，排查一个问题要同时理解产品协议和业务代码。

本章的选型地图会反复出现在后续章节里。每学完一个产品，你都应该回到这张地图，重新标注它的能力边界。选型不是一次性的拍板，而是随着团队能力、页面生命周期、交付节奏不断修正的判断。

先看漫画 ​

这一话讲了四个动作：先承认「拍脑袋选型」的代价，再按形态给工具分类，然后用四个问题缩小范围，最后强调「先跑通最小闭环」。漫画里的四个问题会在本章第三节展开，七个 lab 则会在第四节给出安装矩阵。

如果你只记住一句话：低代码选型的第一步不是比较功能列表，而是描述页面由谁维护、数据从哪里来、改动有多频繁。

完整的逐格讲解在 EP.00 漫画讲解，包含四格对应的知识点、坑点清单和三道自测题。建议先看漫画建立直觉，再回到正文看细节。

低代码全景与选型维度 ​

五类形态，而不是五个产品 ​

行业里常把低代码当成一个赛道，但真正落地时，你面对的是五种不同的技术形态。它们的产物、扩展方式和失败模式都不一样。

形态核心产物典型代表最适合主要代价
Schema 驱动一份 JSON 页面配置amis中后台 CRUD、运营后台复杂交互要写自定义组件
表单领域模型字段树 + 响应式规则Formily复杂表单、联动、异步校验页面层与数据层要自己组装
可视化编排引擎设计器 + 渲染器 + 物料协议lowcode-engine平台型产品、长期演进的搭建系统概念多、接入与治理成本高
页面搭建器编辑器 + 运行时 + 数据源tmagic-editor运营页面、活动页、内容页偏页面生产，复杂业务逻辑弱
自由画布HTML/CSS 结构 + 样式GrapesJS视觉自由、静态页面、邮件模板工程约束弱，需要自建规范

这张表不是功能对比，而是「产物形态」对比。amis 的产物是一棵 JSON Schema 树，Formily 的产物是字段模型，lowcode-engine 的产物是带物料协议的节点树，tmagic-editor 的产物是可被运行时解释的页面 Schema，GrapesJS 的产物更接近真实 DOM 与 CSS。

产物形态决定了三件事：谁来维护、如何 diff、如何回滚。JSON 配置容易做版本管理和灰度；DOM/CSS 产物更自由，但结构约束弱；字段模型擅长表达联动，却不负责页面布局。选型时先看产物，再看功能，能避免很多「 demo 很惊艳、上线很痛苦」的误判。

产品矩阵：五个主线 + 两个对照 ​

本教程的主线是五个产品，另有两个平台型产品只做对照，不进入安装链路。

产品定位技术栈教程章节是否做 lab
amisSchema 驱动中后台React 1801~03是
Formily表单领域模型React 18 + antd 504~06是
lowcode-engine可视化编排内核React（跟随官方 demo）07~09是
tmagic-editor页面搭建器Vue 310~11是
GrapesJS自由画布原生 TypeScript12~13是
Appsmith平台型应用搭建自带后端 + Docker14（对照）否
ToolJet平台型应用搭建自带后端 + Docker14（对照）否

为什么把 Appsmith 和 ToolJet 放在对照位？因为它们不是「前端库」，而是「平台」：自带后端、数据库连接、账号体系，安装形态是 Docker 服务。把它们塞进主线 lab，会让读者误以为低代码的前端选型必须绑定某个后端平台。第 14 章会解释它们的适用场景和代价，但本教程的安装链路只覆盖纯前端可验证的部分。

选型四问 ​

把功能列表收起来，先回答四个问题。它们分别对应「结构稳定性、表单复杂度、编排需求、布局自由度」。

第一问：页面结构稳定、以 CRUD 为主吗？ 如果答案是「是」，优先考虑 amis。列表、表单、弹窗、筛选、分页这些中后台高频结构，amis 已经用 Schema 封装好了。你付出的代价是学习它的配置协议；换来的是极低的页面搭建成本。

第二问：表单联动与校验是核心难点吗？ 如果页面主体是表单，且联动关系复杂（省市区、额度计算、异步唯一性校验、动态增减行），Formily 的字段模型比任何「配置页面」都更可靠。它把字段当成一等公民，联动写在模型层，测试和复用都更容易。

第三问：需要让非开发者长期搭建页面吗？ 这时候才轮到 lowcode-engine 或 tmagic-editor。两者都提供设计器，但侧重点不同：lowcode-engine 更像平台底座，强调物料、插件、出码与扩展；tmagic-editor 更像页面生产工具，强调编辑器与运行时分离、数据源、事件和动画。

第四问：需要像素级自由布局并导出 HTML/CSS 吗？ 如果产物要脱离框架运行，或者视觉还原度是第一位，GrapesJS 更合适。它的画布直接操作 DOM，自由度高，但工程约束需要团队自己补。

四个问题没有标准答案，但它们能帮你排除掉明显不合适的选项。选型的目标不是找到「最强」的产品，而是找到「代价可接受」的产品。

两卷路线：先用，再造 ​

这套教程分两卷，顺序固定。

产品实战卷（第 00~15 章）按产品逐个上手：先跑通最小示例，再理解核心协议，最后做一个可验收的页面或扩展。学完这一卷，你应该能为一个真实需求完成选型，并搭出可运行的原型。

从零搭建进阶卷（第 16~20 章）从空目录开始，写一个教学级 mini 低代码系统：Schema 协议、递归渲染器、可视化设计器、撤销重做与插件、出码导出。学完这一卷，你应该能解释商业产品的内核链路，而不是只会调用 API。

两卷共用同一套漫画、文档门禁和部署链路。进阶卷不依赖任何商业低代码产品包，只依赖 Vue 3、Vite、TypeScript、Vitest、zod 和 jsep。它不会宣称生产可用，也不会和商业产品做功能对等比较；它的价值是「把黑盒拆开给你看」。

环境准备与跑通仓库 ​

固定版本，不要追新 ​

整套教程固定两个版本：Node 22 LTS 与 pnpm 9.15.4。原因很现实：lockfile 格式、依赖解析、CI 缓存行为都跟主版本绑定。用 Node 24 配 pnpm 12 生成 lockfile，再拿到 CI 的 Node 22 + pnpm 9 上跑 --frozen-lockfile，最常见的结局就是安装失败或依赖树漂移。

先确认版本：

bash
node -v    # 期望 v22.x
pnpm -v    # 期望 9.15.4

如果本机装了多个 Node 版本，用 nvm 切换；如果 pnpm 版本不对，用 corepack 激活固定版本：

bash
nvm install 22
nvm use 22
corepack enable
corepack prepare pnpm@9.15.4 --activate

不要用 npm install -g pnpm 追最新版。全局安装会把版本绑死在本机，换一台机器或进 CI 又要重来；packageManager 字段加 corepack 才是可复现的做法。

文档站：三条命令 ​

项目根只负责文档站与校验脚本，不管理 labs 的依赖。首次运行：

bash
pnpm install
pnpm docs:dev

浏览器打开终端输出的地址（默认 http://localhost:5173），应能看到首页。构建与本地预览：

bash
pnpm docs:build
pnpm docs:preview

构建产物在 .vitepress/dist。部署到 GitHub Pages 时，CI 会注入 DEPLOY_BASE，把资源前缀改成 /<仓库名>/；本地开发不需要设置这个变量。

七个 lab 的安装矩阵 ​

七个 lab 是独立工程，各自有 package.json 和 pnpm-lock.yaml，不共享 node_modules，也不在根目录建 workspace。这样做的好处是 React 18/19、antd 4/5、Vue 3 的版本不会互相污染；代价是要多敲几次 cd。

lab技术栈章节目录建议端口启动命令
amisReact 18 + Vite01 / 02 / 035174cd labs/amis && pnpm install && pnpm dev
formilyReact 18 + antd 5 + Vite04 / 05 / 065175cd labs/formily && pnpm install && pnpm dev
lowcode-engineReact + 官方 demo 构建链07 / 08 / 095176cd labs/lowcode-engine && pnpm install && pnpm dev
tmagic-editorVue 3 + Vite10 / 115177cd labs/tmagic-editor && pnpm install && pnpm dev
grapesjs原生 TypeScript + Vite12 / 135178cd labs/grapesjs && pnpm install && pnpm dev
capstoneReact 18 + amis + Formily155179cd labs/capstone && pnpm install && pnpm dev
mini-lowcodeVue 3 + Vite + Vitest16~205180cd labs/mini-lowcode && pnpm install && pnpm dev

端口只是约定。Vite 发现端口被占用会自动顺延，以终端实际输出为准。所有 lab 的端口都会回填到 命令速查，方便你对照。

每个 lab 的根页面都列出章节目录、验收点和当前版本。进入 lab 后先看根页面，再点进具体章节，不要直接猜路由。

一套验收命令 ​

项目根提供统一门禁：

bash
pnpm check

它会依次执行环境检查、漫画校验、内容校验、链接校验、lab 结构校验和格式检查。任何一项失败都会返回非零退出码。CI 与本地使用同一条命令，避免「本地过了、CI 挂了」。

产品 lab 的安装、构建和烟测由另一个脚本在本地执行：

bash
node scripts/smoke-labs.mjs --all

这个脚本不进 CI，因为它要安装七个工程，耗时且依赖网络。CI 只安装根工程，保证文档门禁和部署稳定。

本章的最小验收 ​

完成环境准备后，你应该能独立完成下面三步，且每一步都有可见输出：

  1. pnpm docs:dev 启动成功，首页、教程侧边栏、搜索框都可用；
  2. node scripts/check-env.mjs 输出 Node、pnpm、七个 lab 目录和文档依赖全部通过；
  3. 任选一个已完成的 lab，按矩阵中的命令启动，根页面能进入对应章节。

如果第三步还做不到，不要急着往下读。先记录报错原文，对照下一节的「跑不起来？」逐条排查。低代码教程最容易出现的问题不是概念难，而是环境版本不对导致示例跑不起来。

跑不起来？ ​

报错一：ERR_PNPM_UNSUPPORTED_ENGINE 或 lockfile 版本不兼容 ​

现象：执行 pnpm install --frozen-lockfile 时报锁文件版本不支持，或者提示当前 Node 版本不满足 engines。

原因：本机 Node 低于 22，或 pnpm 主版本不是 9。lockfile 的 lockfileVersion 与 pnpm 主版本绑定，跨主版本会直接拒绝安装。

修复：

bash
node -v
nvm install 22
nvm use 22
corepack prepare pnpm@9.15.4 --activate
pnpm -v
pnpm install

如果是在 lab 目录里报错，先确认你进对了目录。每个 lab 都有自己的 lockfile，根目录的 lockfile 不能替代。

报错二：Cannot find module 'vitepress' ​

现象：pnpm docs:dev 直接报模块找不到，或提示 .vitepress/config.ts 加载失败。

原因：根工程依赖没有安装，或 node_modules 被清理过。也可能是在 lab 目录里执行了根命令。

修复：

bash
cd lowcode-products-guide
pnpm install
pnpm docs:dev

确认当前目录有 package.json 且其中包含 vitepress。如果刚切换过 Node 版本，重新执行一次 pnpm install，避免原生依赖与 Node ABI 不匹配。

报错三：文档站能构建，但页面白屏 ​

现象：pnpm docs:build 成功，浏览器打开却是空白；控制台可能没有任何报错。

原因：Markdown 里出现了未被反引号包裹的裸花括号，例如直接写 { name: "amis" }。VitePress 底层的 Markdown 插件会把它当成 HTML 属性解析，SSR 阶段不报错，客户端 hydration 失败后白屏。

修复：把所有代码片段放进行内反引号或围栏代码块：

md
配置里写 `{ "type": "page" }`，不要裸写花括号。

同理，正文里的 localhost 地址也要包进反引号，否则链接检查器会把它当成外链或死链。改完后重新构建，并用浏览器强刷一次。

报错四：端口被占用 ​

现象：pnpm dev 提示端口已在使用，或者启动后访问的是另一个项目。

原因：默认端口被其他进程占用，Vite 自动顺延到了新端口，但你还开着旧地址。

修复：看终端输出里的实际端口，或者显式指定：

bash
pnpm dev --port 5181

不要直接杀掉不认识的进程。先确认占用者是不是你正在跑的其他 lab，再决定换端口还是关进程。

避坑清单 ​

  1. 不要建根级 pnpm-workspace.yaml。 七个 lab 一旦被提升到同一个 workspace，React 18/19、antd 4/5、Vue 3 的依赖会互相污染，而且 lockfile 变动会让 CI 的 --frozen-lockfile 频繁失败。根工程只管理文档与校验脚本。
  2. 不要把 latest 或 ^ 写进产品核心包。 低代码产品的 API 跨版本变化很大，博客里的写法往往对应旧版本。所有核心包使用精确版本，安装用 pnpm add --save-exact，实际版本回填 版本锁定表。
  3. 不要一上来就装七个 lab。 按产品推进，跑通一个再下一个。一次性装完再集中排错，会把版本问题、网络问题、配置问题混在一起，定位成本成倍增加。
  4. 不要把 labs/ 放进文档站的扫描范围。 VitePress 的 srcExclude 已排除 labs/**、scripts/** 和根 README.md；如果你自己改配置，记得保留这三项，否则 lab README 的相对链接触发构建失败。
  5. 不要手写锚点 slug。 中文标题生成锚点时会做小写、去标点、重复标题加序号等处理。优先链接到页面，需要锚点时用 ./xx.md#标题 并跑 check-links.mjs 验证。
  6. 不要伪造「已跑通」。 本教程所有结论都应该能用命令或截图复现。装不上就说装不上，构建失败就贴报错；把失败步骤标成完成，比不会更糟。

小结与自测 ​

本章的核心不是记住五个产品的功能，而是建立「形态 → 产物 → 代价」的判断链：

  • 低代码有五类形态：Schema 驱动、表单模型、编排引擎、页面搭建器、自由画布；
  • 选型先问四个问题：结构是否稳定、表单是否复杂、是否需要非开发者编排、是否需要像素级自由布局；
  • 产品实战卷解决「怎么用」，进阶卷解决「怎么造」；
  • 环境固定 Node 22 + pnpm 9.15.4，七个 lab 独立安装，根工程只做文档与门禁。
1. 为什么不能把七个 lab 放进同一个 pnpm workspace？

因为它们的运行时和技术栈不同：amis/Formily 要 React 18，tmagic-editor 要 Vue 3，lowcode-engine 跟随官方 demo 的 React 版本，GrapesJS 是原生 TypeScript。workspace 会把依赖提升到根 node_modules，版本冲突时只能靠 overrides 打补丁，lockfile 也会互相影响。独立工程虽然多几次安装，但边界清晰、可独立构建、CI 也不必安装全部 lab。

2. 一个「客户运营后台」，页面以列表和表单为主，偶尔有复杂联动，应该怎么选？

先用 amis 搭页面骨架：列表、筛选、弹窗、CRUD 都能用 Schema 快速完成。把最复杂的表单（例如带异步校验和动态字段的那一块）单独用 Formily 实现，再嵌进 amis 页面。这样页面层享受配置效率，表单层保留模型能力。只有当需求真的需要非开发者长期拖拽编排时，才考虑 lowcode-engine 或 tmagic-editor；为「偶尔改一次」引入完整设计器，维护成本通常不划算。

3. 为什么教程要求先跑通最小示例，再读原理？

低代码产品的概念密度很高，纯读文档很容易把「协议」「物料」「渲染器」当成抽象名词。先跑通一个最小示例，你能看到输入（Schema/配置）与输出（页面/DOM）的真实对应关系，再回读原理时，每个概念都有落点。更重要的是，跑通过程会暴露版本、样式、入口等真实问题，这些问题才是日常使用的主要成本。
