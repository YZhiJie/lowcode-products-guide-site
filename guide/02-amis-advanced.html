第 02 章 · amis 进阶：接口一改，页面不崩 ​

前置章节：第 01 章 · amis 快速上手
所需环境：同第 01 章，继续使用 labs/amis。
难度：★★★
本章交付物：一个能消化「非标准接口」的页面、一组可复用的联动表达式、一个注册进 amis 的自定义组件。

第 01 章的接口是「配合页面」设计的：字段名刚好叫 items，响应刚好有 status，状态值刚好是四个英文枚举。真实世界不会这么配合。后端可能返回 { code, result }，列表可能叫 list，状态可能是数字 1/2/3，接口还可能在版本迭代中改字段。本章要解决的就是「接口变了，页面还能不能活」的问题。

本章你将获得 ​

读完本章，你应该能：

  1. 用 adaptor 把任意响应结构转换成 amis 约定，而不是让后端为前端改协议；
  2. 说清 env.fetcher 应该返回什么形状，以及为什么直接把业务数据当返回值会失败；
  3. 用 visibleOn、disabledOn 表达字段联动，并知道表达式的能力边界；
  4. 用 Renderer 注册一个自定义组件，让它在 Schema 里像内置组件一样使用；
  5. 判断一段逻辑应该留在 Schema、放进 adaptor，还是下沉到自定义组件。

这一章不再增加新的页面骨架，所有内容都在第 01 章的订单场景上做「协议升级」。这样你能清楚看到：同一份业务，换一种接口和展示方式，Schema 需要改哪里、不需要改哪里。

先看漫画 ​

这一话的核心冲突是「接口字段对不上」。后端把 customerName 改成了 customer_name，把 status 从字符串改成了数字，把列表从 data.items 挪到了 result.list。前端如果每个页面都写一套转换，改一次接口就要改三十个文件；如果有统一的 adaptor 层，只需要改一处。

漫画里码叔说了一句话：适配不是给后端擦屁股，是给页面装保险。 保险的价值不在于接口永远不变，而在于接口变化时，页面有一层缓冲。逐格讲解见 EP.02 漫画讲解。

从一个真实问题说起 ​

第 01 章的订单页上线两周后，后端做了三次调整：

  1. 统计接口从 { total, pending } 改成 { code: 0, data: { total, pending } }，理由是「统一响应规范」；
  2. 列表接口的 items 改名为 list，total 改名为 count，理由是「和 Java 后端的命名习惯对齐」；
  3. 状态接口不再返回字符串，而是返回数字 1/2/3/4，理由是「数据库存的是 tinyint」。

如果页面直接依赖后端字段，这三次调整每次都要改 Schema、改 fetcher、重新回归。更糟的是，不同页面可能对同一份响应做不同的转换，最后没人说得清「订单状态 2」到底代表已付款还是已发货。

正确的做法不是拒绝后端改协议，而是把「协议差异」收敛到一个明确的边界。amis 提供了两个边界：

  • api.adaptor：在 Schema 里声明「如何把这份响应变成 amis 能理解的形状」；
  • env.fetcher：在 React 层统一处理请求实现，包括鉴权、错误码、超时。

本章的 lab 故意把这两个边界都用到：fetcher 返回「HTTP 响应形状」，adaptor 负责「业务响应到 amis Payload」的转换，自定义渲染器负责「状态值到视觉表现」的转换。三层各管一件事，接口再改，只需要动其中一层。

原理拆解 ​

第一层：env.fetcher 返回的是响应，不是业务数据 ​

这是本章最容易错的地方，也是 lab 里真实踩过的坑。

env.fetcher 的签名是 (api, data, options) => Promise<响应>。这里的「响应」不是最终业务数据，而是接近 axios 响应的形状：至少包含 status（HTTP 状态码）和 data（响应体）。amis 拿到响应后，会继续做两步处理：

  1. 如果有 api.adaptor，先调用 adaptor(response.data, response, api)；
  2. 再走 responseAdaptor，把结果归一化成 { ok, status, msg, data }。

如果你在 fetcher 里直接返回业务数据，比如 { total: 6, pending: 2 }，amis 会把它当成响应对象：response.status 是 undefined，response.data 也是 undefined。于是 adaptor 收到 undefined，页面字段全部为空，但控制台不一定报错。第 02 章的 lab 最初就是这样：统计卡只显示标题，数字全是空白。

修正后的 fetcher 长这样：

ts
// 文件: labs/amis/src/chapters/02-amis-advanced/mock-api.ts（节选）
if (method === "get" && url === "/api/orders/stats") {
  return delay({
    // 模拟 axios 响应：status 是 HTTP 状态码，data 才是响应体
    status: 200,
    data: {
      total: rows.length,
      pending: rows.filter((row) => row.status === "pending").length,
      paid: rows.filter((row) => row.status === "paid").length,
      amount: rows.reduce((sum, row) => sum + row.amount, 0),
    },
  });
}

记住这条规则：fetcher 负责「HTTP 层」，adaptor 负责「业务协议层」。 两层混在一起，出问题时很难判断是请求没发出去，还是响应没解析对。

第二层：adaptor 是 Schema 里的协议转换器 ​

adaptor 是一个函数，写在 api 对象里。它接收三个参数：响应体、完整响应、请求配置；返回值必须能被 responseAdaptor 继续处理。

本章的统计接口返回裸数据，所以 adaptor 只需要补上 status 和 data 外壳：

ts
// 文件: labs/amis/src/chapters/02-amis-advanced/schema.ts（节选）
const wrapPayload = (payload: StatsPayload | { items: unknown[]; total: number }) => ({
  status: 0,
  msg: "",
  data: payload,
});

const statsApi = {
  method: "get",
  url: "/api/orders/stats",
  adaptor: wrapPayload,
};

为什么把 adaptor 写在 Schema 里，而不是 fetcher 里？因为适配规则和页面语义强相关：这个页面把 total 当作「订单总数」，另一个页面可能把同样的 total 当作「记录条数」。把规则放在页面配置里，页面能自己消化差异；fetcher 则可以保持通用，只负责发请求。

如果后端把 items 改成 list，adaptor 可以这样写：

ts
// 示例：把后端的 list/count 转成 amis 的 items/total
const listAdaptor = (payload: { list: unknown[]; count: number }) => ({
  status: 0,
  msg: "",
  data: { items: payload.list, total: payload.count },
});

这段代码没有出现在 lab 的运行路径里，但它是本章最重要的迁移技巧：接口改名时，改 adaptor，不改表格列。

第三层：表达式负责「局部联动」 ​

amis 的表达式写在 Schema 字符串里，用 ${...} 包裹。本章用了三类：

  • visibleOn: "${status === 'pending'}"：只有待处理状态才显示备注；
  • disabledOn: "${status === 'closed'}"：已关闭订单不允许改优先级；
  • disabledOn: "${amount <= 0}"：金额不大于 0 时禁用提交按钮。

表达式的求值依赖当前数据域。表单里的字段值变化时，amis 会重新计算依赖这些字段的表达式，从而控制显隐与禁用。你不需要写 onChange，也不需要在 React 里保存表单状态。

但表达式有明确的边界：

  • 不要做异步操作。表达式是同步求值，写 await 或请求会直接失效；
  • 不要做复杂计算。超过三行的逻辑放进自定义组件或独立函数；
  • 不要依赖外部闭包。表达式只能访问当前数据域里的字段和少量内置函数，访问 window 上的变量在 SSR 或隔离环境里会失败。

本章的联动都很轻：状态决定哪个字段出现，金额决定按钮是否可用。这类逻辑用表达式最划算；省市区三级联动、异步唯一性校验，就应该交给 Formily 或自定义组件。

第四层：自定义渲染器是「有状态的展示组件」 ​

Renderer 是 amis 的注册工厂。调用 Renderer({ type: "order-status" })(组件) 之后，Schema 里写 { "type": "order-status" } 就会命中这个组件。

本章的徽章组件做了三件事：

tsx
// 文件: labs/amis/src/shared/order-status/index.tsx（节选）
function OrderStatusBadge(props: OrderStatusProps) {
  const raw = props.status ?? props.data?.status ?? "pending";
  const status = (raw in ORDER_STATUS_MAP ? raw : "pending") as OrderStatusValue;
  const config = ORDER_STATUS_MAP[status];

  return (
    <span className={`order-status order-status--${config.tone}`} data-status={status}>
      {config.label}
    </span>
  );
}

Renderer({
  type: "order-status",
  name: "order-status",
  autoVar: true,
})(OrderStatusBadge as any);

三个设计点值得解释：

  • 状态兜底：props.status 可能来自 Schema 字面量，也可能来自表格行数据 props.data.status。两种场景都兼容，组件才能在表单、表格、面板里复用。
  • 白名单映射：未知状态回退到 pending，而不是渲染空字符串。生产环境里，后端加一个新状态是常事，前端至少要保证页面不崩。
  • autoVar: true：让 amis 在传入组件前先求值 ${status}。没有这个配置，组件收到的是字符串 ${status}，不是实际值。

注册必须发生在 render(schema) 之前。本章在 index.tsx 顶部 import "../../shared/order-status"，利用 ES 模块的副作用执行注册。如果注册晚于渲染，amis 会显示「未知组件」占位，而不是报错。

产品对照 ​

把本章的四个能力放到其他产品里看，会更容易理解 amis 的定位：

能力amisFormilylowcode-enginetmagic-editor
接口适配api.adaptor在 effects 或请求层处理数据源 + 请求适配数据源 + 处理器
字段联动visibleOn / disabledOn 表达式reactions，模型层驱动插件/联动配置事件 + 数据源
自定义展示Renderer 注册自定义字段组件物料 + Setter自定义组件

amis 的强项是「页面级快速组合」，弱项是「逻辑复用与测试」。同一段联动，在 amis 里是一串表达式，在 Formily 里是一个可单测的 reaction。页面只有几处联动时，amis 更省事；联动变成核心复杂度时，Formily 更稳。

这也解释了为什么第 00 章建议「amis 搭页面骨架，Formily 实现复杂表单」。两者不是竞争关系，而是分层关系。

动手实现 ​

第一步：准备非标准接口 ​

本章的 mock 接口在 mock-api.ts。它有三个特点：

  1. 统计和列表接口返回裸数据，没有 status 外壳；
  2. 响应对象模拟 axios，带 status: 200 和 data；
  3. 所有请求都有 320ms 延迟，方便观察加载态。

列表分支如下：

ts
// 文件: labs/amis/src/chapters/02-amis-advanced/mock-api.ts（节选）
if (method === "get" && url === "/api/orders") {
  const query = readQuery(api);
  const keywords = String(query.keywords ?? "")
    .trim()
    .toLowerCase();
  const filtered = rows.filter(
    (row) =>
      !keywords ||
      row.orderNo.toLowerCase().includes(keywords) ||
      row.customer.toLowerCase().includes(keywords),
  );
  return delay({ status: 200, data: { items: filtered, total: filtered.length } });
}

这里的 data 是响应体，不是 amis 的最终 Payload。页面的 adaptor 会把它包成 { status: 0, data: { items, total } }。如果你把这段和上一章的 fetcher 对比，会发现「返回形状」完全不同：上一章直接返回 Payload，因为 CRUD 的 api 没有写 adaptor；本章返回响应对象，因为 Schema 明确要求走 adaptor。

第二步：在 Schema 里写 adaptor ​

统计卡是一个 service 组件，api 使用对象写法：

ts
// 文件: labs/amis/src/chapters/02-amis-advanced/schema.ts（节选）
{
  type: "service",
  api: {
    method: "get",
    url: "/api/orders/stats",
    adaptor: wrapPayload,
  },
  body: {
    type: "tpl",
    tpl:
      "<div style='display:flex;gap:28px;flex-wrap:wrap'>" +
      "<span>订单总数：<b>${total}</b></span>" +
      "<span>待处理：<b>${pending}</b></span>" +
      "<span>已付款：<b>${paid}</b></span>" +
      "<span>订单金额合计：<b>¥${amount}</b></span>" +
      "</div>",
  },
}

service 负责「先请求、再渲染 body」，它的数据域就是 adaptor 返回的 data。所以 tpl 里能直接写 ${total}，不需要加 data. 前缀。这是 amis 数据域的一个便利，也是容易混淆的地方：不同渲染器的数据域层级不同，写表达式前先确认当前节点拿到的是哪一层数据。

第三步：表单联动 ​

表单的完整结构在 schema.ts 的 orderForm。关键片段如下：

ts
// 文件: labs/amis/src/chapters/02-amis-advanced/schema.ts（节选）
{ type: "select", name: "status", label: "状态", value: "pending", options: statusOptions },
{
  type: "textarea",
  name: "remark",
  label: "待处理备注",
  visibleOn: "${status === 'pending'}",
},
{
  type: "input-text",
  name: "expressCompany",
  label: "物流单号",
  visibleOn: "${status === 'shipped'}",
  required: true,
},
{
  type: "textarea",
  name: "closeReason",
  label: "关闭原因",
  visibleOn: "${status === 'closed'}",
  required: true,
},
{
  type: "select",
  name: "priority",
  label: "优先级",
  disabledOn: "${status === 'closed'}",
},
{
  type: "button",
  label: "提交订单",
  actionType: "submit",
  disabledOn: "${amount <= 0}",
},

切换状态下，备注、物流单号、关闭原因会互斥出现；选择已关闭时，优先级不可改；金额为 0 时提交按钮禁用。三组联动没有一行 React 代码，全部由 Schema 表达式完成。

注意 required: true 与 visibleOn 的组合：字段隐藏时，amis 不会把它当作「未填的必填项」，所以不会阻止提交。这正是我们要的行为：只有发货状态才要求物流单号。

第四步：注册自定义组件 ​

shared/order-status/index.tsx 里的注册代码只有几行，但它是本章的核心扩展点：

tsx
// 文件: labs/amis/src/shared/order-status/index.tsx（节选）
export const ORDER_STATUS_MAP = {
  pending: { label: "待处理", tone: "pending" },
  paid: { label: "已付款", tone: "paid" },
  shipped: { label: "已发货", tone: "shipped" },
  closed: { label: "已关闭", tone: "closed" },
} as const;

Renderer({ type: "order-status", name: "order-status", autoVar: true })(OrderStatusBadge as any);

然后在表格列里直接使用：

ts
// 文件: labs/amis/src/chapters/02-amis-advanced/schema.ts（节选）
{
  type: "order-status",
  name: "status",
  label: "状态",
  width: 110,
}

amis 会把当前行的 data 传给组件，组件从 props.data.status 读到状态值。这是自定义列的标准写法：name 用于数据映射，type 用于渲染器匹配。如果你的组件需要更多字段，可以从 props.data 里取，不需要在 Schema 里逐个声明。

第五步：验收 ​

启动 pnpm dev，切到第 02 章，依次验证：

  1. 统计卡显示 6 条订单、2 条待处理、2 条已付款、金额合计 127300；
  2. 表单里把状态切到「已发货」，物流单号出现，备注消失；切到「已关闭」，关闭原因出现，优先级变灰；
  3. 金额填 0，提交按钮不可点；
  4. 切到「数据源与自定义组件」页签，表格状态列显示彩色徽章，下面三个静态徽章也正常。

四步都通过，说明 fetcher、adaptor、表达式、自定义渲染器四条链路都通了。

跑不起来？ ​

报错一：统计卡只有标题，数字全空 ​

现象：页面能渲染，${total} 等表达式没有输出。

原因：env.fetcher 直接返回了业务数据，而不是 { status, data } 响应对象。amis 取 response.data 得到 undefined，adaptor 也跟着拿到 undefined。

修复：按本章示例，把 fetcher 的返回值改成 { status: 200, data: 业务数据 }。如果你用的是 axios，它本身就会返回这个形状，直接用即可。

报错二：写了 adaptor 但完全不生效 ​

现象：接口返回的数据正确，页面还是空。

原因：api 写成了字符串 "get:/api/orders/stats"，字符串形式没有地方挂 adaptor；或者 adaptor 写在了 page 层级，而不是 api 对象里。

修复：改成对象写法 { method: "get", url: "...", adaptor: fn }。确认 adaptor 是 api 的直接属性，不是同级的兄弟字段。

报错三：自定义组件显示为「未知组件」 ​

现象：表格状态列出现一块灰色占位，控制台提示渲染器不存在。

原因：注册代码没有执行，或者执行晚于 render(schema)。

修复：确认页面文件顶部有 import "../../shared/order-status"，且导入发生在 render 调用之前。如果用了代码分割，确保注册模块在渲染前被 await import()。

报错四：徽章状态永远是「待处理」 ​

现象：表格每一行都显示同一个状态。

原因：组件只读了 props.status，没有读 props.data.status；或者注册时漏了 autoVar: true，${status} 没有被求值。

修复：按本章组件写法，先读 props.status，再回退到 props.data.status；检查 Renderer 配置里是否有 autoVar: true。

报错五：表达式报语法错误 ​

现象：控制台出现公式解析错误，字段显隐不生效。

原因：表达式里用了 amis 公式不支持的语法，例如可选链、模板字符串嵌套、箭头函数。

修复：把表达式收敛到「字段比较、布尔运算、简单四则运算」范围内。需要复杂逻辑时，改用 static 组件加自定义函数，或下沉到自定义渲染器。

避坑清单 ​

  1. 先分清「响应」和「Payload」。 fetcher 返回响应，adaptor 返回 Payload。两层混用，页面会以「空白但不报错」的方式失败。
  2. adaptor 只做协议转换，不做业务计算。 把金额单位从分转元可以，把订单状态机跑一遍不可以。后者属于业务层，应该独立测试。
  3. 表达式里不要写异步。 显隐、禁用是同步求值；异步校验请用表单的校验接口或自定义组件。
  4. 自定义组件要做未知值兜底。 后端新增枚举值时，组件至少不能崩；回退到默认状态比白屏好。
  5. 注册要早于渲染。 把注册放在模块顶层，并在页面入口显式 import，不要依赖「碰巧先加载」。
  6. 不要把所有差异都塞进一个 adaptor。 如果适配逻辑超过二十行，说明接口和页面语义已经偏离，应该拉后端一起对齐契约，而不是在前端堆转换。

小结与自测 ​

本章把 amis 的「协议层」拆成了三段：

  • fetcher：负责 HTTP，返回 { status, data } 形状的响应；
  • adaptor：负责业务协议，把任意响应体转成 { status: 0, msg, data }；
  • Renderer：负责展示协议，把状态值转成视觉组件。

三段各司其职，接口变化时只需要改对应的一段。表达式则负责页面内的局部联动，适合显隐、禁用、简单文案，不适合复杂业务逻辑。

1. 为什么 fetcher 不能直接返回 `{ total: 6 }`？

因为 amis 把 fetcher 的返回值当作 HTTP 响应对象，会去读 response.status 和 response.data。直接返回业务数据时，response.data 是 undefined，后续 adaptor 和 responseAdaptor 都拿不到内容，页面字段为空但不一定报错。正确做法是返回 { status: 200, data: { total: 6 } }，让 adaptor 去处理业务协议。

2. adaptor 应该放在 Schema 里还是 fetcher 里？

看适配规则和谁相关。如果规则是「这个页面如何理解这份响应」，放在 Schema 的 api.adaptor 里，页面能自治；如果规则是全局的（例如所有接口都要把 code 转成 status），放在统一的 fetcher 或请求封装里，避免每个页面重复写。两者可以并存，但职责要分清。

3. 什么时候应该把表达式换成自定义组件？

当逻辑需要异步、需要访问外部状态、需要单测、或者超过三行时，就应该换。表达式适合「一个字段的值决定另一个字段显隐/禁用」这种局部规则；一旦涉及多字段计算、请求校验、跨表单联动，表达式的可读性和可测试性都会迅速下降。
