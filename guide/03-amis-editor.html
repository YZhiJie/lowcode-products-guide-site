第 03 章 · amis 编辑器：拖拽编辑器不是玩具 ​

前置章节：第 02 章 · amis 进阶
所需环境：同第 01 章，继续使用 labs/amis；新增 amis-editor 6.13.0 与 monaco-editor 0.30.1。
难度：★★★☆
本章交付物：一个嵌入 amis-editor 的页面，支持拖拽物料、编辑属性、保存/读取/导出/预览 Schema，并注册一个自定义物料。

前两章都在手写 JSON。对研发来说，这已经足够快；但对运营、产品、实施同学来说，JSON 仍然是门槛。amis-editor 要解决的就是这个门槛：把 Schema 的编写过程变成拖拽和表单配置。它不是另一个运行时，而是「Schema 的生产工具」。理解这一点，你才不会把编辑器和引擎混为一谈。

本章你将获得 ​

读完本章，你应该能：

  1. 说清 amis-editor 的三栏结构、物料来源与 Schema 流向；
  2. 把编辑器嵌进 React 页面，并处理它依赖的 Monaco worker、样式与高度；
  3. 把第 02 章的自定义渲染器注册成编辑器物料，让它出现在物料面板并可配置；
  4. 实现 Schema 的本地保存、读取、重置、导出与预览；
  5. 判断「用 amis-editor 够不够」，以及什么时候需要 lowcode-engine 这类更重的平台。

本章的代码集中在 labs/amis/src/chapters/03-amis-editor。编辑器本身很重，构建产物会明显变大，这是引入它的真实代价之一；本章也会解释如何控制它的加载范围。

先看漫画 ​

这一话里，运营同学第一次看到编辑器，兴奋地把所有物料拖进画布，做出一个「看起来什么都有」的页面；上线后却发现字段绑定错了、接口没配、移动端布局塌了。码叔的结论是：编辑器降低的是「生成 Schema 的门槛」，不是「理解业务」的门槛。

漫画还讲了一个关键动作：保存 Schema。拖拽出来的页面如果不落盘、不版本化，就只是一次性的演示。真正可复用的资产是那份 JSON，而不是编辑器截图。逐格讲解见 EP.03 漫画讲解。

从一个真实问题说起 ​

假设运营团队每个月要做 5 个活动页，每个页面包含标题、倒计时、商品列表、报名表单和按钮。过去的流程是：运营提需求 → 前端排期 → 前端写页面 → 运营验收 → 改文案再来一轮。一个页面平均改 8 次，前端一半时间花在改文案和调间距上。

引入 amis-editor 后，期望的流程是：前端提供物料与页面模板 → 运营拖拽生成 Schema → 运营在编辑器里改文案、调属性 → 预览确认 → 发布 Schema。前端从「每次改页面」变成「维护物料和模板」，运营获得有限的自主权。

这个流程能否成立，取决于四个条件：

  1. 物料是否覆盖了运营的真实需求，而不是「看起来很多」；
  2. 物料属性是否被正确建模，运营改一个属性不会把页面改坏；
  3. Schema 是否能被保存、版本化、回滚，而不是存在浏览器缓存里就丢了；
  4. 运行时是否与编辑器解耦，Schema 能在没有编辑器的页面里独立渲染。

amis-editor 能覆盖前三个条件的大部分，第四个条件需要你自己设计：编辑器负责生产 Schema，运行时只依赖 amis，不依赖编辑器。本章的 lab 就是按这个边界实现的。

原理拆解 ​

三栏结构：物料、画布、属性 ​

amis-editor 的界面可以拆成三栏：

  • 左侧物料面板：按分类列出可用组件，数据来自「已注册的渲染器 + 对应的编辑器插件」；
  • 中间画布：把当前 Schema 渲染成页面，同时提供选中、拖拽、复制、删除等操作；
  • 右侧属性面板：根据选中节点的类型，渲染对应的表单，修改后写回 Schema。

三栏共享同一份 Schema。拖拽物料时，编辑器把插件的 scaffold 插入树中；改属性时，编辑器把表单值合并到节点；选中节点时，编辑器和画布通过节点 id 同步。你看到的「拖拽」本质上是对一棵 JSON 树做插入、移动、删除。

物料 = 渲染器 + 编辑器插件 ​

一个组件要同时出现在「运行时」和「编辑器」，需要两份注册：

  • 运行时用 Renderer(...) 注册，决定 Schema 怎么渲染；
  • 编辑器用 registerEditorPlugin(...) 注册，决定物料面板怎么展示、拖入时生成什么 Schema、右侧面板能改什么。

只注册渲染器，编辑器不知道它的存在；只注册插件，预览时找不到渲染器。两者用同一个 rendererName / type 对接，这是本章自定义物料的关键。

本章的 order-status 物料包含四部分：

  • rendererName：与 Renderer 的 type 一致；
  • scaffold：拖入画布时的初始 Schema；
  • previewSchema：物料面板里的缩略预览；
  • panelControls：右侧属性面板的配置项。

这四部分合起来，才是一个「可被运营安全使用」的物料。缺了 panelControls，运营只能改源码；缺了 scaffold，拖进去是空节点；缺了 previewSchema，物料面板只有名字没有样子。

Schema 的流向：编辑器不是运行时 ​

编辑器内部有自己的状态，但它的输入输出都是 Schema：

text
初始 Schema -> Editor -> onChange(新 Schema) -> 你的状态 -> 保存/导出/预览

它不会把 Schema 编译成另一种格式，也不会在运行时依赖编辑器。预览时，你完全可以把 Schema 交给第 01 章的 render 函数，用同一个 amis 渲染器渲染。这个设计带来的好处是：编辑器可以只在「搭建页面」时加载，C 端或运营端只加载运行时，包体积和权限都能分开。

本章的 lab 把编辑器和预览放在同一个页面，是为了方便对比；真实项目里通常会把编辑器做成独立的管理端路由，运行时做成另一个入口。

持久化：Schema 是资产，缓存不是 ​

本章用 localStorage 保存 Schema，目的是让「保存后刷新仍然存在」可被直接验证。它不是生产方案，原因有三：

  • 缓存只存在当前浏览器，换设备就丢；
  • 没有版本历史，改坏了无法回滚；
  • 没有权限控制，任何人都能改。

生产环境至少需要：服务端存储、版本号、发布状态、回滚入口。再进一步，还需要 Schema 校验、灰度发布、按环境区分。本章不实现这些，但你要知道边界在哪里：编辑器只负责生产，资产治理是另一套系统。

产品对照 ​

amis-editor 与另外几个「带编辑器」的产品，定位差异很大：

维度amis-editorlowcode-enginetmagic-editorGrapesJS
编辑器定位Schema 生产工具平台底座页面搭建器自由画布
物料体系渲染器 + 插件物料协议 + Setter + 资产包组件 + 属性配置器Block + Trait
Schema 粒度页面 JSON节点树 + 物料协议页面 SchemaHTML/CSS
扩展成本低到中高中中
适合谁前端给运营做工具平台团队做产品运营/内容团队视觉/静态页团队

如果你的需求是「给运营一个能改文案、换组件、调属性的页面工具」，amis-editor 的投入产出比最高：物料就是 React 组件加一个插件类，不需要设计物料协议、资产包、出码。如果你的需求是「做一个可被其他团队接入的低代码平台」，amis-editor 就不够了，你需要 lowcode-engine 那套物料协议、插件体系与出码链路。

不要因为 amis-editor 「看起来简单」就低估它，也不要因为它「不够平台化」就否定它。选型的分界线不是功能多少，而是「谁维护物料、谁承担 Schema 治理」。

动手实现 ​

第一步：安装编辑器依赖 ​

在第 01 章的工程里新增三个直接依赖：

bash
cd labs/amis
pnpm add --save-exact amis-editor@6.13.0 amis-editor-core@6.13.0 monaco-editor@0.30.1

为什么要显式安装 amis-editor-core？因为本章需要引入它的样式文件。pnpm 不会把传递依赖提升到顶层 node_modules，直接 import 一个未声明的包会解析失败。显式安装不是多余，而是把「我用到了它」写进契约。

monaco-editor 是编辑器的代码面板依赖。它的版本必须与 amis-editor 内部使用的一致，否则会出现 worker 协议不匹配。本章锁定 0.30.1，与 amis-editor 6.13.0 的依赖树对齐。

第二步：处理 Monaco worker ​

amis-editor 的「代码」面板使用 Monaco。Monaco 默认会去请求 pkg/editor.worker.js，但 Vite 不会自动复制这个文件。结果是：编辑器能打开，控制台却报 Unexpected token '<'，因为请求被 SPA 回退到了 index.html。

本章的解法是用 Vite 的 ?worker&url 把 worker 打成一个自包含文件：

ts
// 文件: labs/amis/src/monaco-env.ts
import EditorWorkerUrl from "monaco-editor/esm/vs/editor/editor.worker?worker&url";

(globalThis as unknown as { MonacoEnvironment: unknown }).MonacoEnvironment = {
  getWorkerUrl: () => EditorWorkerUrl,
};

然后在入口文件里，把它排在 App 之前：

tsx
// 文件: labs/amis/src/main.tsx（节选）
import "./monaco-env";
import App from "./App";

这段代码看起来像「环境补丁」，但它解决的是真实的构建问题：Monaco 的 worker 不是普通依赖，它需要独立的打包入口。用 ?worker&url 让 Vite 负责打包与哈希，比手动复制文件可靠。

第三步：注册自定义物料 ​

物料插件在 order-status-plugin.ts。核心结构如下：

ts
// 文件: labs/amis/src/chapters/03-amis-editor/order-status-plugin.ts（节选）
import { BasePlugin, registerEditorPlugin } from "amis-editor";
import "../../shared/order-status";

export class OrderStatusPlugin extends BasePlugin {
  static scene = ["layout"];
  rendererName = "order-status";
  $schema = "/schemas/OrderStatus.json";
  name = "订单状态徽章";
  description = "把订单状态渲染成彩色标签，支持四种内置状态。";
  tags = ["展示", "自定义"];
  order = -100;
  icon = "fa fa-tag";

  scaffold = { type: "order-status", status: "pending" };
  previewSchema = { type: "order-status", status: "paid" };

  panelControls = [
    {
      type: "select",
      name: "status",
      label: "状态",
      options: [
        { label: "待处理", value: "pending" },
        { label: "已付款", value: "paid" },
        { label: "已发货", value: "shipped" },
        { label: "已关闭", value: "closed" },
      ],
    },
  ];
}

registerEditorPlugin(OrderStatusPlugin);

逐项解释：

  • rendererName 必须与第 02 章 Renderer({ type: "order-status" }) 完全一致。不一致时，编辑器能在物料面板展示，但拖进画布会渲染成未知组件。
  • scaffold 是拖入画布时的初始 Schema。这里给 status: "pending"，运营拖进来就能看到一个可见的徽章，而不是空白。
  • previewSchema 是物料面板的缩略图。用 paid 而不是 pending，是为了让预览和默认值有区分，运营能看出它是一个可变属性。
  • panelControls 是右侧属性面板的 Schema。它本身就是一棵 amis 表单树，所以可以直接用 select、input-text、switch 这些内置组件。改属性时，编辑器把值合并回节点 Schema。
  • scene 决定物料出现在哪个场景。layout 表示布局类；不同场景的物料面板分类不同，写错会出现「注册了但找不到」。

第四步：把编辑器嵌进页面 ​

页面状态只有一个 Schema、一个模式和一个提示：

tsx
// 文件: labs/amis/src/chapters/03-amis-editor/index.tsx（节选）
const [schema, setSchema] = useState<any>(() => readStoredSchema() ?? starterSchema);
const [mode, setMode] = useState<"edit" | "preview">("edit");
const [message, setMessage] = useState("已载入初始 Schema");

const preview = useMemo(() => {
  if (mode !== "preview") return null;
  return render(schema, {}, previewEnv as any);
}, [mode, schema]);

return mode === "edit" ? (
  <div className="editor-host">
    <Editor
      value={schema}
      onChange={(next) => {
        setSchema(next);
        setDirty(true);
      }}
    />
  </div>
) : (
  <div className="editor-preview">{preview}</div>
);

三个设计点：

  • 编辑与预览互斥挂载：编辑器和预览同时挂载会争抢 DOM 与数据域，也浪费性能。用 mode 二选一，切换时彻底卸载另一个。
  • onChange 是唯一写入口：编辑器内部状态变化都会通过 onChange 抛出完整 Schema。你不要去改编辑器内部状态，只维护自己的 schema。
  • 初始值优先读缓存：readStoredSchema() ?? starterSchema 让「保存后刷新」可验证；解析失败时 readStoredSchema 会清掉坏数据并返回 null，避免页面每次启动都报错。

编辑器容器必须有明确高度。.editor-host 设置为 720px，因为编辑器内部用绝对定位布局，高度为 0 时画布会消失。这不是样式细节，而是必须满足的宿主条件。

第五步：保存、读取、导出、预览 ​

保存与读取都围绕 localStorage：

ts
// 文件: labs/amis/src/chapters/03-amis-editor/index.tsx（节选）
const handleSave = useCallback(() => {
  window.localStorage.setItem(STORAGE_KEY, JSON.stringify(schema));
  setDirty(false);
  setMessage(`已保存，Schema 大小 ${JSON.stringify(schema).length} 字符`);
}, [schema]);

const handleLoad = useCallback(() => {
  const stored = readStoredSchema();
  if (!stored) {
    setMessage("本地没有已保存的 Schema，请先点击保存");
    return;
  }
  setSchema(stored);
  setDirty(false);
  setMessage("已从 localStorage 恢复");
}, []);

导出使用 Blob 与临时下载链接：

ts
// 文件: labs/amis/src/chapters/03-amis-editor/index.tsx（节选）
const blob = new Blob([JSON.stringify(schema, null, 2)], { type: "application/json" });
const url = URL.createObjectURL(blob);
const link = document.createElement("a");
link.href = url;
link.download = "amis-page-schema.json";
link.click();
URL.revokeObjectURL(url);

导出的是纯 Schema，不含编辑器状态、不含 React 代码。这份 JSON 可以直接交给第 01 章的 render，也可以存进服务端，作为页面版本的资产。预览按钮则用同一个 render 函数验证 Schema 能否独立运行，避免「编辑器里好看、运行时崩」。

第六步：验收 ​

启动 pnpm dev，切到第 03 章：

  1. 左侧物料面板能找到「订单状态徽章」，拖进画布后显示徽章；
  2. 右侧属性面板切换状态，画布徽章同步变化；
  3. 点「保存到本地」，刷新页面，Schema 仍然是修改后的版本；
  4. 点「导出 JSON」，得到 amis-page-schema.json；
  5. 点「预览页面」，页面用运行时渲染，不出现编辑器三栏。

五步都通过，说明物料注册、Schema 读写、运行时分叉都成立。

跑不起来？ ​

报错一：编辑器区域高度为 0 或画布消失 ​

现象：页面只有工具栏，编辑器不显示或只显示一条线。

原因：宿主容器没有显式高度。amis-editor 内部使用绝对定位与 height: 100%，父容器高度为 auto 时会塌陷。

修复：给容器设置固定高度或可计算高度，例如 height: 720px 或 height: calc(100vh - 180px)。同时确认容器没有 overflow: hidden 把画布裁掉。

报错二：控制台 Unexpected token '<'，指向 pkg/editor.worker.js ​

现象：编辑器能打开，但代码面板报语法错误。

原因：Monaco worker 没有被构建器打包，请求被 SPA 回退到 HTML。

修复：按本章的 monaco-env.ts，用 ?worker&url 引入 worker，并在 App 之前设置 MonacoEnvironment.getWorkerUrl。不要手动把 node_modules 里的 worker 复制到 public，那个文件是 ESM 源码，缺少依赖解析。

报错三：自定义物料不出现在左侧面板 ​

现象：运行时能看到徽章，编辑器里找不到。

原因：只注册了 Renderer，没有注册 EditorPlugin；或者插件的 rendererName 与渲染器的 type 不一致；或者 registerEditorPlugin 没有执行。

修复：确认插件文件被页面 import；检查 rendererName === "order-status"；在控制台确认注册函数确实执行。必要时在插件文件顶层加一行日志，排除「模块没加载」的可能。

报错四：拖入物料后显示「未知组件」 ​

现象：物料面板有名字，拖进画布却是错误占位。

原因：编辑器进程和运行时进程加载了不同的渲染器注册表，或者预览环境的 amis 实例没有执行第 02 章的注册代码。

修复：确保插件文件顶部 import "../../shared/order-status"，并且预览使用的 render 来自同一个 amis 包实例。monorepo 里出现两份 amis 时，注册表会分裂，这是常见坑。

报错五：刷新后 Schema 回到初始值 ​

现象：保存成功，刷新却恢复默认。

原因：保存时用了错误的键名，或者读取发生在 localStorage 写入之前；也可能是浏览器隐私模式禁用了存储。

修复：确认保存与读取使用同一个 STORAGE_KEY；在控制台执行 localStorage.getItem("lab-amis-editor-schema") 验证是否真的写入；隐私模式下要给出提示，而不是静默失败。

报错六：构建产物过大 ​

现象：pnpm build 后出现多个 1MB 以上的 chunk，构建警告不断。

原因：amis-editor 自带 Monaco、ECharts、富文本编辑器等重型依赖，全部打包会非常大。

修复：本章的 lab 为了完整体验没有做按需加载。真实项目应把编辑器路由做成动态 import()，让运营端才加载编辑器；运行时入口只引 amis，不引 amis-editor。同时可以用 build.rollupOptions.output.manualChunks 拆分 vendor，但不要为了消除警告而过度拆包。

避坑清单 ​

  1. 编辑器不是运行时。 不要把编辑器依赖带进 C 端或运营端页面；Schema 才是交付物，编辑器只是生产工具。
  2. 物料必须有 scaffold 与 panelControls。 只注册渲染器，运营拖进去是空节点；没有属性面板，运营只能改源码，等于没有低代码。
  3. 宿主容器必须给高度。 这是 amis-editor 最常见的「页面空白」原因，不是 bug。
  4. Monaco worker 要单独打包。 不要复制源码文件，不要依赖 CDN；用构建器的 worker 能力生成自包含文件。
  5. localStorage 只用于演示。 生产环境需要服务端存储、版本历史、权限与回滚，否则 Schema 迟早会丢。
  6. 控制包体积。 编辑器与运行时分离，按路由动态加载；物料按需注册，不要把整个组件库塞进首屏。
  7. Schema 要做校验。 编辑器产出的 JSON 可能包含未知字段或非法结构，发布前应跑一次 Schema 校验，避免运行时白屏。

小结与自测 ​

本章把「低代码编辑器」拆成了三层：

  • 物料层：渲染器 + 编辑器插件，决定「能拖什么、拖出来是什么、能改什么」；
  • 编辑层：三栏共享一棵 Schema 树，拖拽与属性修改都是对树的编辑；
  • 资产层：Schema 的保存、导出、预览与治理，决定「拖出来的东西能不能长期用」。

amis-editor 的价值在于把 Schema 生产门槛降下来，但它不替代业务理解，也不自动解决 Schema 治理。这两件事仍然需要工程团队设计。

1. 为什么自定义物料要同时注册 Renderer 和 EditorPlugin？

因为它们服务于两个不同的进程。Renderer 决定运行时如何渲染 Schema，EditorPlugin 决定编辑器物料面板如何展示、拖入时生成什么、属性面板能改什么。只注册其中一个，要么运行时找不到组件，要么编辑器里找不到物料。两者通过相同的 type / rendererName 对接。

2. 为什么编辑器与预览要互斥挂载？

编辑器和预览都会创建 amis 数据域与 DOM 结构，同时挂载会争抢容器、重复请求、增加内存占用，还可能出现「预览改了编辑器的数据」这类难以排查的问题。用模式切换彻底卸载另一个，边界最清晰。

3. `localStorage` 保存 Schema 在生产环境缺什么？

缺服务端存储、版本历史、权限控制、发布状态与回滚能力。浏览器缓存只存在当前设备，清缓存就丢；没有版本历史，改坏无法恢复；没有权限，任何人都能改。生产环境应把 Schema 存到服务端，并配套校验、灰度与回滚流程。
