第 05 章 · Formily 联动：依赖、校验与生命周期 ​

前置章节：第 04 章 · Formily 基础
所需环境：Node 22 LTS、pnpm 9.15.4；本章沿用 Formily 2.3.7 + antd 5.29.3。
难度：★★★
本章交付物：一个带省市区三级联动、金额自动计算、客户编号异步查重、生命周期日志的表单。

上一章的表单是静态的：字段各自有值，各自校验，互不干扰。真实业务从「互不干扰」结束的地方开始。省份变了，城市的选项要跟着变，旧城市值必须清掉；数量或单价变了，合计要重算；客户编号输入完，要去后端查重；发票开关打开，抬头才出现。这些行为如果散落在组件里，就是一堆互相引用的 useEffect；Formily 把它们收进字段的依赖图，用 x-reactions 和 effects 两个入口统一表达。

本章的重点不是记住 API，而是建立两个判断：一条规则该写成函数式还是表达式式；一条联动改了选项之后，为什么还必须处理旧值。前者决定 Schema 能否序列化，后者决定表单会不会提交出「看起来合法但业务上不存在」的数据。

本章你将获得 ​

读完本章，你应该能完成四件事：

  1. 用函数式 x-reactions 实现省市区三级联动，并解释 Formily 如何知道该在什么时候重新执行；
  2. 用表达式式 x-reactions 计算合计金额，说清 dependencies 与 $deps 的对应关系；
  3. 写出一个会 loading、会失败、能显示错误的异步校验器，并知道它的竞态风险；
  4. 用 effects 挂载生命周期日志，把联动从黑盒变成可观察的行为。

本章的 lab 仍然在 labs/formily，入口是 #/05。页面右侧下方有一块日志面板，每次初始化、字段变化、提交都会留下记录。建议先跑一遍页面，再回来看代码，日志会让「谁触发了谁」变得非常直观。

先看漫画 ​

这一话里，标签君给省市区加了联动：省份一变就替换城市选项，看起来工作正常。上线后客服反馈，有客户的城市显示「杭州」，省份却是「江苏省」，提交后地址校验失败。码叔指出问题不在选项，而在旧值：选项换了，字段值还留在原地，表单就会产生一个业务上不存在的组合。

第二个冲突是异步校验。标签君把请求写进 onChange，用户每敲一个字符就发一次请求，返回顺序还不保证，最后页面显示的错误可能来自三次输入之前。漫画用「快递单」做比喻：你寄出的查询和回来的结果必须能对上号，否则越查越乱。

逐格讲解、坑点清单和三道自测题在 EP.05 漫画讲解。

从一个真实问题说起 ​

把第 04 章的订单表单交给真实业务，产品会提出四类新要求：

  • 级联选择：省份、城市、区县三级联动，切换上级必须清空下级，不能留下非法组合；
  • 自动计算：数量乘单价得到合计，合计只读，但必须参与提交与校验；
  • 异步查重：客户编号输入完成后调用后端接口，已占用则阻止提交；
  • 条件显示：只有打开「需要开票」时才显示发票抬头，关闭时不应该提交一个隐藏的抬头值。

这四类需求的共同点是：它们都不是「某个字段自己的事」，而是字段之间的关系。用传统受控组件写，每一类都要在父组件里维护状态、在回调里判断、在提交前再清洗一遍。规则越多，父组件越像一个手写的调度中心，测试也只能通过整体渲染来验证。

Formily 把这些关系拆成两种表达：reactions 负责「字段之间的即时影响」，effects 负责「表单生命周期上的横切逻辑」。前者写在 Schema 里，跟着字段走；后者写在 createForm 的配置里，跟着表单走。两者都不需要修改组件树，这让规则可以被单独测试，也可以被配置化系统读取。

原理拆解 ​

reactions 的本质是依赖追踪 ​

x-reactions 不是事件监听，而是依赖追踪。你在 reactions 函数里读过的字段，会被 Formily 记录下来；这些字段变化时，函数重新执行。这和第 04 章说的「字段树」是同一套模型：字段不是孤立的输入框，而是依赖图上的节点。

函数式写法长这样：

ts
"x-reactions": (field) => {
  // 读取 province：这一步同时建立了依赖关系
  const province = field.query("province").value();
  const cities = REGIONS[province]?.cities ?? [];
  field.dataSource = cities.map((city) => ({ label: city.label, value: city.label }));
  // 选项变了，旧值可能不再合法，必须主动清理
  if (field.value && !cities.some((city) => city.label === field.value)) {
    field.value = undefined;
  }
}

field.query("province") 不只是取值，它把 province 注册成当前字段的依赖。field.dataSource 是 Select 的数据源，修改它会触发控件重渲染。最后那段清理是本章最重要的细节：替换选项不等于校验旧值，如果不主动清空，表单会保留一个不在选项里的值，提交时后端才报错。

表达式式写法长这样：

ts
"x-reactions": {
  dependencies: ["quantity", "unitPrice"],
  fulfill: {
    state: {
      value: "{{ ($deps[0] || 0) * ($deps[1] || 0) }}",
    },
  },
}

它没有函数，只有依赖数组和一段表达式字符串。$deps[0] 对应 quantity，$deps[1] 对应 unitPrice，顺序就是 dependencies 的顺序。这种写法可以被 JSON 序列化，因此能存进数据库、能做版本 diff、能被非开发者修改。代价是表达能力有限：它适合「算一个值」「切一个可见性」，不适合「读三个字段、调接口、改数据源」这类有副作用的逻辑。

函数式与表达式式的选择标准 ​

可以用三个问题判断：

  1. 这段逻辑需要写多个字段或调用外部函数吗？是，选函数式。
  2. 这段逻辑只根据依赖字段算出一个值或一个布尔状态吗？是，优先表达式式。
  3. 这份 Schema 需要存库、跨端、给配置平台编辑吗？是，尽量表达式式；必须用函数时，把函数抽成具名组件或后端可识别的规则。

本章的省市区用函数式，因为要改 dataSource、要清空旧值；合计金额用表达式式，因为它只是一次乘法；发票抬头用表达式式，因为它只是一个可见性判断。三种场景对应三种复杂度，读者不需要为了统一而把所有逻辑都写成函数。

可见性与取值是两件事 ​

visible 控制的是显示，不是取值。一个字段被隐藏后，它的值仍然留在 form.values 里，仍然会被提交。这是一条很容易被忽略的规则，也是「关掉发票开关却提交了发票抬头」的根因。

如果业务要求「隐藏即清空」，需要在 reactions 里显式处理：

ts
"x-reactions": {
  dependencies: ["invoice"],
  fulfill: { state: { visible: "{{$deps[0] === true}}" } },
  otherwise: { state: { value: null } },
}

fulfill 是依赖条件成立时的分支，otherwise 是不成立时的分支。把清空写在 otherwise 里，才能保证关闭开关时值真的被移除。第 05 章的 lab 只演示了显示，正文把清空写法列出来，是因为真实项目几乎一定会遇到这个需求。

异步校验的契约与竞态 ​

Formily 的 x-validator 接受函数，函数返回字符串表示错误，返回空字符串表示通过，返回 Promise 则进入异步校验。异步期间字段会进入 validating 状态，FormItem 可以显示 loading。

ts
"x-validator": async (value: string) => {
  if (!value) return "客户编号不能为空";
  if (value.length < 8) return "客户编号至少 8 位";
  const used = await checkCustomerCode(value);
  return used ? "该客户编号已被占用" : "";
}

这段代码能工作，但它有一个真实项目必须处理的问题：竞态。用户输入 C-2025-001 触发第一次请求，紧接着改成 C-2025-002 触发第二次请求；如果第一次请求比第二次晚返回，页面会显示一个过期的错误。Formily 会为每次校验维护状态，但网络层不会自动帮你取消旧请求。生产环境通常有三种处理：给输入加防抖、在 validator 里用 AbortController 取消旧请求、或者在后端返回时带上请求序号并在前端丢弃过期结果。本章的 mock 只有 600ms 延迟，读者可以手动快速修改输入来观察这个现象。

effects 是表单级横切逻辑 ​

reactions 跟着字段走，effects 跟着表单走。它们在 createForm 的配置里注册，常用的钩子有：

  • onFormInit：表单实例初始化完成；
  • onFieldValueChange：某个字段的值变化；
  • onFormSubmit：校验通过、提交发生时；
  • onFormSubmitFailed：提交校验失败时。
ts
const form = useMemo(
  () =>
    createForm({
      effects() {
        onFormInit(() => push("onFormInit：表单实例创建完成"));
        onFieldValueChange("province", (field) => push(`province 变为 ${field.value}`));
        onFormSubmit((form) => push(`提交通过，共 ${Object.keys(form.values).length} 个字段`));
      },
    }),
  [push],
);

effects 适合放埋点、草稿保存、权限校验、跨字段审计这类「不属于某个字段」的逻辑。它不适合放 UI 状态，因为 UI 状态应该由组件自己管理。把 effects 和 reactions 分开，form 的职责才清晰：reactions 维护字段之间的关系，effects 维护表单与外部世界的关系。

amis 的表达式更适合「根据数据决定显示什么」，Formily 的 reactions 更适合「根据字段决定字段怎么变」，lowcode-engine 的事件系统适合「节点之间的编排」。三者不是替代关系，而是抽象层级不同。你在一个平台里同时用三种能力也不奇怪，关键是不要让同一类规则散落在三个地方。

动手实现 ​

本章 lab 的代码分布在四个文件：region-data.ts 放静态省市区，mock-api.ts 放查重接口，schema.ts 放字段与规则，index.tsx 放表单装配与日志。先看联动的数据源：

ts
// 文件: labs/formily/src/chapters/05-formily-linkage/region-data.ts
export const REGIONS = {
  zhejiang: {
    label: "浙江省",
    cities: [
      { label: "杭州", districts: ["西湖区", "滨江区", "余杭区"] },
      { label: "宁波", districts: ["海曙区", "鄞州区"] },
    ],
  },
  // ...江苏省、广东省
};

数据结构是「省份 → 城市数组 → 区县数组」。真实项目里这份数据来自接口，放本地是为了让联动逻辑不被网络状态干扰。注意城市和区县直接用中文名做 value，是为了让日志和截图可读；生产环境通常用行政区划编码，读者替换时只需要改 value 字段。

城市字段的 reactions 在上一节已经展示，这里补充区县字段，它同时依赖省份和城市：

ts
"x-reactions": (field: any) => {
  const province = field.query("province").value();
  const city = field.query("city").value();
  const districts =
    REGIONS[province]?.cities.find((item) => item.label === city)?.districts ?? [];
  field.dataSource = toOptions(districts);
  field.disabled = districts.length === 0;
  // 城市变了，区县也必须重新校验合法性
  if (field.value && !districts.includes(field.value)) {
    field.value = undefined;
  }
}

这段代码的关键不是 dataSource 赋值，而是两次清理的级联：省份变化清空城市，城市变化清空区县。Formily 的依赖追踪会自动按顺序执行，不需要手写「先清城市再清区县」的调度。这也是模型驱动相比手写 useEffect 最实在的收益。

合计金额是表达式式 reactions 的最小案例。它的字段本身是只读控件，值由依赖计算：

ts
total: {
  type: "number",
  title: "合计金额（元）",
  "x-decorator": "FormItem",
  "x-component": "NumberPicker",
  "x-component-props": { disabled: true },
  "x-reactions": {
    dependencies: ["quantity", "unitPrice"],
    fulfill: {
      state: { value: "{{ ($deps[0] || 0) * ($deps[1] || 0) }}" },
    },
  },
}

这里有一个容易忽略的点：total 仍然是表单字段，仍然会出现在 form.values 里。它不是「界面上的一个计算结果」，而是模型里的一个值。这意味着提交时后端能直接拿到合计，不需要在提交函数里再算一遍；也意味着如果后端对合计有精度要求，应该在这里统一处理，而不是在多个页面各写一份。

异步查重放在 mock-api.ts：

ts
const USED_CODES = new Set(["C-2025-001", "C-2025-002", "C-2024-099"]);

export async function checkCustomerCode(code: string) {
  await delay(600); // 让 loading 与错误态可见
  return USED_CODES.has(code.trim().toUpperCase());
}

Schema 里的 validator 先做本地规则，再做远程规则。本地规则负责「空值」和「长度」，远程规则负责「是否占用」。这种分层能减少无效请求：用户还没输完，就不应该发请求。生产环境还可以在本地规则里加防抖，或者把远程校验改成失焦触发。

index.tsx 的 effects 负责把生命周期写成日志。日志用 useRef 保存完整数组，再同步到 state，避免 effects 闭包拿到过期数据：

tsx
const push = useCallback((line: string) => {
  const time = new Date().toLocaleTimeString("zh-CN", { hour12: false });
  logsRef.current = [...logsRef.current, `[${time}] ${line}`].slice(-8);
  setLogs(logsRef.current);
}, []);

只保留最近 8 条是有意为之：日志面板是观察工具，不是审计系统。真实项目要审计，应该把事件发给后端，而不是堆在页面上。

验证顺序建议这样：先把数量改成 2，确认合计变 2400；再把客户编号改成 C-2025-001，等 600ms 看错误出现；然后切换省份到江苏省，确认城市被清空、日志出现两条记录；最后打开「需要开票」，确认抬头出现，再关闭，观察值是否还在。最后一步正好对应上一节说的「可见性不等于取值」。

跑不起来？ ​

现象一：切换省份后城市选项没变。 先确认 reactions 函数里确实通过 field.query("province").value() 读取了省份，而不是直接读 field.form.values.province。后者不一定能建立精确依赖，且容易读到旧值。其次确认 field.dataSource 赋值的是数组，不是对象或 Promise。

现象二：城市下拉是空的。 antd Select 的选项来自 field.dataSource，数据项必须是 { label, value }。如果传了字符串数组，控件不会报错，但选项显示为空。本章用 toOptions 统一转换，就是为了避免这个低级错误。

现象三：合计不更新。 检查 dependencies 的字段名是否与 Schema 的 key 完全一致，以及表达式里是否用了 $deps 的正确下标。dependencies: ["quantity", "unitPrice"] 对应 $deps[0]、$deps[1]，顺序错了不会报错，只会算错。

现象四：异步校验不显示错误。 validator 必须返回字符串或 Promise<string>。如果返回 false、undefined 或抛异常，Formily 不会把它当成业务错误展示。调试时先在 validator 里 console.log 返回值，确认契约正确。

现象五：日志出现重复记录。 开发态 StrictMode 会让 effects 执行两次。本章 lab 没有启用 StrictMode；如果你在自己的工程里启用了，需要接受这一点，或者把日志改成幂等。

避坑清单 ​

  1. 联动换了选项，必须检查旧值。 只改 dataSource 不改 value，会留下业务上不存在的组合。这是本章最值得记住的一条。
  2. visible 不负责清空。 隐藏字段仍然参与提交；需要隐藏即清空时，在 otherwise 里显式置空。
  3. 异步校验要处理竞态。 防抖、取消请求、丢弃过期结果，至少做一种；否则快速输入时会显示旧错误。
  4. 表达式式 reactions 优先。 能序列化就序列化，这样 Schema 才能存库、做 diff、被配置平台编辑。函数式是逃生通道，不是默认选择。
  5. effects 里不要写 UI 状态。 它适合埋点、审计、草稿；把 loading、弹窗开关塞进去，会让表单和视图重新耦合。

小结与自测 ​

本章把联动拆成两套机制：reactions 管字段之间，effects 管表单生命周期。函数式 reactions 能读写多个字段、能改数据源，但不可序列化；表达式式 reactions 可序列化，适合计算与显隐。联动之后必须处理旧值，可见性不等于取值，异步校验必须考虑竞态。这四条比记住 API 更重要。

1. 为什么切换省份后要主动清空城市值？

因为替换 dataSource 只改变了可选项，不会自动校验或清除已经存在的值。旧城市可能不在新省份的城市列表里，如果不清空，表单会提交一个业务上不存在的「省份 + 城市」组合。主动清空是保证数据合法性的必要步骤。

2. 函数式 reactions 和表达式式 reactions 怎么选？

需要读写多个字段、修改数据源、调用外部函数时用函数式；只根据依赖字段计算一个值或一个布尔状态时用表达式式。如果 Schema 需要存库、跨端、被配置平台编辑，优先表达式式，因为函数无法被 JSON 序列化。

3. 异步校验器返回什么才算通过？

返回空字符串（或 resolve 空字符串）表示通过；返回非空字符串表示业务错误；抛异常或返回非字符串通常不会被当作可展示的业务错误。异步期间字段进入 validating 状态，FormItem 可以显示 loading。
