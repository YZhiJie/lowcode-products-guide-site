第 06 章 · Formily 进阶：自定义字段与 Schema 复用 ​

前置章节：第 05 章 · Formily 联动
所需环境：Node 22 LTS、pnpm 9.15.4；本章沿用 Formily 2.3.7 + antd 5.29.3。
难度：★★★☆
本章交付物：一个带自定义金额字段、两列栅格布局、可实时编辑 JSON 并预览的表单页面。

前两章都在 Schema 能表达的范围内工作：内置组件、内置校验、内置 reactions。真实项目一定会遇到 Schema 表达不了的部分：公司自己的金额输入框、带业务格式的只读展示、需要复用的一段字段组合、需要在运行时编辑配置的运营页面。Formily 的处理方式不是「把组件写进 Schema」，而是注册表 + 字符串名：组件实现留在代码里，Schema 里只写名字。

本章还要回答一个低代码绕不开的问题：为什么第 06 章的实时编辑器只接受纯 JSON，而不接受带函数的 Schema？答案不是技术限制，而是产品边界。一份能存库、能跨端、能做版本 diff 的 Schema，才有资格成为低代码平台的配置；一份带闭包的 Schema，本质上仍然是代码，只是换了写法。

本章你将获得 ​

读完本章，你应该能完成四件事：

  1. 用 connect + mapProps 把第三方组件接入 Formily，并说清哪些字段状态该映射、哪些不该映射；
  2. 用 FormGrid 和 gridSpan 实现两列表单布局，理解布局信息写在 Schema 里的好处；
  3. 用对象展开复用一段 Schema，知道这种复用方式的边界；
  4. 实现一个可编辑 JSON 的 Schema 预览器，理解「配置可序列化」对低代码平台的意义。

本章的 lab 入口是 #/06。页面分成上下两块：上面是完整表单，下面是实时编辑器。建议先提交一次上面的表单，确认自定义字段的值能被收集；再在下面故意写坏 JSON，观察错误提示而不是白屏。

先看漫画 ​

这一话里，标签君遇到一个「Schema 写不出来」的金额输入框，第一反应是把整个表单改回 JSX：反正只有这一页，手写更快。码叔拦住他，因为这一页改回 JSX 之后，后面所有页面都会跟着改回去，配置平台再也接不住。

第二个冲突是 Schema 复用。标签君复制粘贴了三大段字段配置，第二周电话格式要改，他改了其中两处，漏了第三处，线上出现两种校验规则。码叔的解法是把公共片段抽成对象，用展开组合，而不是复制。

最后的冲突是实时编辑器。标签君想把校验函数也放进 JSON，码叔问了一句：这份 JSON 要存进数据库吗？要给别人改吗？如果要，它就不能带函数。漫画最后用一句话收束：能序列化的配置才是配置，不能序列化的配置只是代码。

逐格讲解、坑点清单和三道自测题在 EP.06 漫画讲解。

从一个真实问题说起 ​

假设合同管理页面需要这些能力：

  • 合同金额用公司统一的金额输入框，带 ¥ 前缀、两位小数、千分位展示；
  • 金额下方有一个只读预览，用大写或格式化文案展示，方便审批人快速核对；
  • 表单字段较多，需要两列布局，备注占满整行；
  • 联系人与联系电话这两段字段，在客户页、合同页、工单页都要用，格式必须一致；
  • 运营同学希望能直接改一段 JSON，就调整表单字段，不用等研发发版。

前四条是普通的工程需求，第五条是低代码需求。它们看起来是五个独立问题，实际上都指向同一个设计决定：UI 实现和 Schema 配置要不要分离。如果金额输入框直接写进 Schema（比如把组件对象塞进 x-component），Schema 就无法序列化；如果联系字段靠复制，就无法保证一致；如果实时编辑器允许函数，就无法安全地存库和跨端。

Formily 的答案是三层分离：组件实现放在代码里，通过 createSchemaField({ components }) 注册；Schema 里只写字符串名；布局与复用信息写在 Schema 的结构里，而不是散落在 CSS 或复制粘贴中。这样，研发升级组件不会破坏历史配置，运营改 Schema 也不需要重新构建。

原理拆解 ​

connect 与 mapProps：字段状态到组件 props 的桥 ​

自定义字段不是「写一个 React 组件然后注册」这么简单。Formily 的字段有 value、onChange、disabled、errors、loading 等状态，而第三方组件通常只认识 value 和 onChange。connect 负责把组件包成 observer，mapProps 负责声明「哪些字段状态要变成 props」。

tsx
export const MoneyInput = connect(
  (props) => {
    const { value, onChange, disabled } = props;
    return (
      <InputNumber
        prefix="¥"
        precision={2}
        value={typeof value === "number" ? value : undefined}
        onChange={(next) => onChange?.(next ?? 0)}
        disabled={disabled}
      />
    );
  },
  // 只映射需要的字段状态，不把整个 field 对象透传给组件
  mapProps({ value: true, onChange: true, disabled: true }),
);

这段代码有三个边界。第一，mapProps 只取 value、onChange、disabled，第三方组件拿不到 field、form 这些内部对象，避免组件绕过模型直接改状态。第二，onChange 要把 null 转成 0，因为 antd 的 InputNumber 清空时给的是 null，而金额字段的业务语义是「没有值就是 0」。第三，connect 返回的组件已经是 observer，字段变化时只重渲染这个组件，不会带动整页。

只读展示字段用同一套机制，但不映射 onChange：

tsx
export const MoneyText = connect(
  (props) => <span>¥ {formatMoney(props.value)}</span>,
  mapProps({ value: true }),
);

它在 Schema 里仍然是一个字段，可以被 reactions 计算、被表单收集、被校验。这一点很重要：只读不等于不存在。很多团队把只读展示写成纯 UI，结果提交时拿不到这个值，只能在提交函数里再算一遍，规则又散了一处。

createSchemaField 是注册表，不是工厂 ​

createSchemaField({ components }) 返回的是一个渲染器组件。它把 Schema 里的字符串名映射到真实组件，支持点路径，例如 Input.TextArea 会从 components.Input 上取 TextArea。这意味着：

  • Schema 里永远只有字符串，没有组件引用；
  • 组件升级、替换、按环境切换，都不需要改 Schema；
  • 未注册的组件不会报错，只会静默不渲染，所以调试时要先检查注册表。

本章用 createLabSchemaField({ MoneyInput, MoneyText }) 在基础组件表上追加自定义组件，而不是修改全局注册表。这样第 04、05 章的 SchemaField 不受影响，章节之间不会互相污染。

FormGrid 与 gridSpan：布局也是配置 ​

布局有两种写法：外层写 CSS Grid，或者让 Schema 自己声明占位。Formily 的 FormGrid 提供上下文，FormItem 读取 x-decorator-props.gridSpan 决定占几列。本章的 Schema 里，备注写 gridSpan: 2，其余字段默认一列：

ts
remark: {
  type: "string",
  title: "补充说明",
  "x-decorator": "FormItem",
  "x-decorator-props": { gridSpan: 2 },
  "x-component": "Input.TextArea",
}

把布局写进 Schema 的好处是：同一份字段配置，换一个 maxColumns 就能从两列变三列，不需要改每个字段的样式；配置平台也能把「占几列」当成一个可编辑属性。坏处是它只适合规整的栅格，不适合像素级自由布局。需要自由布局时，应该回到页面搭建器或画布工具，而不是逼 Formily 做它不擅长的事。

Schema 复用：对象展开的能与不能 ​

本章的联系人片段是一个普通对象：

ts
export const contactBaseSchema = {
  type: "object",
  properties: {
    contactName: {/* ... */},
    contactPhone: {/* ... */},
  },
};

export const advancedSchema = {
  type: "object",
  properties: {
    ...contactBaseSchema.properties,
    // 合同页自己的字段
  },
};

对象展开能解决「字段级复用」，优点是零依赖、可读、可测试；边界是它只做浅合并。如果两个页面都要改同一个字段的标题，展开后就变成了两份独立配置，后续仍然可能漂移。更稳妥的做法是把公共片段抽成函数，接收覆盖参数；但函数会让 Schema 不可序列化，所以只适合代码内复用，不适合配置平台。这个取舍没有标准答案，关键是团队要知道自己选的是哪一条。

实时编辑器：配置可序列化的试金石 ​

第 06 章下半部分是一个最小的低代码闭环：左侧 textarea 编辑 JSON，右侧 SchemaField 实时渲染，下方用 observer 展示 form.values。核心逻辑只有三步：

  1. JSON.parse 文本，失败则展示错误，不渲染；
  2. 校验根节点是 type: "object"，避免把数组或字符串当 Schema；
  3. 把解析结果交给同一个 SchemaField，组件注册表不变。
tsx
function parseSchema(text: string) {
  try {
    const parsed = JSON.parse(text);
    if (!parsed || parsed.type !== "object") {
      return { schema: null, error: "根节点必须是 type: object 的 JSON Schema" };
    }
    return { schema: parsed, error: "" };
  } catch (error) {
    return { schema: null, error: `JSON 解析失败：${(error as Error).message}` };
  }
}

这段代码故意不接受函数。因为一旦允许 x-validator: () => ...，JSON 就不再是 JSON，文本无法解析，配置无法存库，跨端也无法执行。需要函数的场景应该回到第 05 章的函数式 reactions，或者把规则抽成具名组件、后端规则引擎。低代码平台的边界，往往就定在「这份配置能不能被序列化」这一条线上。

observer 与渲染范围 ​

实时值面板用 observer 包住：

tsx
const LiveValues = observer(({ form }) => <pre>{JSON.stringify(form.values, null, 2)}</pre>);

observer 会追踪组件内部读取的响应式数据。这里只读了 form.values，所以只有值变化时它才重渲染，左侧 textarea 和右侧表单不会跟着抖动。这也是 Formily 性能模型的核心：不是「整页重渲染」，而是「谁读了谁负责」。自定义组件用 connect 自动获得同样的能力，不需要额外包 observer。

产品对照 ​

Formily 的扩展成本最低，因为它只要求一个组件和一个注册名；amis 的自定义渲染器要处理 Schema 解析与数据域；lowcode-engine 的物料要同时考虑渲染、属性配置、拖拽与设计器。扩展成本低，意味着它适合「字段级差异」；一旦差异上升到「区块级编排」，就应该换工具。

动手实现 ​

本章 lab 的代码在 labs/formily/src/chapters/06-formily-advanced，三个文件：custom-fields.tsx、schema.ts、index.tsx。先看自定义字段的注册：

tsx
// 文件: labs/formily/src/chapters/06-formily-advanced/index.tsx
const SchemaField = createLabSchemaField({ MoneyInput, MoneyText });

createLabSchemaField 是第 04 章共享文件里的工厂，它在基础组件表上追加传入的组件。这里没有修改全局注册表，所以第 04、05 章仍然只有内置组件。章节隔离不是洁癖，而是可预测性：读者在某一章看到的行为，不会被另一章的扩展影响。

主表单用 FormGrid 包住 SchemaField：

tsx
<Form
  form={form}
  layout="vertical"
  onAutoSubmit={(values) => setResult(JSON.stringify(values, null, 2))}
>
  <FormGrid maxColumns={2} columnGap={20} rowGap={0}>
    <SchemaField schema={advancedSchema} />
  </FormGrid>
  <FormButtonGroup.FormItem>
    <Submit>提交合同</Submit>
  </FormButtonGroup.FormItem>
</Form>

FormGrid 通过 context 给每个 FormItem 分配列宽，gridSpan 写在 Schema 里。提交后结果面板会包含 amount、summary 这些自定义字段的值，说明它们确实进入了模型，而不是只做了展示。

实时编辑器的装配稍微多一点：

tsx
const playgroundForm = useMemo(() => createForm({}), []);
const { schema: parsedSchema, error } = useMemo(() => parseSchema(schemaText), [schemaText]);

<FormProvider form={playgroundForm}>
  {parsedSchema ? <SchemaField schema={parsedSchema} /> : null}
  <LiveValues form={playgroundForm} />
</FormProvider>;

这里用 FormProvider 而不是 Form，因为预览区不需要提交按钮和布局容器，只需要表单上下文。playgroundForm 只创建一次，Schema 变化时字段会按名称复用或销毁，值面板也随之更新。如果每次解析都新建 Form，输入到一半的预览值会全部丢失。

验证顺序建议：先提交主表单，确认结果里有 amount: 128000 与 summary: 128000；再改左侧 JSON 里的标题，确认右侧立即变化；然后把 JSON 改成 { bad json，确认出现解析错误而不是白屏；最后恢复 JSON，确认表单重新出现。这四步覆盖了自定义字段、布局、复用、容错四条链路。

跑不起来？ ​

现象一：自定义组件渲染了，但输入不生效。 检查 mapProps 是否映射了 value 和 onChange。只写 connect 不写 mapProps，组件拿不到字段值，表现就是「能看不能改」。如果只有只读展示，只映射 value 即可。

现象二：提交时拿不到自定义字段的值。 检查组件是否真的调用了 onChange。Formily 通过 onChange 收集值，如果组件内部把值存在自己的 state 里，模型不会知道。另一个常见原因是字段被写成了 void 类型，void 不参与取值。

现象三：FormProvider 报上下文错误。 实时预览区如果没有 FormProvider，SchemaField 找不到表单实例。主表单用 <Form> 自带上下文，预览区用 <FormProvider>，两者选一个，不能都没有。

现象四：gridSpan 不生效。 确认 FormGrid 确实包住了 SchemaField，并且 gridSpan 写在 x-decorator-props 里而不是 x-component-props 里。FormItem 读取的是 decorator props。

现象五：改 JSON 后页面白屏。 检查解析逻辑是否捕获异常，以及根节点类型校验是否生效。本章的 parseSchema 在 JSON.parse 失败时返回错误对象，不抛出，因此页面能显示可读的错误信息。

避坑清单 ​

  1. Schema 里只写字符串名。 不把组件对象、函数、正则字面量塞进 Schema；否则无法序列化、无法存库、无法跨端。
  2. mapProps 只映射需要的字段状态。 不要图省事把整个 field 透传给第三方组件，否则组件可能绕过模型改状态，联动和校验都会失控。
  3. 只读字段也要进模型。 用 connect + mapProps({ value: true }) 保留字段身份，而不是写成纯展示组件。
  4. 复用优先用对象展开，但要接受浅合并的边界。 需要参数化时抽函数，但要清楚这会牺牲可序列化。
  5. 实时编辑器必须做容错。 JSON.parse 一定会有失败的时候，错误提示比白屏更有用；根节点类型校验能挡住一半的低级错误。

小结与自测 ​

本章把「Schema 表达不了的部分」收回到注册表：组件实现留在代码里，Schema 只写名字。connect + mapProps 控制字段状态到 props 的映射边界，FormGrid 把布局变成配置，对象展开解决字段级复用，实时编辑器则划出了低代码的底线——能序列化的配置才是配置。下一卷会进入真正的可视化编排引擎，那里会把「物料、插件、设计器、渲染器」拆得更细，但这条底线不会变。

1. 为什么 Schema 里不能直接写 React 组件？

因为 Schema 需要被序列化、存库、跨端传输和做版本 diff。React 组件包含函数、闭包和运行时依赖，无法被 JSON 表达。用字符串名 + 注册表，可以把「配置」和「实现」分离，实现升级不影响历史配置。

2. `mapProps` 的作用是什么？

它声明字段状态到组件 props 的映射关系，例如把 field.value 映射成 props.value、把 field.onChange 映射成 props.onChange。显式映射可以避免把整个 field 对象透传给第三方组件，保持组件与模型的边界清晰。

3. 为什么实时编辑器只接受纯 JSON？

因为它的目标是演示「配置可序列化」。一旦允许函数，文本无法被 JSON.parse，配置无法存库和跨端，低代码平台的价值就消失了。需要函数的逻辑应该放在代码里的自定义组件、函数式 reactions 或后端规则引擎中。
