第 07 章 · lowcode-engine 架构：一个设计器由哪几层组成 ​

前置章节：第 06 章 · Formily 进阶
所需环境：Node 22 LTS、pnpm 9.15.4；本章 lab 使用 React 16.14.0 + Fusion Next 1.24.18 + @alilc/lowcode-engine 1.3.4。
难度：★★★
本章交付物：一个能启动、能选中节点、能在大纲与设置器之间联动的三栏设计器，以及一张能解释启动链路的架构图。

前六章我们一直在「用别人的低代码产品」：amis 用 Schema 描述页面，Formily 用 Schema 描述表单。它们都默认了一件事——页面结构已经有人设计好了，你只需要填配置。到了 lowcode-engine，问题反过来了：你要做的不是一个页面，而是一个让别人做页面的工具。这时真正难的已经不是表单或表格，而是编辑器的分层：谁持有节点树，谁负责渲染，谁把拖拽变成数据，谁在右侧显示属性。

阿里低代码引擎是国内讨论度最高的开源搭建内核之一。它不提供成品的业务组件，也不提供完整的后台模板，它提供的是一套「设计器骨架 + 物料协议 + 插件机制」。理解这套骨架，比记住某个 API 更重要；因为 API 会随版本变化，分层不会。

本章你将获得 ​

读完本章，你应该能完成四件事：

  1. 说清引擎（engine）、设计器（designer）、模拟器（simulator）、物料（material）、插件（plugins）五层各自的职责与依赖方向；
  2. 跑通 labs/lowcode-engine 的最小设计器，并解释 init 之前为什么必须先注册初始化插件；
  3. 看懂 project schema 的 componentsMap 与 componentsTree，知道缺一个字段会导致画布空白还是组件报错；
  4. 判断一个团队该自研设计器、基于 lowcode-engine 二次开发，还是直接买商业搭建平台。

本章的 lab 只有一个工程 labs/lowcode-engine，第 07~09 章共用。第 07 章只做「启动 + 三栏」，不引入自定义物料和业务插件；这样你看到的每一个现象，都能追溯到引擎的某一层。

先看漫画 ​

这一话的冲突很常见：团队决定自研搭建平台，第一版把「拖拽 + 渲染 + 属性面板」写在一个大组件里，两周看起来能用；第三周要加撤销、第四周要加多人协作、第五周要接物料市场，结果每一层改动都牵动另外两层，最后没人敢动核心代码。

码叔没有直接给方案，而是先画了一张分层图：引擎管生命周期，设计器管节点树，模拟器管真实渲染，物料管「有哪些组件」，插件管「平台自己的业务」。漫画想说明的不是「分层很优雅」，而是「不分层，扩展成本会指数上升」。

如果你只记住一句话：设计器的复杂度不在画布，而在层与层之间的边界。 边界定错，后面每加一个功能都是在还债。

逐格讲解、坑点清单和三道自测题在 EP.07 漫画讲解。

从一个真实问题说起 ​

假设你所在的公司有 40 个中后台页面，前端只有 6 个人。运营提出三个诉求：

  • 常规列表页、详情页希望能自己改文案、调字段顺序，不再排期；
  • 复杂页面仍由前端开发，但希望和运营搭建的页面使用同一套组件与发布流程；
  • 未来要把页面能力输出给客户，客户在自己的系统里也能搭建。

这时你会遇到三个选择。第一，继续手写，把运营需求排进迭代；第二，买一套商业搭建平台，接受它的组件体系与数据源约束；第三，基于开源引擎自研，保留组件与发布链路的控制权。三条路都能走，但成本结构完全不同：手写的成本随页面数量线性增长；商业平台的成本是 license 加定制；自研的成本集中在第一年，之后随物料与插件增加而摊薄。

lowcode-engine 适合第三种。它把最难的几件事——节点树、选中态、拖拽、撤销、模拟器通信、物料协议——做成了内核，把业务相关的部分留成插件。代价是概念多、启动链路长、文档偏工程化。这一章就是把这套概念压缩成一条可以跑通的路径。

需要提前说明边界：本章不会教你写一个完整的页面搭建平台。数据源、多人协作、发布、权限、物料市场都不在 lab 范围内。lab 只保留最小设计器，目的是让你看清内核如何运转；真正的产品化，是在这套内核上逐个补插件。

原理拆解 ​

五层：engine、designer、simulator、material、plugins ​

先给结论，再逐层解释：

  • engine（引擎）：最外层门面。负责 init、插件注册、配置、快捷键、整体生命周期。它不直接画画布，也不直接管节点。
  • designer（设计器）：节点树与编辑态的核心。持有 document、node、selection、history、dragon（拖拽）等模型。你在画布上选中一个节点，本质是 designer 的 selection 发生了变化。
  • simulator（模拟器）：真正把 Schema 渲染成页面的地方。它运行在一个 iframe 里，用真实组件渲染，并把鼠标事件回传给 designer。设计器画布不是「另一套渲染」，而是「真实渲染 + 编辑遮罩」。
  • material（物料）：组件元数据与资产包。它回答三个问题：有哪些组件、每个组件有哪些属性、这些组件的运行时代码从哪里加载。
  • plugins（插件）：平台自己的业务扩展。保存、预览、出码、数据源、权限按钮，全部以插件形式挂在引擎上，而不是改引擎源码。

依赖方向是单向的：engine 启动 plugins，plugins 操作 designer / material / skeleton；designer 把 Schema 交给 simulator；simulator 通过 postMessage 把选中、悬停、拖拽落点回传给 designer。material 是 designer 与 simulator 的共同输入，所以它必须能被序列化、能被跨窗口加载。

理解这一点，很多「为什么改了 Schema 画布不更新」的问题就有答案了：要么 designer 没收到变更，要么 simulator 没收到消息，要么 material 没解析出组件。三者是三段链路，不是一件事。

启动链路：为什么先注册插件，再 init ​

官方 demo 的启动顺序不是「先 init 再配置」，而是：

  1. plugins.register(EditorInitPlugin, options) 注册初始化插件；
  2. plugins.register(其他业务插件)；
  3. plugins.init()；
  4. init(container, options) 渲染 Workbench。

第 3 步会按注册顺序执行每个插件的 init()。初始化插件在这个阶段做两件事：material.setAssets(assets) 与 project.importSchema(schema)。如果反过来，先 init 再设置物料，Workbench 第一次渲染时组件表还是空的，画布会先报一轮「未知组件」，再靠后续事件补救，体验和日志都很差。

本 lab 把这个顺序收进 bootEngine：

ts
// 文件: labs/lowcode-engine/src/engine/boot.ts（节选）
await engine.plugins.register(createLabInitPlugin(options));
for (const plugin of options.extraPlugins ?? []) {
  await engine.plugins.register(plugin);
}
await engine.init(host, {
  locale: "zh-CN",
  enableCondition: true,
  enableCanvasLock: true,
  supportVariableGlobally: true,
  enableContextMenu: true,
});

这里有一个工程细节值得单独说：初始化插件用闭包接收 assets 与 projectSchema，而不是走 plugins.register(plugin, options) 的第二个参数。因为引擎会用 preferenceDeclaration 过滤插件选项，没有声明 preference 的插件拿到的是空对象，表现就是 setAssets(undefined)，控制台报 Cannot read properties of undefined (reading 'components')。这个坑在官方 demo 里不明显，因为它的初始化插件声明了完整的 preference；裁到最小工程时反而容易踩到。

UMD 还是 ESM：引擎为什么必须走全局变量 ​

低代码引擎的 npm 包同时提供 ESM 与 UMD。看起来 ESM 更现代，但直接 import 会在浏览器端遇到两个问题：

第一，部分内部模块仍在使用 CommonJS 的 require，例如 setter 注册表里对 @alilc/lowcode-engine-ext 的引用。Vite 的 ESM 转换不会自动补一个浏览器可用的 require，运行时会直接报 require is not defined。

第二，模拟器是一个独立 iframe，它需要 React、ReactDOM、PropTypes、物料库都挂在全局。官方 demo 的做法是先加载 UMD，再把 parent.React、parent.ReactDOM 注入 iframe；引擎从 engine-core.js 的 script 地址推导 public path，再去同级目录加载 react-simulator-renderer.js。这条链路依赖全局变量与固定目录结构，改成打包产物反而更难复现。

所以本 lab 沿用官方 demo 的加载方式：index.html 里按顺序加载 React、工具库、Fusion Next、引擎、引擎扩展，最后才是我们自己的 type=module 入口。scripts/sync-vendor.mjs 负责把 UMD 文件从 node_modules 复制到 public/vendor，保证版本与 lockfile 一致。

这不是「技术栈落后」，而是尊重运行时的真实约束。你要改的是业务插件，不是引擎的加载机制；在没有充分理由前，不要为了「看起来现代」去重写启动链路。

project schema：componentsMap 与 componentsTree ​

引擎导入的不是单个页面的 Schema，而是一个 project schema：

ts
// 文件: labs/lowcode-engine/src/engine/project-schema.ts（节选）
return {
  version: "1.0.0",
  componentsMap: [
    pageComponent,
    nextComponent("Button"),
    nextComponent("Card"),
    nextComponent("Input"),
  ],
  componentsTree: [pageSchema],
  i18n: {},
};

componentsTree 是页面节点树，和 amis 的 Schema 很像：每个节点有 componentName、id、props、children。componentsMap 则回答「这个组件从哪里来」：包名、版本、导出名、是否解构。少了 componentsMap，designer 仍能创建节点，但 simulator 找不到组件，画布会显示错误块而不是真实组件。

这里有两个常见误解。第一，以为 componentsMap 可以自动从物料推断。实际上引擎只使用你导入的这份映射；物料元数据负责「组件面板与设置器」，componentsMap 负责「运行期取组件」，两者相关但不能互相替代。第二，以为 Page 是自动存在的。Page 确实是引擎内置的根容器，但它仍要出现在 componentsMap 里，否则 isValidComponent 会返回 false，根节点被当成未知组件。

产品对照 ​

把 lowcode-engine 放回五类产品里，它的定位是「搭建内核」，不是「开箱即用的搭建平台」。和前面几章的对照如下：

维度amisFormilylowcode-enginetmagic-editorGrapesJS
抽象层级页面 Schema表单模型设计器内核页面编排HTML/CSS 画布
你得到什么渲染器 + 组件库表单引擎可扩展设计器可视化编辑器自由画布
业务成本低中高中中
扩展方式自定义渲染器自定义字段物料 + 插件组件 + 数据源插件 + Block
适合谁业务前端表单密集型团队平台型团队运营/活动团队建站/邮件

这张表最重要的不是「谁更强」，而是「谁把复杂度留给了你」。amis 把组件与布局都准备好了，你只需要写 Schema；lowcode-engine 把内核准备好了，组件、数据源、发布、权限都要你自己补。选择 lowcode-engine，等于选择了一支平台团队的工作量。

什么时候不该用 lowcode-engine？至少三类：只需要几十个固定后台页面，用 amis 更快；只需要复杂表单，用 Formily 更专注；只需要活动页或静态页，用 tmagic-editor 或 GrapesJS 成本更低。lowcode-engine 的优势只在「要长期维护一套搭建平台，且物料与插件需要持续演进」时才会显现。

动手实现 ​

第一步：目录与命令 ​

lab 的目录按「共享内核 + 章节目录」组织：

text
labs/lowcode-engine/
├── index.html                 # UMD 加载顺序
├── public/lab-materials.js    # 第 08 章自定义物料
├── scripts/sync-vendor.mjs    # 复制 UMD 到 public/vendor
├── scripts/smoke.mjs          # 三章烟测
└── src/
    ├── engine/                # boot / assets / project schema
    ├── overview.ts            # 章节入口页
    └── chapters/
        ├── 07-lowcode-engine-architecture/
        ├── 08-lowcode-engine-materials/
        └── 09-lowcode-engine-plugins/

命令只有四条：

bash
cd labs/lowcode-engine
pnpm install
pnpm dev      # 5176
pnpm smoke    # 构建 + preview 5276 + 系统 Chrome

pnpm dev、pnpm build、pnpm smoke 之前都会自动执行 pnpm vendor。这一步不是可选优化，而是必需：public/vendor 被 .gitignore 忽略，不跑同步就没有 React 与引擎文件。

第二步：写物料资产 ​

第 07 章只需要 Fusion Next 的三个组件。资产清单分两段：

ts
// 文件: labs/lowcode-engine/src/engine/assets.ts（节选）
export const baseAssets = {
  packages: [nextPackage, ...runtimePackages],
  components: nextComponents,
  sort: {
    groupList: ["精选组件"],
    categoryList: ["基础元素", "容器"],
  },
};

packages 只描述运行时资源：包名、版本、全局变量名、需要加载的 JS/CSS。components 才是组件元数据：标题、属性、Setter、npm 来源。两者分开不是风格问题，而是引擎的硬约束：assetsTransform 只读顶层 components，把元数据塞进 packages[].components 会在 setAssets 阶段直接抛错。

每个组件的 npm 字段必须写全：

ts
npm: {
  package: "@alifd/next",
  version: NEXT_VERSION,
  exportName: "Button",
  destructuring: true,
  subName: "",
}

少了 exportName 与 destructuring，designer 生成的 componentsMap 会退化成「取整个包的 default」，simulator 拿到的是一个模块对象而不是 React 组件，控制台报 Card is not a react component。这是本章最容易踩、也最不像「配置错误」的坑。

第三步：用插件导入物料与 Schema ​

初始化插件只做两件事，但顺序不能反：

ts
// 文件: labs/lowcode-engine/src/engine/boot.ts（节选）
const plugin = (ctx: any) => ({
  async init() {
    ctx.config.set("scenarioName", `lab-${options.chapter}`);
    await ctx.material.setAssets(options.assets);
    ctx.project.importSchema(options.projectSchema);
  },
});

setAssets 是异步的：它要解析组件元数据、建立索引、通知 designer 与 simulator。如果不等它完成就 importSchema，画布可能先拿空组件表渲染一轮，出现短暂错误块。importSchema 本身是同步创建文档模型，真正的渲染由 simulator 在后续消息中完成。

第四步：页面 Schema 与三栏验证 ​

第 07 章的页面只有三层：Page → Card → Input/Button。跑起来后做三件事验证分层：

  1. 点击左侧大纲图标，核对节点树是否与 Schema 一致；
  2. 点击画布上的卡片，右侧应该出现「卡片标题」Setter；
  3. 修改标题，画布应实时更新，大纲节点的标题也应同步。

这三步分别验证了 designer 的节点树、material 的元数据、simulator 的渲染回路。任何一步失败，都能定位到具体一层：大纲错是 designer 或 Schema 的问题，右栏空是 material 的问题，画布不刷新是 simulator 通信的问题。

第五步：烟测为什么点三栏 ​

scripts/smoke.mjs 不只等页面加载，而是真的打开大纲、点选卡片、断言右栏出现 Setter。原因是设计器的「加载完成」很难用一个选择器判断：.engine-main 出现只代表外壳好了，iframe 里可能还在加载 React；设置器面板一直存在，只是内容为空。烟测用「选中后出现具体字段」作为完成信号，比等固定秒数可靠。

跑不起来？ ​

先按这个顺序排查，能覆盖九成问题：

  1. 页面白屏，控制台报 window.AliLowCodeEngine 不存在：检查 index.html 的 script 顺序，以及 public/vendor/engine/js/engine-core.js 是否存在；不存在就先跑 pnpm vendor。
  2. 报 require is not defined：说明引擎被当成 ESM 打包了。确认走的是 UMD，而不是 import { init } from '@alilc/lowcode-engine'。
  3. 画布空白，但大纲有节点：通常是 componentsMap 缺项或 npm.exportName 缺失，打开控制台看 is not a react component。
  4. Cannot read properties of undefined (reading 'components')：插件选项被 preference 过滤成空对象，检查是否用闭包传 assets。
  5. 端口冲突：lab 用 --strictPort 锁 5176/5276，被占用会直接失败，先 lsof -i :5176 再决定换端口还是杀进程。
  6. 模拟器 iframe 里没有 Next：packages[].urls 必须包含 /vendor/next.min.js，iframe 不会自动继承父页面的全局变量。

避坑清单 ​

  1. 不要在同一页面初始化两个引擎。章节切换用整页刷新，比 destroy() 后重新 init() 稳；残留的 iframe 与消息监听很难彻底清理。
  2. 不要把业务逻辑写进物料元数据。元数据只描述「怎么展示、怎么设置」，真正的业务规则放插件或运行时代码。
  3. 不要省略 componentsMap 里的 Page。它是内置根容器，但仍需登记。
  4. 不要用 packages[].components 代替顶层 components。层级错了，报错信息不会告诉你「放错地方」，只会说 undefined。
  5. 不要把所有组件塞进一个资产包。按业务域拆包，后续才能按需加载、独立发版。
  6. 不要在 UI 线程做重活。物料解析、Schema 转换都可能很重，平台化之后要评估是否需要 Worker。

小结与自测 ​

本章的核心不是某个 API，而是分层：engine 管生命周期，designer 管节点与编辑态，simulator 管真实渲染，material 管组件协议，plugins 管平台业务。启动顺序必须是「注册插件 → 插件 init 设置物料与 Schema → 渲染 Workbench」。project schema 由 componentsMap 与 componentsTree 两部分组成，前者决定组件能不能被解析，后者决定页面长什么样。

1. 为什么必须先 setAssets 再 importSchema？

importSchema 创建文档后，simulator 会立即按组件表渲染。如果此时物料还没解析完，组件表为空，画布会先渲染错误块，再靠后续事件补救。先 setAssets 能保证第一次渲染就拿到完整组件索引。

2. `componentsMap` 和物料元数据各自负责什么？

物料元数据负责设计态：组件面板展示、右侧 Setter、属性默认值。componentsMap 负责运行态：simulator 按包名、导出名、是否解构去全局变量里取真实组件。两者相关，但不能互相替代；缺 componentsMap 的后果是画布报「不是 React 组件」。

3. 为什么这个 lab 不把引擎打成 ESM？

引擎内部仍有 CommonJS require，模拟器又依赖全局 React 与固定 public path。官方 demo 的 UMD 链路是经过验证的；改成 ESM 需要额外处理 require、iframe 全局注入与资源路径，收益很低，风险很高。

下一步 ​

第 07 章只证明了「设计器能启动」。第 08 章会把物料协议拆开：自定义一个业务组件，写它的元数据，再注册一个自定义 Setter，让右侧面板能改它的业务属性。到那时你会更清楚地看到，material 不是一个组件库，而是一份可被设计器与渲染器共同解释的协议。
