第 09 章 · 插件系统：保存、预览与出码 ​

前置章节：第 08 章 · lowcode-engine 物料协议
所需环境：Node 22 LTS、pnpm 9.15.4；本章 lab 使用 React 16.14.0 + Fusion Next 1.24.18 + @alilc/lowcode-engine 1.3.4。
难度：★★★
本章交付物：一个带「保存 Schema / 查看 Schema / 预览 / 出码」四个按钮的插件，以及一份可读的 React 出码结果。

前两章解决了「设计器能启动」和「组件能被认识」。但一个平台只有设计器是不够的：用户搭完页面，总得保存、预览、发布，最好还能导出代码。这些动作不属于引擎内核，而属于平台业务。lowcode-engine 的做法是把它们全部做成插件：引擎只提供生命周期与扩展点，平台通过插件往里加东西，不必 fork 引擎。

插件系统听起来抽象，落到代码其实只有几个接口：插件函数、ctx 上下文、init() 生命周期、skeleton.add() 扩展点。真正难的不是 API，而是边界感——什么该放插件、什么该放引擎、什么该放物料。边界放错，插件会越写越像补丁。

本章你将获得 ​

读完本章，你应该能完成四件事：

  1. 说清插件函数的签名、init() 的调用时机，以及插件之间如何声明依赖；
  2. 用 ctx.skeleton.add 往顶部工具条加按钮，并解释 area / type / props / content 的含义；
  3. 用 ctx.project.exportSchema("save") 导出 Schema，完成保存、查看、轻量预览与出码；
  4. 判断预览与出码的工程边界，知道教学级实现与生产级实现的差距。

本章 lab 在第 08 章基础上增加 09-lowcode-engine-plugins 目录。它不改引擎、不改物料，只新增一个插件与三个工具函数，正好对应「平台业务」这一层。

先看漫画 ​

这一话的冲突很典型：平台第一版把保存、预览、发布按钮直接写进设计器源码，能跑；第二版要接公司的权限系统，第三版要换发布流程，第四版要给不同租户定制工具条。每次需求都改内核，合并冲突不断，最后没人敢升级引擎版本。

码叔的方案是把业务动作收进插件：引擎升级不影响插件，插件可以按租户组合，权限与发布流程各自独立。漫画里那句「你不是在改引擎，你是在组合引擎」就是本章的主线。

如果你只记住一句话：插件的价值不在「能加按钮」，而在「加完按钮不用改内核」。 逐格讲解、坑点清单和三道自测题在 EP.09 漫画讲解。

从一个真实问题说起 ​

设计器能用了，运营问的第一个问题不是「怎么拖」，而是「我改的东西保存了吗」。第二个问题是「能不能先看看效果」。第三个问题来自研发：「能不能直接给我 React 代码，我不想再手写一遍」。

这三个需求看似不同，其实共享同一条数据链路：

  1. 从 designer 导出当前 project schema；
  2. 把 schema 序列化，写入某个存储；
  3. 用另一套渲染器解释 schema，得到预览；
  4. 用代码生成器把 schema 转成源码。

如果每个需求都直接写进设计器组件，就会出现三份重复的「取 Schema」逻辑和三种不一致的保存格式。正确做法是先定义一个稳定的导出边界：project.exportSchema("save")。保存、预览、出码都从这份导出结果出发，插件只负责「拿去做什么」，不负责「怎么取」。

本章的 lab 就按这个思路实现：一个插件注册四个按钮，三个工具函数分别处理 Schema 展示、预览渲染与代码生成。它们都很短，但边界清晰。

原理拆解 ​

插件函数的签名与生命周期 ​

一个插件本质上是一个函数：

ts
function MyPlugin(ctx) {
  return {
    init() {
      // 在这里访问 ctx.config / ctx.project / ctx.skeleton / ctx.material
    },
  };
}
MyPlugin.pluginName = "MyPlugin";

引擎在 plugins.init() 阶段按注册顺序调用每个插件的 init()。ctx 是插件与引擎之间的唯一通道，常用成员有：

  • ctx.config：读写场景配置，例如场景名、租户、功能开关；
  • ctx.project：当前项目与文档，导出 Schema、导入 Schema、监听变更；
  • ctx.material：物料资产与组件元数据；
  • ctx.skeleton：工作台布局扩展点，加工具条、面板、按钮；
  • ctx.setters：Setter 注册表；
  • ctx.event：事件总线，插件之间解耦通信。

pluginName 不是装饰，它是插件依赖声明的键。插件可以写 meta.dependencies，引擎会据此调整初始化顺序。第 09 章的工具栏插件声明依赖 LabInitPlugin，保证执行到它时物料与 Schema 已经就绪。

扩展点：skeleton 的四个参数 ​

ctx.skeleton.add(config) 是往工作台加 UI 的入口。四个关键字段：

  • area：加到哪里，例如 topArea、leftArea、rightArea；
  • type：扩展点类型，例如 Widget、Panel、Dock；
  • props：布局参数，例如 align: "right"；
  • content：React 元素，真正渲染的内容。

本章的按钮都加在 topArea，align: "right" 让它们靠右排列。content 用 window.React.createElement(window.Next.Button, ...) 创建，而不是 JSX，因为我们的入口是 .ts 文件，不经过 React 插件编译。这个选择看起来朴素，但避免了「打包 React 与全局 React 两份实例」的问题——在 UMD 体系里，两份 React 会让 hooks 直接报 invalid hook call。

导出边界：stage 为什么传 save ​

project.exportSchema(stage) 支持多个转换阶段：render、serialize、save、clone、init、upgrade。不同阶段会对 Schema 做不同处理，例如补全、裁剪、升级版本。

插件保存时应该用 "save"，因为它代表「准备持久化的稳定形态」；预览可以用 "render"，因为它更接近运行期需要的结构。如果所有场景都随手传一个阶段，短期看不出问题，长期会出现「保存的 Schema 能回显但不能渲染」或「预览正常但保存丢字段」。

本 lab 统一用 "save"，是为了让保存、查看、预览、出码看到同一份数据，便于对照。真实平台建议把「存储 Schema」与「运行 Schema」分开，明确哪些字段只属于设计态。

预览：为什么不用第二个引擎 ​

最直接的预览方式是再启动一个引擎实例，把 Schema 导进去。但这会带来三个问题：同一页面两个引擎、模拟器 iframe 重复加载、内存与事件监听双份。官方建议预览用独立的渲染器或独立窗口，而不是在设计器页面里再 init 一次。

本 lab 用一个几十行的递归渲染器做轻量预览：

ts
const RENDERERS = {
  Page: (_props, children) => React.createElement("div", null, children),
  Card: (props, children) => React.createElement(Next.Card, props, children),
  Input: (props) => React.createElement(Next.Input, props),
  Button: (props) => React.createElement(Next.Button, props, props.children),
  OrderSummary: (props) => React.createElement(LabMaterials.OrderSummary, props),
};

它只覆盖 lab 用到的组件，遇到未知组件会降级成占位块。这不是「偷懒」，而是明确边界：教学预览只证明「Schema 能被另一套渲染器解释」，不承诺生产级的组件覆盖、样式隔离与数据源注入。

出码：Schema 到源码的映射 ​

出码的目标是把节点树翻译成可读的 React 代码。最小实现要做四件事：

  1. 根据 componentsMap 生成 import，避免手写时漏包；
  2. 递归节点，把 componentName 映射成 JSX 标签；
  3. 把静态 props 转成 JSX 属性，跳过表达式与事件；
  4. 处理 children 与文本子节点，控制缩进。

本章的 generateReactCode 就是这四步。它故意不处理 JSExpression、JSFunction、循环、插槽与样式单位，因为这些需要一套完整的表达式求值与代码打印器。教学级出码的价值是让你看清「Schema 与源码同构」，而不是替代官方出码服务。

产品对照 ​

插件机制不是 lowcode-engine 独有，但各家的扩展面差别很大：

维度lowcode-engineamisFormilytmagic-editor
扩展单位插件渲染器字段组件编辑器插件
能改什么工具条/面板/生命周期组件渲染字段行为编辑器能力
业务动作保存/预览/发布/权限通常外置通常外置保存/发布
学习成本高低中中
适合场景平台型产品中后台表单活动页

amis 的扩展面在「渲染器」，你很难通过它改编辑器工具条；Formily 的扩展面在「字段」，它不关心页面级业务动作；tmagic-editor 的插件更偏编辑器能力；lowcode-engine 的插件面最宽，能加 UI、能监听生命周期、能接外部服务，所以它适合做平台，而不是做页面。

这也意味着责任更重：插件能做的事越多，越需要约定「什么不该做」。保存插件不应该直接改节点树，预览插件不应该启动第二个引擎，出码插件不应该依赖设计器的内部对象。边界清晰，插件才能独立升级。

动手实现 ​

第一步：注册插件 ​

章节入口只多了一行 extraPlugins：

ts
await bootEngine(host, {
  chapter: "09",
  assets: materialChapterAssets,
  projectSchema: createProjectSchema(page, [orderSummaryComponent]),
  extraPlugins: [LabToolbarPlugin],
});

bootEngine 先注册初始化插件，再注册业务插件，最后 init。这个顺序保证 LabToolbarPlugin.init() 执行时，ctx.project 已经有文档。

第二步：加四个工具条按钮 ​

四个按钮共用同一个工厂，避免重复写 props：

ts
function toolbarButton(label, onClick, primary = false) {
  return React.createElement(
    Next.Button,
    {
      size: "small",
      type: primary ? "primary" : "normal",
      onClick,
      style: { marginLeft: "8px" },
    },
    label,
  );
}

保存按钮加 primary，因为它是高频动作；其余三个用普通样式。每个按钮都通过 skeleton.add 注册到 topArea，name 必须唯一，否则后注册的会覆盖先注册的。

第三步：保存到 localStorage ​

保存逻辑只有三行：

ts
const schema = ctx.project.exportSchema("save");
localStorage.setItem(`${scenarioName}:projectSchema`, JSON.stringify(schema));
Next.Message.success("已保存到 localStorage");

scenarioName 来自初始化插件写入的 ctx.config。加场景前缀是为了避免多个 lab、多个租户互相覆盖。真实平台会换成后端接口，但「先取 Schema、再序列化、再写入」的顺序不变。

保存成功后不要忘记给用户反馈。设计器里没有浏览器地址栏变化，也没有页面跳转，静默保存会让用户不确定是否成功。

第四步：查看 Schema 与轻量预览 ​

查看 Schema 用原生弹层展示 JSON，重点是让用户能直接看到 componentsTree 与 componentsMap。预览则把同一份 Schema 交给递归渲染器：

ts
openModal("预览 · 基于 Schema 的轻量渲染", (body) => {
  const root = document.createElement("div");
  body.appendChild(root);
  ReactDOM.render(renderNode(page), root);
  return () => ReactDOM.unmountComponentAtNode(root);
});

openModal 返回清理函数，关闭时卸载 React 树，避免旧节点与事件残留。这个小细节在多轮预览时很重要：不卸载会出现「上一次的组件还在后台跑定时器」。

第五步：生成 React 代码 ​

出码器先按 componentsMap 生成 import，再递归节点。核心是缩进：每个递归层级传 depth + 1，不要「生成完再整体缩进一次」，否则子节点会越缩越深。生成结果应该像手写代码：

tsx
import { Card } from "@alifd/next";
import { OrderSummary } from "lab-materials";

export default function LowcodePage() {
  return (
    <div className="lowcode-page">
      <Card title={"待发货订单金额"}>
        <OrderSummary title={"待发货订单金额"} amount={45980.5} tone={"violet"} />
      </Card>
    </div>
  );
}

字符串属性用 {"..."} 而不是裸引号，是为了避免中文、引号、换行带来的转义问题。真实出码器还会处理表达式、事件、样式单位与组件导入去重，这里保持最小可读。

第六步：烟测四个按钮 ​

pnpm smoke 对第 09 章做四件事：

  1. 断言四个按钮都出现；
  2. 点保存，等待 localStorage 出现 lab-09 键；
  3. 点查看，断言弹层内容含 componentsTree；
  4. 点出码，断言结果含 <Card 与 <OrderSummary。

截图输出 screenshots/09-plugins.png。这四步覆盖了「插件加载 → 扩展点生效 → 数据导出 → 代码生成」的完整链路。

跑不起来？ ​

  1. 工具条没有按钮：检查插件是否在 extraPlugins 里，init() 是否执行，skeleton.add 的 area 是否是 topArea。
  2. 点保存报 exportSchema is not a function：ctx.project 在插件 init 时还没就绪，通常是插件顺序问题；给插件加 meta.dependencies。
  3. 保存的 Schema 回显后画布空白：检查导出阶段与导入阶段是否匹配，以及 componentsMap 是否完整。
  4. 预览弹层白屏：打开控制台看是否缺 Next 或 LabMaterials；预览复用父页面全局变量，父页面没加载就会失败。
  5. 出码结果无法编译：教学级出码只处理静态 props，遇到表达式会跳过；不要把生成结果直接当生产代码。
  6. 弹层关闭后定时器还在跑：确认 openModal 的清理函数被调用，React 树已卸载。

避坑清单 ​

  1. 插件名必须唯一。重复注册会互相覆盖，工具条只剩一个按钮。
  2. 不要在插件里直接改节点树。节点变更走 designer 的 API，插件只做业务编排。
  3. 不要在设计器页面启动第二个引擎。预览用独立渲染器或独立窗口。
  4. 保存与预览使用同一份导出边界，但可以按场景选择不同 stage。
  5. 出码是产品能力，不是教学玩具。真要上线，评估官方出码服务或自研打印器。
  6. 插件也要有错误处理。保存失败、网络失败、Schema 不合法，都要给用户明确反馈。

小结与自测 ​

插件是引擎留下的正式扩展面：插件函数返回 init()，通过 ctx 访问配置、项目、物料、骨架与 Setter；skeleton.add 把 UI 加到工作台；project.exportSchema("save") 是保存、预览、出码的共同起点。预览与出码都有工程边界，教学实现只证明链路，不承诺生产级覆盖。

1. 为什么保存、预览、出码都从 exportSchema 开始？

因为它是设计器与外部世界之间稳定的数据边界。三者如果各自从内部对象取数据，会出现格式不一致、字段缺失、无法回显的问题。统一导出后再分发，能保证它们看到同一份 Schema。

2. skeleton.add 的 area 与 type 分别决定什么？

area 决定加在哪个区域（顶部、左侧、右侧等），type 决定扩展点类型（Widget、Panel、Dock 等），两者共同决定布局行为。props 再补充对齐、尺寸等参数，content 才是真正的 React 内容。

3. 教学级预览与生产级预览差在哪里？

教学预览只覆盖少量组件与静态 props，没有数据源、样式隔离、表达式求值、异步加载与错误边界。生产预览需要完整物料包、运行环境注入、沙箱与性能优化，通常由独立渲染服务承担。
