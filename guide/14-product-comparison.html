第 14 章 · 产品横向对比：五强横评，没有银弹 ​

前置章节：第 13 章 · GrapesJS 进阶
所需环境：无（纯文档章节）；本章不建 lab，对照结论基于前 13 章的实测。
难度：★
本章交付物：5+2 产品对照矩阵、三问选型决策树、场景选型映射表、组合使用策略。

走完五个主线产品（amis、Formily、lowcode-engine、tmagic-editor、GrapesJS），你应该能感受到一个事实：没有银弹。每个产品都在"约束强度"和"灵活度"的光谱上占据一个位置——amis 最约束（Schema 驱动一切），GrapesJS 最自由（直接操作 DOM），Formily/lowcode-engine/tmagic-editor 在中间各有侧重。

本章的目标是帮你建立选型直觉：面对一个具体需求，能用三问决策树快速定位到合适的产品，知道每个产品的"甜蜜区"和"雷区"，理解什么场景下该组合使用多个产品。本章不涉及新的代码和 lab，所有结论都基于前 13 章的实测。

本章你将获得 ​

读完本章，你应该能完成四件事：

  1. 说出五个主线产品在"画布自由度 / DSL 形式 / 自定义组件协议 / 运行时分离 / 导出产物"五个维度的差异；
  2. 用三问决策树（表单还是页面？自由还是约束？单端还是跨端？）快速选型；
  3. 看懂五强能力对照表，知道每个产品的"甜蜜区"和"雷区"；
  4. 理解组合使用策略——比如 amis 做页面 + Formily 做复杂表单、lowcode-engine 做设计器 + tmagic 做 H5 运行时。

从一个真实问题说起 ​

你接到一个需求：做一个"客户运营后台"，包含概览卡片、客户列表 CRUD、复杂表单（含联动/异步校验）、状态筛选、导出。团队问你：用哪个低代码产品？

如果你说"用 amis"，有人会问"复杂表单的联动 Formily 不是更强吗？"；如果你说"用 lowcode-engine"，有人会问"运营同学能拖得动吗？学习成本多高？"；如果你说"用 GrapesJS"，有人会问"中后台表单能用自由画布做吗？"。

选型焦虑的本质是：每个产品都有它擅长的场景，但没有产品能覆盖所有场景。本章给你一套决策框架，让你面对需求时不是"拍脑袋选"，而是"按维度匹配"。

三问选型决策树 ​

面对任何需求，先问三个问题：

第一问：这是表单还是页面？

  • 如果核心是表单（字段多、校验复杂、联动多）→ 优先 Formily。Formily 的领域模型是五个产品里对表单抽象最彻底的——Field 模型、reactions 联动、异步校验、生命周期钩子，专为复杂表单设计。
  • 如果核心是页面（列表、卡片、布局、导航）→ 看第二问。

第二问：要约束还是要自由？

  • 如果运营/业务人员要自助搭建、要"所见即所得"、要快速交付 → amis。Schema 约束让非技术人员也能搭出结构清晰的页面。
  • 如果需要高度定制化（自定义设计器、自定义物料、自定义插件）→ lowcode-engine。它的引擎/物料/插件三层架构是五个产品里扩展性最强的。
  • 如果要自由排版（像素级布局、营销页、邮件模板）→ GrapesJS。直接操作 DOM，想怎么拖怎么拖。
  • 如果是 H5 活动页（绝对布局 + 动画 + 跨端）→ tmagic-editor。它的 MApp DSL 可以跨端渲染（移动端、小程序）。

第三问：单端还是跨端？

  • 如果只在 PC 端跑 → amis / Formily / GrapesJS 都可以。
  • 如果要跨端（PC + 移动 + 小程序）→ tmagic-editor。它的 DSL 运行时可以部署到多个端。
  • 如果要完全自定义渲染目标 → lowcode-engine。你可以写自己的渲染器，把 Schema 渲染成任何东西。

两个对照产品 ​

规格里还提到 Appsmith 和 ToolJet 作为对照（不做主线 lab）。它们是平台型应用搭建器——自带后端、数据库、权限，一站式构建内部工具。和五个主线产品的区别：

维度Appsmith / ToolJetamis / Formily / lowcode / tmagic / GrapesJS
自带后端是（数据库 + API）否（纯前端，后端自己接）
部署方式Docker / 云服务静态部署 / 自有服务
适合场景内部工具快速搭建前端页面/表单
学习曲线缓（全栈一站式）中（要接后端）
定制化低（平台约束）高（代码可控）

如果团队没有后端、要快速搭内部工具，Appsmith/ToolJet 更合适；如果团队有前端能力、要深度定制，五个主线产品更灵活。

本章本身就是对照章节，这里给一个"同一需求，五种实现"的对比：

需求：客户运营后台——概览卡片 + 客户列表 CRUD + 复杂表单 + 导出。

产品实现方式优势劣势

推荐方案：amis 做列表和页面骨架 + Formily 嵌入做复杂表单（capstone 第 15 章就是这个组合）。

动手实现 ​

本章是纯文档章节，没有代码和 lab。但你可以做一个选型练习：

选型练习 ​

假设你要做以下三个需求，分别选哪个产品？为什么？

  1. 营销活动落地页：运营要频繁换 banner、调布局、加按钮，上线后导出静态 HTML 部署到 CDN。
  2. 内部审批表单：含多级联动（省→市→区）、异步校验（用户名是否已存在）、条件显隐（选"其他"时显示备注框）。
  3. 可视化大屏设计器：运营拖拽图表组件、配置数据源、设计布局，生成的大屏要在 PC 和移动端都能看。

参考答案：1→GrapesJS（自由画布 + HTML 导出）；2→Formily（复杂表单联动 + 异步校验）；3→lowcode-engine 或 tmagic-editor（自定义设计器 + 跨端渲染）。

选型验证清单 ​

选定产品后，用这个清单验证是否合适：

  • [ ] 核心场景是否在产品的"甜蜜区"？
  • [ ] 自定义能力是否足够（组件、样式、逻辑）？
  • [ ] 团队学习成本是否可接受？
  • [ ] 导出/部署产物是否符合要求？
  • [ ] 社区活跃度和文档质量是否支撑长期使用？

跑不起来？ ​

本章是选型章节，没有代码可跑。但选型本身也会"跑不起来"——常见的选型失败模式：

症状原因修复
选了 amis 但表单联动做不了amis 的表达式能力有限嵌入 Formily 做复杂表单，或改用 Formily
选了 GrapesJS 但中后台做不动自由画布不适合表单密集场景改用 amis 或 Formily
选了 lowcode-engine 但进度卡住学习曲线陡，物料/插件要自己写先用 amis/Formily 快速出 MVP，再考虑 lowcode
选了 tmagic 但只做 PC 端跨端优势没用上，徒增复杂度改用 amis（纯 PC）或 GrapesJS（落地页）
强行用一个产品做所有事没有产品能覆盖所有场景组合使用：amis 页面 + Formily 表单 + GrapesJS 落地页

避坑清单 ​

  1. 不要因为"最火"就选：lowcode-engine 虽然出自阿里、生态大，但它是为"定制化设计器"设计的，不是为"快速搭页面"设计的。快速交付选 amis，不是 lowcode-engine。
  2. 不要因为"最自由"就选 GrapesJS：自由画布在表单/数据场景下是灾难——没有字段模型、没有校验、没有联动。GrapesJS 只适合视觉为主的页面。
  3. 不要低估 amis 的能力：很多人觉得 amis 只是"写 JSON"，但它的 CRUD、弹窗、API 数据源、表达式能力足够覆盖 80% 的中后台场景。先考虑 amis，再考虑更复杂的方案。
  4. 组合使用比单一产品更强：没有产品能覆盖所有场景。amis 做页面骨架 + Formily 做复杂表单 + GrapesJS 做营销页，是常见的组合。
  5. 选型要看团队，不只是看产品：如果团队前端能力强，lowcode-engine 的灵活性是优势；如果团队偏后端，amis 的低代码门槛更友好。

选型的三个常见误区 ​

误区一：用一个产品做所有事。 很多团队选了 amis 就想用 amis 做一切——落地页、表单、大屏、甚至小程序。结果是每个场景都做得"能用但不好用"。正确的做法是按场景选产品，允许一个项目里用多个产品。

误区二：只看功能列表，不看工程化。 选型时容易陷入"功能对比表"——A 有 X 功能，B 有 Y 功能。但实际开发中，工程化能力（构建、部署、版本管理、二次开发）比功能列表更重要。lowcode-engine 功能多但搭建成本高，amis 功能少但开箱即用——后者往往更适合快速交付。

误区三：忽视社区和文档。 低代码产品的坑很多，遇到问题时社区和文档是唯一依靠。amis 的文档最完善、lowcode-engine 的社区最活跃、GrapesJS 的英文文档好但中文资料少——这些都是选型时要考虑的。

小结与自测 ​

你应该记住的 ​

  • 五强在"约束-自由"光谱上：amis（最约束）< Formily < lowcode-engine < tmagic-editor < GrapesJS（最自由）
  • 三问决策树：表单还是页面？约束还是自由？单端还是跨端？
  • amis 甜蜜区：中后台 CRUD；雷区：复杂表单联动、深度样式定制
  • Formily 甜蜜区：复杂表单；雷区：非表单页面
  • lowcode-engine 甜蜜区：定制化设计器；雷区：快速交付、运营自助
  • tmagic-editor 甜蜜区：H5 活动页、跨端；雷区：中后台表单
  • GrapesJS 甜蜜区：营销落地页、邮件模板；雷区：表单、数据看板
  • Appsmith/ToolJet：自带后端的内部工具平台，适合无后端团队

自测题 ​

  1. 选择题：一个需求是"营销活动落地页，运营要自由排版、导出静态 HTML"，最适合的产品是？（A）amis；（B）Formily；（C）tmagic-editor；（D）GrapesJS。
  2. 选择题：一个需求是"内部审批表单，含省市区联动、异步校验、条件显隐"，最适合的产品是？（A）amis；（B）Formily；（C）lowcode-engine；（D）GrapesJS。
  3. 思考题：为什么说"没有银弹"？能不能设计一个产品同时覆盖 amis 的中后台、Formily 的表单、GrapesJS 的自由画布？为什么现有产品都没做到？

自测题参考答案 ​

  1. 答案 D。GrapesJS 的自由画布和 HTML 导出正好匹配营销落地页场景。amis 的 Schema 约束太死，tmagic 的 DSL 导出不是纯 HTML，Formily 是表单不是页面。
  2. 答案 B。Formily 的领域模型专为复杂表单设计——reactions 联动、异步校验、条件显隐都是一等公民。amis 的表达式能力有限，lowcode-engine 杀鸡用牛刀，GrapesJS 没有表单能力。
  3. "没有银弹"的本质是约束和自由不可兼得。约束越强（amis），结构越清晰、越可预测，但灵活度越低；自由越强（GrapesJS），灵活度越高，但结构越乱、越难维护。中间的产品（Formily/lowcode/tmagic）在某一个维度上做得更深（表单/设计器/跨端），但不可能同时在所有维度都做到极致。如果硬要做一个"全能产品"，结果往往是"什么都能做但什么都做不好"——这就是为什么低代码领域会分化出五个定位不同的产品。
