第 15 章 · Capstone 综合实战：从选型到上线 ​

前置章节：第 14 章 · 产品横向对比
所需环境：Node 20 + pnpm 9.15.4 + 现代浏览器（烟测用 headless chromium）；本章 lab 在 labs/capstone，是 amis + Formily 的组合工程。
难度：★★★★
本章交付物：客户运营后台（概览 + CRUD + 复杂表单 + 导出）、E2E 烟测 7 项全绿。

本章是产品实战卷的收尾——综合运用 amis 和 Formily，完成一个完整的"客户运营后台"。需求覆盖了中后台最常见的场景：概览卡片、列表 CRUD、复杂表单（联动 + 异步校验）、状态筛选、数据导出。

关键决策是组合使用：amis 负责它擅长的列表和概览，Formily 负责它擅长的复杂表单，两者在同一个 React 工程里通过路由串联，不需要 iframe。这验证了第 14 章的选型结论——没有银弹，按场景组合。

本章你将获得 ​

读完本章并跑通 lab，你应该能：

  1. 独立完成一个中后台全栈需求的低代码实现，知道什么场景用 amis、什么场景用 Formily；
  2. 在 amis 里通过自定义 fetcher 对接内存/真实后端，理解 amis 的数据协议；
  3. 在 Formily 里实现字段联动（onFieldReact）和异步校验（Promise validator）；
  4. 处理amis 和 Formily 在同一工程共存时的集成坑（路由跳转、样式隔离、数据边界）；
  5. 写一个端到端烟测，验证从"打开首页 → 新增客户 → 表单校验 → 保存 → 列表出现"的完整链路。

先看漫画 ​

这一话画的是 capstone 的完整决策链——需求评审时标签君面对五个产品做选型，像素酱拆解架构（amis 列表 + Formily 表单 + React Router 串联），编码时验证两者在同一 DOM 共存，最后码叔复盘"组合拳比单打独斗强"。逐格讲解、坑点清单和三道自测题在 EP.15 漫画讲解。

从一个真实问题说起 ​

假设你是某 SaaS 公司的前端，产品经理丢过来一个需求：做一个"客户运营后台"，让运营同学管理客户信息。具体功能：

  1. 概览页：三张统计卡片——客户总数、活跃客户数、VIP 客户数；
  2. 客户列表：表格展示所有客户，支持按姓名/状态/等级筛选，支持编辑和删除；
  3. 新增/编辑客户：一个复杂表单，字段包括姓名、邮箱、电话、等级、行业、状态、备注；
  4. 表单联动：客户等级选 SVIP 时，出现"专属客服"字段；
  5. 异步校验：邮箱不能重复，需要查库校验；
  6. 导出：把客户列表导出成 CSV。

你翻了一下第 14 章的选型矩阵，发现：

  • 概览卡片和列表 CRUD → amis 最擅长（Schema 驱动，开箱即用）；
  • 复杂表单（联动 + 异步校验）→ Formily 最擅长（领域模型 + reactions）；
  • 如果全用 amis，表单联动和异步校验会很别扭；
  • 如果全用 Formily，列表和概览要自己写大量模板代码。

结论：组合使用。amis 做列表和概览，Formily 做表单，用 React Router 把三个页面串起来。数据统一存 localStorage（无后端），amis 通过自定义 fetcher 读写，Formily 直接读写同一个 db 模块。这种组合既保留了 amis 在列表场景的高效率，又发挥了 Formily 在复杂表单上的表达力，是中后台需求的典型解法。

原理拆解 ​

架构拆解 ​

┌─────────────────────────────────────────────────┐
│                  React Router                    │
│  /            /customers        /customers/new   │
└──────┬───────────────┬───────────────┬───────────┘
       │               │               │
   ┌───▼───┐      ┌────▼────┐     ┌────▼─────┐
   │ amis  │      │  amis   │     │ Formily  │
   │概览卡片│      │CRUD 列表│     │复杂表单   │
   └───────┘      └────┬────┘     └────┬─────┘
                       │               │
                  ┌────▼───────────────▼────┐
                  │   shared/db (localStorage) │
                  └──────────────────────────┘
  • amis 页面（概览、列表）：用 amis.render(schema, {}, { fetcher }) 渲染，fetcher 拦截 /api/* 请求，调用 db 模块返回数据；
  • Formily 页面（新增/编辑）：用 createForm + Field 组件，直接调用 db.create / db.update；
  • 数据层：db 模块封装 localStorage CRUD，amis 和 Formily 共用同一个数据源；
  • 路由：React Router 三个路由，编辑页通过 :id 参数区分新增/编辑。

这个架构的核心是"数据层统一、视图层分工"——amis 和 Formily 各自渲染自己擅长的视图，但读写的是同一份数据。

amis 的数据协议 ​

amis 的所有数据请求都走 env.fetcher。fetcher 收到 { url, method, query, data }，返回 { status: 0, data, msg: "" }（status=0 表示成功）。

关键约定：

  • 列表接口：返回 { items: [], total: n }，crud 组件自动渲染分页；
  • 表单接口：返回 { ...entity }，amis 自动回填表单；
  • 失败：返回 { status: 1, msg: "错误信息" }，amis 会 toast 提示。

capstone 的 amisFetcher 拦截了 6 个路径：GET /api/stats、GET /api/customers、POST /api/customers、PUT /api/customers/:id、DELETE /api/customers/:id、GET /api/customers/export。

Formily 的联动与校验 ​

联动用 onFieldReact("level", field => {...})：监听 level 字段变化，当值为 "svip" 时显示 vipService 字段，否则隐藏并清空。这是 Formily 的响应式模型——字段变化自动触发副作用，不需要手动写事件监听。

异步校验用 validator 返回 Promise：邮箱校验里 setTimeout 模拟查库，db.emailExists 检查是否重复。校验通过 resolve(true)，失败 reject(Error("消息"))。

amis 与 Formily 的集成点 ​

两个产品在同一工程共存，有三个集成点要处理：

  1. 路由跳转：amis 的 actionType: "url" 会调 window.location.href，在 SPA 里会整页刷新。解决方案是把"新增客户"按钮放在 amis 容器外，用 React Router 的 <Link> 跳转；
  2. 样式隔离：amis 用 amis/lib/themes/default.css，Formily 用 antd 的 reset.css。两者类名不冲突，但 amis 的全局样式（如 body 字体）可能影响 Formily。capstone 里没有明显冲突，但如果有，可以用 CSS 作用域隔离；
  3. 数据边界：amis 走 fetcher 读写 db，Formily 直接调用 db。两者共享同一个 localStorage key，数据实时同步——amis 列表新增后刷新能看到 Formily 创建的客户。

为什么不用 iframe 集成？ ​

很多低代码平台（如 lowcode-engine、tmagic-editor）用 iframe 隔离设计器和运行时。但 capstone 里 amis 和 Formily 不需要 iframe，原因有三：

第一，两者都是普通 React 组件。amis 的 render() 返回 React 元素，Formily 的 <Form> 也是 React 组件，它们可以在同一个 React 树里共存，不需要 iframe 隔离作用域。

第二，iframe 会增加通信成本。如果用 iframe 嵌 Formily，amis 和 Formily 之间要通过 postMessage 传递数据（如新客户信息），还要处理 iframe 高度自适应、跨域等问题。同进程直接调用 db 模块简单得多。

第三，样式和路由可以统一管理。同一进程下，amis 和 Formily 共享同一个 React Router 和全局样式，导航切换是 SPA 级别的，体验更流畅。

只有在需要强隔离（如第三方插件不受信任）或技术栈不兼容（如一个用 Vue 一个用 React）时，才需要 iframe。capstone 两个产品都是 React 生态，同进程是最优解。

数据一致性保证 ​

amis 和 Formily 共用 db 模块，本质上是共用一个 localStorage 单例。一致性保证来自两点：

  1. 所有写操作都走 db 模块：amis 的 fetcher 调 db.create/update/remove，Formily 的表单提交也调 db.create/update。没有"绕过 db 直接改 localStorage"的路径。
  2. 读操作实时从 localStorage 加载：db.list() 每次都 localStorage.getItem 再 parse，不是缓存内存。所以 Formily 创建客户后，amis 列表刷新（fetcher 重新调 db.list()）能立即看到新数据。

这种"单数据源 + 实时读"的模式保证了一致性，但缺点是每次读都要 parse JSON，数据量大时会有性能问题。生产环境可以加内存缓存 + 变更通知机制。

产品对照 ​

本章是组合使用，对照一下"全用 amis" vs "全用 Formily" vs "amis + Formily"：

维度全用 amis全用 Formilyamis + Formily（capstone）
概览卡片原生支持（service + tpl）要自己写 Reactamis 原生
列表 CRUD原生支持（crud）要自己写表格amis 原生
表单联动expressions（弱）reactions（强）Formily 强
异步校验支持但写法绕Promise validator（原生）Formily 原生
开发效率列表快、表单慢表单快、列表慢都快
维护成本表单联动难维护列表代码多各取所长

组合方案的核心价值：让每个产品做它最擅长的事。amis 的列表和概览用 Schema 几分钟就能搭好，Formily 的复杂表单用领域模型优雅地处理联动和校验。

动手实现 ​

1. 启动 capstone ​

bash
cd labs/capstone
pnpm install
pnpm dev          # http://localhost:5179

打开后左侧导航有三个入口：概览、客户列表、新增客户。

2. 验证概览页 ​

访问 /，应该看到三张卡片：客户总数、活跃客户、VIP 客户。数字来自 GET /api/stats，由 amisFetcher 从 localStorage 计算返回。

3. 验证列表 CRUD ​

访问 /customers，看到客户表格（种子数据 3 条）。可以：

  • 用筛选器按姓名/状态/等级过滤；
  • 点"编辑"跳转到 Formily 表单（回填数据）；
  • 点"删除"移除客户（带确认）；
  • 点"导出 CSV"下载 customers.csv。

4. 验证复杂表单 ​

访问 /customers/new，填写表单：

  • 姓名、邮箱、电话（必填 + 格式校验）；
  • 等级选 SVIP → 出现"专属客服"字段（联动）；
  • 邮箱填已存在的邮箱 → 异步校验报错"该邮箱已存在"；
  • 选行业、状态，点保存 → 回到列表，新客户出现。

5. 跑 E2E 烟测 ​

bash
pnpm build && pnpm preview   # 启动 preview 5279
pnpm smoke                    # 7 项断言

烟测覆盖：概览渲染 → 列表种子数据 → 跳转表单 → 表单输入框渲染 → SVIP 联动 → 保存后列表出现新客户。

6. 扩展练习 ​

跑通基础功能后，可以尝试以下扩展，加深对组合使用的理解：

  • 批量操作：给 amis 列表加多选 + 批量修改状态（selectable: true + bulkActions）；
  • 分页：当前 fetcher 返回全部数据，改成支持 page/perPage 分页，amis crud 会自动渲染分页器；
  • 表单分步：把 Formily 表单拆成两步（基本信息 + 等级信息），用 Formily 的 FormStep 或自定义步骤条；
  • 真实后端：把 db 模块换成真实 REST API，amis fetcher 用 fetch 转发，Formily 也调同一 API——数据层替换不影响 UI 层。

避坑清单 ​

  1. amis 的 fetcher 返回格式必须是 { status, msg, data }：status=0 成功，非 0 失败。不要返回 axios 风格的 { status: 200, data }，amis 会把外层 status 当业务状态码。
  2. amis 的 url 匹配要去掉 query 字符串：api.url 可能带 ?page=1&perPage=10，必须 url.split("?")[0] 再匹配，否则 GET 列表会匹配失败。
  3. 不要用 amis 的 actionType: "url" 在 SPA 里跳转：它会调 window.location.href 导致整页刷新。用 React Router 的 <Link> 或 useNavigate。
  4. Formily 用 Form 不用 FormProvider：@formily/antd-v5 的 Form 组件已经封装了 FormProvider，再套一层 FormProvider 会导致 context 丢失、字段不渲染。
  5. Formily 的 Submit 按钮文字有字间距：antd 的按钮样式加了 letter-spacing，导致 "保存" 变成 "保 存"，自动化测试要用模糊匹配。
  6. amis 和 Formily 共享数据源要走同一 db 模块：不要各自维护一份数据，否则列表和表单的数据会不一致。capstone 用 localStorage 单例，两边都调同一个 db。
  7. 导出 CSV 要返回 dataURL：amis 的 actionType: "download" 期望接口返回 { url: "data:...", filename: "x.csv" }，不要返回文件流——amis 的 download action 会直接用 url 触发下载。

小结与自测 ​

你应该记住的 ​

  • 组合使用比单一产品更强：amis 做列表/概览，Formily 做复杂表单
  • amis 的数据协议：fetcher 返回 { status: 0, data, msg }，列表要 { items, total }
  • Formily 的联动用 onFieldReact，异步校验用 Promise validator
  • SPA 里不要用 amis 的 actionType: "url"，用 React Router Link
  • Formily 用 Form 组件（已含 Provider），不要套 FormProvider
  • 数据层统一：amis 和 Formily 共用同一个 db 模块
  • 导出用 dataURL：amis download action 期望 { url, filename } 格式

自测题 ​

  1. 选择题：capstone 里为什么不用 amis 做复杂表单？（A）amis 不支持表单；（B）amis 的表达式联动和异步校验写法别扭，Formily 的领域模型更适合；（C）amis 的表单样式不好看；（D）amis 不能做必填校验。
  2. 选择题：amis 的 fetcher 返回列表数据时，正确的格式是？（A）[{ id:1, name:"x" }]；（B）{ status: 0, data: [{ id:1 }] }；（C）{ status: 0, data: { items: [{ id:1 }], total: 1 } }；（D）{ items: [{ id:1 }] }。
  3. 思考题：如果 capstone 的客户列表要支持"批量选中后批量修改状态"，应该用 amis 还是自己写 React 组件？为什么？

自测题参考答案 ​

  1. 答案 B。amis 支持表单且有校验，但它的联动靠 expressions（字符串表达式），异步校验要写 fetcher 适配器，复杂场景下可读性和可维护性差。Formily 的领域模型（Field + reactions + Promise validator）是为复杂表单设计的，联动和校验都是一等公民。
  2. 答案 C。amis 的 crud 组件期望 data.items 是数组、data.total 是总数，外层 status: 0 表示成功。A 是裸数组（amis 会报错），B 缺少 items/total 结构，D 缺少 status 包裹。
  3. 应该用 amis。amis 的 crud 组件原生支持多选（selectable: true）和批量操作（bulkActions），只需在 schema 里配置批量 action 调用后端接口。自己写 React 组件要处理选中状态、全选逻辑、批量请求等，重复造轮子。amis 在列表操作场景下的生产力远高于手写。
