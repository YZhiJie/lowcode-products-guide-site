第 16 章 · mini-lowcode 架构：从零开始，先画一张架构图 ​

前置章节：第 15 章 · Capstone 综合实战
所需环境：Node 20 + pnpm 9.15.4；本章 lab 在 labs/mini-lowcode，是从零搭建的教学级低代码引擎。
难度：★★★★★
本章交付物：mini-lowcode 架构图、六大模块职责定义、Schema 数据结构初版、zod 校验。

从本章开始进入进阶卷。前十五章我们学习了五个现成的低代码产品（amis、Formily、lowcode-engine、tmagic-editor、GrapesJS），第 14-15 章学会了按场景组合使用。但这些都是黑盒——我们知道怎么用，却不知道内部怎么实现。

进阶卷的目标是：不依赖任何商业低代码框架，从零搭建一个教学级低代码引擎，叫 mini-lowcode。通过亲手实现，你会理解低代码引擎的底层原理：Schema 怎么定义、渲染器怎么递归、拖拽怎么计算落点、撤销重做怎么实现、插件怎么扩展、代码怎么生成。

本章你将获得 ​

读完本章并跑通 lab，你应该能：

  1. 画出 mini-lowcode 的六大模块架构图，说清每个模块的职责；
  2. 理解"数据驱动视图"是低代码引擎的核心思想；
  3. 设计带 version 字段的 Schema 数据结构，用 zod 做校验；
  4. 校验失败时返回「节点 id.字段」形式的错误路径，便于定位；
  5. 跑通 pnpm test 中的 schema 相关用例（7 条全绿）。

从一个真实问题说起 ​

你用过 amis，知道写一份 JSON Schema 就能渲染出页面；你用过 lowcode-engine，知道拖拽组件到画布就能生成 Schema。但你有没有想过：这些产品的内部，到底是怎么把"一份数据"变成"一个界面"的？

这个问题的答案，就是低代码引擎的核心原理。理解了原理，你就能：

  • 在使用商业产品时，知道它的能力边界在哪；
  • 遇到 bug 时，能猜到大概是哪层出了问题；
  • 有定制化需求时，知道能不能自己实现、要实现哪些模块。

进阶卷就是要回答这个问题。我们不引 amis、不引 Formily、不引 lowcode-engine，只用 Vue 3 + TypeScript + 几个基础库（zod 做校验、jsep 做表达式解析），从零搭一个能跑的低代码引擎。

整个进阶卷共 5 章，每章实现一个核心模块：第 16 章定义 Schema，第 17 章写渲染器，第 18 章做拖拽设计器，第 19 章加撤销重做和插件，第 20 章实现出码。每章都有对应的单测，最终 pnpm test 跑通 35 条用例。学完这五章，你会对低代码引擎的全链路有完整的理解。

原理拆解 ​

六大模块架构 ​

mini-lowcode 由六个核心模块组成，每个模块职责单一、可独立测试：

┌──────────────────────────────────────────────────┐
│                    Schema 层                       │
│  定义页面结构：{ version, root: { id, type, ... } } │
└──────────────────────┬───────────────────────────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
┌──────────────┐ ┌──────────┐ ┌──────────────┐
│  Renderer    │ │ Designer │ │   Codegen    │
│  递归渲染树   │ │ 拖拽落点  │ │ 生成 .vue    │
└──────────────┘ └──────────┘ └──────────────┘
        │              │
        ▼              ▼
┌──────────────┐ ┌──────────────┐
│  Expression  │ │   History    │
│  表达式求值   │ │ undo/redo    │
└──────────────┘ └──────────────┘
                       │
                       ▼
                ┌──────────────┐
                │    Plugin    │
                │  setup(api)  │
                └──────────────┘
  1. Schema：数据结构定义 + zod 校验。所有其他模块都围绕 Schema 运作。
  2. Renderer：递归把 Schema 树渲染成 Vue 组件树。核心是 render(node) 递归调用。
  3. Expression：模板里的 $&#123;&#123; expr &#125;&#125; 表达式求值。用 jsep 解析 AST，白名单解释执行，禁止 eval。
  4. Designer：拖拽落点计算。给定拖拽节点、目标节点、位置（before/after/inside），返回新 Schema 树。
  5. History：撤销重做。命令模式 + 300ms 合并窗口。
  6. Plugin：插件系统。setup(api) 暴露 registerComponent / registerSetter / onSchemaChange。
  7. Codegen：出码。把 Schema 转成 .vue + .json 文件。

这六个模块的依赖关系是有向无环的：Schema 是最底层，所有人都依赖它；Renderer 依赖 Schema 和 Expression；Designer 依赖 Schema；History 依赖 Schema；Plugin 依赖 Renderer（注册组件）和 Schema；Codegen 依赖 Schema。没有循环依赖，每个模块都可以独立测试。

为什么不用现成的低代码框架？ ​

你可能会问：已经有 amis、lowcode-engine 这些成熟产品了，为什么还要自己写？原因有三：

第一，教学目标不同。 商业产品的目标是"好用"，会封装大量细节（比如 lowcode-engine 的物料协议、插件机制、模拟器通信）。这些封装对生产是必要的，但对学习是障碍——你看不到底层原理。mini-lowcode 把所有封装都拆掉，只保留最核心的几百行代码，每一行都能看懂。

第二，理解原理才能用好工具。 你用过 amis，知道它的 fetcher 要返回 { status, data }，但你知道为什么是这个格式吗？因为 amis 内部有一层 responseAdaptor，把 fetcher 的返回包装成统一的 Payload。理解了这个原理，你在遇到 fetcher 问题时就能快速定位。mini-lowcode 让你亲手实现这个 responseAdaptor（在 Renderer 层），以后再看 amis 源码就不会陌生。

第三，定制化需要懂原理。 生产中经常要对低代码产品做二次开发——加自定义组件、改渲染逻辑、接入私有数据源。如果不懂原理，你只能在黑盒外面摸索；懂了原理，你就能精准地在正确的层做正确的扩展。

数据驱动视图 ​

低代码引擎的核心思想是数据驱动视图：界面的结构、样式、交互全部由一份数据（Schema）描述，渲染器读取这份数据生成界面。

这意味着：

  • 界面是数据的投影：改数据，界面自动变；
  • 数据是唯一真相源：撤销重做本质是回到历史版本的数据；
  • 出码是数据的序列化：把数据转成代码，就是出码。

这种思想和前端框架的"状态驱动视图"一脉相承——React/Vue 里你改 state，界面自动更新；低代码里你改 Schema，界面自动更新。区别只是 state 存在内存里，Schema 是可持久化、可传输的结构化数据。

所有六个模块都围绕 Schema 这份数据运作：Renderer 读 Schema 渲染，Designer 改 Schema 结构，History 存 Schema 快照，Codegen 把 Schema 转成代码。

Schema 数据结构 ​

mini-lowcode 的 Schema 极简：

ts
interface SchemaDocument {
  version: string; // 版本号，用于破坏性升级时迁移
  root: SchemaNode; // 根节点
}

interface SchemaNode {
  id: string; // 全局唯一
  type: "page" | "container" | "text" | "button" | "input";
  props?: Record<string, unknown>;
  children?: SchemaNode[];
}

version 字段是关键——它让我们在未来做破坏性改动时，可以写迁移函数把旧版 Schema 升到新版。没有版本号的 Schema 是无法安全演进的。

zod 校验与错误路径 ​

Schema 用 zod 校验。校验失败时，zod 返回的 path 是数组（如 ["root", "children", 0, "id"]），不便于人类阅读。我们做一个转换：把数字索引替换成对应节点的 id，形成「节点 id.字段」的可读路径。

比如错误发生在 root.children[0].id，转换后变成 page-1.children[container-1].id。这样运营或开发者看到错误就能立刻定位到哪个节点的哪个字段。

产品对照 ​

本章是从零实现，对照一下"自研 mini-lowcode" vs "用商业产品"的差异：

维度mini-lowcode（自研）amis / Formily 等（商业）
代码量约 600 行核心代码数万行
功能教学级，只支持 5 种组件生产级，上百种组件
学习价值极高（理解原理）中（会用但不懂原理）
生产可用否（缺很多功能）是
定制成本低（自己写的，随便改）高（要读源码、改黑盒）

mini-lowcode 的定位是教学工具，不是生产工具。它的价值在于让你理解原理，而不是替代商业产品。

动手实现 ​

1. 启动 mini-lowcode ​

bash
cd labs/mini-lowcode
pnpm install
pnpm test          # 跑全部 35 条单测
pnpm dev           # http://localhost:5180 看渲染器演示

2. 看 schema 模块 ​

src/core/schema.ts 定义了 Schema 类型和 zod 校验器。关键函数：

  • validateSchema(doc)：返回错误列表，每项是 { path, message }；
  • createEmptySchema()：创建一个带 version 的空 page；
  • findNode(root, id) / findParent(root, id)：树操作。

schema 模块是整个引擎的基础，其他五个模块都 import 它。它的代码量不到 100 行，但定义了整个系统的数据契约——所有模块都围绕 SchemaNode 这个接口运作。

3. 跑 schema 测试 ​

bash
pnpm test -- schema

7 条用例覆盖：空 schema 通过、缺 version 报错、id 为空报错、非法 type 报错、深层子节点错误路径包含父节点 id、findNode、findParent。

4. 验证错误路径 ​

故意构造一个非法 schema：

ts
const doc = {
  version: "1.0.0",
  root: {
    id: "page-1",
    type: "page",
    children: [{ id: "c1", type: "container", children: [{ id: "", type: "badtype" }] }],
  },
};
const issues = validateSchema(doc);
// issues[0].path 会是 "page-1.children[c1].id" 或 "...type"

5. 扩展练习：加一个新节点类型 ​

mini-lowcode 目前支持 5 种 type：page / container / text / button / input。试着加一个 image 类型：

  1. 在 NODE_TYPES 常量里加 "image"；
  2. 在 zod 的 z.enum(NODE_TYPES) 里会自动生效；
  3. 写一个测试：{ id: "img1", type: "image", props: { src: "x.png" } } 能通过校验；
  4. 写一个测试：{ id: "img1", type: "imag" } 校验失败（拼错了）。

这个练习会让你体会到"白名单 type"的价值——运营只能用允许的类型，不能随便输入。

6. 看测试文件 ​

tests/schema.spec.ts 是 7 条 schema 测试。读一遍测试用例，你能快速理解 validateSchema 的行为边界。测试是最好的文档。

避坑清单 ​

  1. Schema 必须带 version：没有版本号的 Schema 无法安全演进。哪怕第一版，也要写上 "1.0.0"。
  2. zod 校验要返回可读路径：zod 默认的 ["root","children",0,"id"] 对人类不友好，要转换成「节点 id.字段」形式。
  3. id 要全局唯一：拖拽、撤销、出码都依赖 id 定位节点，重复 id 会导致各种诡异 bug。
  4. 递归函数要有终止条件：findNode 遇到叶子节点（没有 children）要返回，不能无限递归。
  5. type 用枚举不用 string：type 用 z.enum 限制可选值，避免运营输入 "div" 这种不在白名单的类型。

Schema 设计的权衡 ​

设计 Schema 数据结构时有几个权衡，理解这些权衡能帮你在生产中做出更好的决策：

权衡一：扁平 vs 嵌套。 mini-lowcode 用嵌套树（children 数组），这是最自然的页面结构描述方式。但有些产品（如某些表单引擎）用扁平结构（所有节点平铺，用 parentId 关联）。嵌套树适合渲染（递归即可），扁平结构适合查询和批量操作。mini-lowcode 选嵌套树，因为教学重点是渲染。

权衡二：宽松 vs 严格。 Schema 校验可以很宽松（只校验 id 和 type），也可以很严格（每个 type 的 props 都有独立 schema）。mini-lowcode 选宽松——props 是 Record<string, unknown>，不做细粒度校验。严格校验更安全但写起来繁琐，宽松校验更灵活但可能放过错误数据。生产中通常按组件类型分别定义 props schema。

权衡三：内置类型 vs 可扩展类型。 mini-lowcode 的 type 是硬编码的 5 种，要加新类型得改源码。生产产品（如 lowcode-engine）的 type 是可注册的——插件可以注册新的组件类型。硬编码简单，可扩展灵活。mini-lowcode 用硬编码，因为教学重点不在插件扩展（插件系统在第 19 章）。

小结与自测 ​

你应该记住的 ​

  • 六大模块：Schema / Renderer / Expression / Designer / History / Plugin / Codegen
  • 核心思想：数据驱动视图——界面是 Schema 的投影
  • Schema 必须带 version 字段，用于未来迁移
  • zod 校验失败要返回「节点 id.字段」的可读错误路径
  • mini-lowcode 是教学工具，价值在理解原理，不在生产可用
  • 六大模块依赖无环：Schema 最底层，其他模块单向依赖它

自测题 ​

  1. 选择题：mini-lowcode 的核心思想是什么？（A）组件驱动开发；（B）数据驱动视图；（C）事件驱动架构；（D）面向对象设计。
  2. 选择题：Schema 必须带哪个字段？（A）name；（B）version；（C）author；（D）date。
  3. 思考题：为什么低代码引擎的撤销重做本质上是"回到历史版本的 Schema 数据"？

自测题参考答案 ​

  1. 答案 B。低代码引擎把界面结构、样式、交互全部描述成一份 Schema 数据，渲染器读取数据生成界面。改数据即改界面，这就是"数据驱动视图"。
  2. 答案 B。version 字段让 Schema 能安全演进——未来做破坏性改动时，可以写迁移函数把旧版升到新版。没有版本号的 Schema 无法判断该用哪套解析逻辑。
  3. 因为界面是 Schema 的投影。撤销操作不是"恢复界面上的 DOM"，而是"把 Schema 恢复到上一个版本"，渲染器会自动重新渲染成对应的界面。所以 History 模块存的是 Schema 快照（或生成快照的命令），不是 DOM 快照。这也是为什么拖拽、改属性等操作都要先改 Schema，再由渲染器更新视图——数据是唯一真相源。
