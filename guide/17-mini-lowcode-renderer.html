第 17 章 · mini-lowcode 渲染器：递归渲染的魔法 ​

前置章节：第 16 章 · mini-lowcode 架构
所需环境：Node 20 + pnpm 9.15.4；本章 lab 在 labs/mini-lowcode，重点看 src/core/renderer.ts 和 src/core/expression.ts。
难度：★★★★
本章交付物：递归渲染器、组件注册表、表达式求值（jsep AST 解释）。

第 16 章定义了 Schema 数据结构，这一章把 Schema"变成"界面——实现 Renderer 模块。渲染器的核心是递归：render(node) 渲染当前节点，然后对每个子节点递归调用 render(child)。递归是处理树结构最自然的方式，但也是最容易出 bug 的地方——必须有终止条件。

本章还会实现 Expression 模块：模板里的 $&#123;&#123; expr &#125;&#125; 表达式怎么求值。我们用 jsep 把表达式解析成 AST，然后白名单解释执行，绝对禁止 eval 和 new Function——这是安全底线。

本章你将获得 ​

读完本章并跑通 lab，你应该能：

  1. 理解递归渲染的原理，写出 render(node) 函数；
  2. 用组件注册表（ComponentRegistry）实现组件和渲染逻辑的解耦；
  3. 用 jsep 解析表达式 AST，白名单解释执行，支持字面量、变量、二元运算、三元、成员访问、函数调用；
  4. 处理模板字符串里的 $&#123;&#123; expr &#125;&#125;，把表达式替换成求值结果；
  5. 跑通 renderer 和 expression 相关测试（共 15 条全绿）。

先看漫画 ​

这一话画的是递归渲染的核心——一棵 Schema 树摆在像素酱面前，她演示 render(node) 调 render(child) 的套娃过程，标签君看到表达式 $&#123;&#123; name &#125;&#125; 被替换成"张三"，码叔提醒"递归要有终止条件，否则栈溢出"。逐格讲解、坑点清单和三道自测题在 EP.17 漫画讲解。

从一个真实问题说起 ​

你有一份 Schema：

json
{
  "version": "1.0.0",
  "root": {
    "id": "page-1",
    "type": "page",
    "children": [
      {
        "id": "c1",
        "type": "container",
        "children": [
          { "id": "t1", "type": "text", "props": { "content": "你好，${{ name }}" } },
          { "id": "b1", "type": "button", "props": { "label": "点击" } }
        ]
      }
    ]
  }
}

怎么把它变成界面？直觉是：遍历这棵树，对每个节点生成对应的 HTML。但树的深度是未知的——可能只有一层，也可能嵌套十层。用循环写太别扭，用递归写最自然。

递归的核心思想是：一个问题可以拆成同样的子问题。渲染一个 page，本质是渲染它的所有 children；渲染一个 container，本质也是渲染它的所有 children。所以 render(node) 只管当前节点，然后把 children 交给 render(child) 处理。

原理拆解 ​

递归渲染函数 ​

递归渲染的伪代码：

ts
function render(node: SchemaNode): VNode {
  switch (node.type) {
    case "page":
      return h(
        "div",
        { class: "lc-page" },
        node.children?.map((child) => render(child)),
      );
    case "container":
      return h(
        "div",
        { class: "lc-container" },
        node.children?.map((child) => render(child)),
      );
    case "text":
      return h("span", { class: "lc-text" }, node.props.content);
    case "button":
      return h("button", { class: "lc-button" }, node.props.label);
  }
}

关键在于：page 和 container 的渲染里，children.map(child => render(child)) 就是递归调用。递归会一直往下走，直到遇到 text / button 这种叶子节点——它们没有 children，不再递归，这就是终止条件。

终止条件的重要性 ​

递归必须有终止条件，否则会无限递归直到栈溢出。在渲染器里，终止条件是：

  • 节点没有 children（叶子节点）；
  • 或者 children 是空数组。

如果 Schema 里不小心出现了循环引用（A 的 children 里有 B，B 的 children 里有 A），递归会无限循环。生产级引擎会在 Schema 校验时检测环，mini-lowcode 为了教学简洁没有做，但你应该知道这个风险。

Vue 里的递归组件 ​

在 Vue 3 里，递归组件需要组件能引用自己。<script setup> 里用 defineOptions({ name: "LowcodeRenderer" }) 声明组件名，然后在模板里用 <LowcodeRenderer> 递归渲染子节点：

vue
<template>
  <div v-if="node.type === 'page'">
    <LowcodeRenderer v-for="child in node.children" :key="child.id" :node="child" />
  </div>
  <span v-else-if="node.type === 'text'">{{ textContent }}</span>
</template>

Vue 的模板编译器会自动处理递归——只要组件名和模板里的标签名一致即可。这比手写 h() 递归更简洁，也是 mini-lowcode 实际采用的方式。

递归 vs 迭代 ​

理论上，任何递归都可以改写成迭代（用显式栈）。那为什么渲染器用递归？

递归的优点：代码简洁，和树结构天然对应。渲染一棵树，递归写法只需十几行，迭代写法要几十行。

递归的缺点：受调用栈深度限制。JavaScript 的调用栈通常支持几千到几万帧，对于一般的页面（几十层嵌套）完全够用。但如果 Schema 有上千层嵌套，递归会栈溢出。

什么时候用迭代：当你无法保证树的深度有上限时（比如用户可以无限嵌套），应该用迭代。生产级低代码引擎通常会限制最大嵌套深度（如 50 层），这样递归就安全了。

mini-lowcode 用递归，因为教学场景下树深度可控，代码简洁比极限性能更重要。

组件注册表 ​

上面的伪代码把渲染逻辑写死在 switch 里，加新组件要改 render 函数。更好的做法是组件注册表：

ts
const registry = new ComponentRegistry();
registry.register("text", (ctx) => ctx.node.props.content);
registry.register("button", (ctx) => ctx.node.props.label);

注册表把"组件类型"和"渲染函数"解耦。加新组件只需 registry.register(...)，不用改 render 函数。这也是 lowcode-engine 的物料注册、amis 的自定义组件注册的核心思想。

上下文传递 ​

渲染时需要把"作用域"（scope）传递给子节点，这样表达式 $&#123;&#123; name &#125;&#125; 才能取到 name 的值。scope 是一个普通对象，包含当前节点的 props、父节点传入的数据等。

递归渲染时，scope 的传递策略有两种：

  • 继承式：子节点继承父节点的 scope，并可以覆盖。这是最常见的方式，类似 JavaScript 的作用域链。
  • 隔离式：每个节点有独立的 scope，互不影响。适合表单场景，避免字段名冲突。

mini-lowcode 用继承式——子节点默认拿到父节点的 scope。如果子节点需要自己的变量，可以在 props 里定义，渲染时合并到 scope。

scope 的传递是递归渲染的关键细节。如果 scope 没传对，表达式会取不到值，渲染出 undefined 或报错。

表达式求值：为什么不能用 eval ​

模板里的 你好，$&#123;&#123; name &#125;&#125; 需要把 $&#123;&#123; name &#125;&#125; 替换成变量 name 的值。最直接的写法是 eval(expr)，但 eval 有严重的安全问题——如果 expr 是恶意代码，eval 会执行它。

mini-lowcode 用 jsep 把表达式解析成 AST（抽象语法树），然后自己写一个解释器遍历 AST 求值。解释器只支持白名单操作（字面量、变量、二元运算、三元、成员访问、白名单函数），不支持任意代码执行。

比如 1 + 2 * 3 被 jsep 解析成：

BinaryExpression(+)
  ├─ Literal(1)
  └─ BinaryExpression(*)
       ├─ Literal(2)
       └─ Literal(3)

解释器递归遍历这棵树，先算 2*3=6，再算 1+6=7。

AST 节点类型全解 ​

jsep 解析后的 AST 节点类型和我们的处理方式：

AST 类型含义处理方式
Literal字面量（数字、字符串、布尔）直接返回 node.value
Identifier变量名从 scope 里取，找不到报错
BinaryExpression二元运算（+ - * / == < > && ||）递归求左右值，按运算符计算
UnaryExpression一元运算（- !）递归求参数，取反/取负
ConditionalExpression三元（a ? b : c）递归求 test，按真假返回
MemberExpression成员访问（a.b / a[b]）递归求对象，取属性
CallExpression函数调用（fn(a, b)）递归求函数和参数，调用
ArrayExpression数组字面量递归求每个元素

每个类型都要在 evaluate 里有对应的 case。如果遇到不支持的类型（如箭头函数、赋值），直接 throw——这就是白名单的边界。

动手实现 ​

1. 启动并看渲染器演示 ​

bash
cd labs/mini-lowcode
pnpm dev          # http://localhost:5180

页面会渲染一个 page，里面有 container，container 里有 text 和 button。这就是递归渲染的效果。

2. 看 renderer.ts ​

src/core/renderer.ts 导出 ComponentRegistry 和 createDefaultRegistry()。默认注册了 page / container / text / button / input 五种组件的渲染函数。

3. 看 expression.ts ​

src/core/expression.ts 是表达式求值器。核心函数：

  • parseExpression(template)：提取模板里所有 $&#123;&#123; expr &#125;&#125;；
  • evalExpression(expr, scope)：对单个表达式求值，返回 { ok, value } 或 { ok: false, error }；
  • renderTemplate(template, scope)：把模板里的 $&#123;&#123; &#125;&#125; 全部替换成求值结果。

4. 跑 renderer + expression 测试 ​

bash
pnpm test -- renderer

8 条用例覆盖：注册表内置组件、countNodes 递归计数、text 渲染内容、模板替换、二元运算、三元表达式、parseExpression 提取、未定义变量报错。

5. 验证表达式安全 ​

试试在浏览器控制台调用：

ts
evalExpression("alert('hacked')", {});
// 返回 { ok: false, error: "不是可调用的函数" }

alert 不在白名单函数里，所以不会执行。这就是白名单解释的安全价值。

6. 扩展练习：加一个取模运算符 ​

当前 evaluate 支持 + - * / %，试着加一个指数运算符 **：

  1. 在 BinaryExpression 的 switch 里加 case "**": return Math.pow(left, right)；
  2. 写测试：evalExpression("2 ** 10", {}) 应该返回 1024；
  3. 验证 jsep 能解析 **（jsep 默认支持）。

这个练习会让你理解 AST 解释器的扩展性——加新运算符只需加一个 case。

7. 看 Vue 递归组件 ​

src/components/LowcodeRenderer.vue 是实际的递归渲染组件。注意模板里 <LowcodeRenderer v-for="child in node.children" />——组件渲染自己，形成递归。defineOptions({ name: "LowcodeRenderer" }) 让组件能在模板里引用自己。

跑不起来？ ​

症状可能原因排查步骤
递归栈溢出Schema 有环或终止条件丢失检查 Schema 是否有循环引用；确认叶子节点不调 render(child)
表达式求值返回 undefined变量不在 scope 里检查 scope 是否包含表达式用到的变量

避坑清单 ​

  1. 递归必须有终止条件：叶子节点（text/button/input）不能再调 render(child)，否则无限递归。
  2. 禁止 eval / new Function：表达式必须用 AST 解释执行。哪怕是内部工具，也要守住这条安全底线。
  3. 白名单函数要严格：只暴露 Math、String、Number 等安全对象，不要暴露 process、require、globalThis。
  4. 组件注册表要在渲染前就绪：如果 render 时注册表没有该类型，会渲染成"未知组件"。
  5. scope 要按需传递：不要把全局变量都塞进 scope，只传表达式需要的，减少意外访问。
  6. 成员访问要做空值保护：a.b.c 当 a 是 undefined 时会报错，解释器要返回 undefined 而不是 throw。

表达式求值的边界 ​

表达式引擎不是编程语言，它只支持"取值 + 计算"，不支持副作用（赋值、函数定义、循环）。这是有意的设计限制：

  • 不支持赋值（a = 1）：表达式应该是纯函数，同样的输入永远返回同样的输出，这样渲染才可预测。
  • 不支持函数定义（() => {}）：函数是代码，不是数据，出码时无法序列化。
  • 不支持循环（for）：表达式应该是即时求值，不应该有长时间运行的逻辑。

这些限制让表达式"可预测、可序列化、可安全执行"。amis 的表达式、Formily 的 reactions 都有类似的限制。

小结与自测 ​

你应该记住的 ​

  • 渲染器核心是递归：render(node) 管当前节点，children 交给 render(child)
  • 终止条件是叶子节点（没有 children），没有终止条件会栈溢出
  • 组件注册表解耦"类型"和"渲染逻辑"，加组件不用改 render
  • 表达式用 jsep 解析 AST + 白名单解释，禁止 eval/new Function
  • 白名单只暴露安全对象（Math、String 等），不暴露 process/require
  • scope 用继承式传递，子节点默认拿到父节点的作用域

自测题 ​

  1. 选择题：递归渲染的终止条件是什么？（A）节点 type 是 page；（B）节点没有 children 或 children 为空；（C）节点 id 为空；（D）节点 props 为空。
  2. 选择题：为什么表达式求值不能用 eval？（A）eval 太慢；（B）eval 有安全风险，会执行任意代码；（C）eval 不支持变量；（D）eval 不支持运算符。
  3. 思考题：如果 Schema 树有 1000 层嵌套，递归渲染会有什么问题？怎么解决？

自测题参考答案 ​

  1. 答案 B。递归渲染在遇到没有 children 的叶子节点时停止。page 和 container 有 children，会继续递归；text 和 button 没有 children，是终止点。
  2. 答案 B。eval 会执行任意 JavaScript 代码，如果表达式来自用户输入（如运营在表单里写的表达式），可能包含恶意代码。白名单 AST 解释只允许预定义的操作，从根本上杜绝代码注入。
  3. 1000 层嵌套会导致栈溢出——JavaScript 的调用栈深度有限（通常几千到几万帧），1000 层递归可能接近或超过极限。解决方案有两种：一是把递归改成迭代（用显式栈模拟递归），二是限制 Schema 的最大深度（在 zod 校验里加深度检查）。生产级引擎通常两种都做，既保证性能又防止恶意构造深层 Schema。
