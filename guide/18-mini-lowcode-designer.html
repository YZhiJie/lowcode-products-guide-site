第 18 章 · mini-lowcode 设计器：拖拽落点计算 ​

前置章节：第 17 章 · mini-lowcode 渲染器
所需环境：Node 20 + pnpm 9.15.4；本章 lab 在 labs/mini-lowcode，重点看 src/core/designer.ts。
难度：★★★★
本章交付物：拖拽落点判断（canDrop）、执行落点（dropNode）、容器类型约束。

设计器（Designer）是低代码平台里用户直接交互的部分——拖拽组件、调整位置、删除节点。本章实现 Designer 的核心：拖拽落点计算。当用户把一个组件拖到画布上，引擎要回答两个问题：

  1. 能不能放：这个组件能不能放到目标位置？（canDrop）
  2. 怎么放：放到目标的前面、后面还是内部？（dropNode）

这是个纯函数问题——输入是 Schema 树 + 拖拽源 + 目标位置，输出是新的 Schema 树。纯函数非常适合写表格驱动的测试，7 条测试覆盖各种边界情况。

本章你将获得 ​

读完本章并跑通 lab，你应该能：

  1. 理解拖拽落点的三种位置：before（前）、after（后）、inside（内）；
  2. 实现 canDrop(draggingId, targetId, position) 判断是否可放置；
  3. 实现 dropNode(draggingId, targetId, position) 执行落点并返回新 Schema；
  4. 处理关键约束：不能拖到自己的子孙、非容器不能 inside、page 不能移动；
  5. 跑通 designer 相关测试（7 条全绿）。

先看漫画 ​

这一话画的是拖拽落点的三种位置——像素酱把一个按钮拖到容器上方、下方和内部，标签君演示"禁止拖到子孙"的红线，码叔解释 before/after/inside 的区别。逐格讲解、坑点清单和三道自测题在 EP.18 漫画讲解。

从一个真实问题说起 ​

用户在画布上拖拽一个按钮到一个 container 上。引擎需要判断：

  • 如果鼠标在 container 上半部分，放到 container 的第一个子节点前面（before）；
  • 如果鼠标在 container 下半部分，放到 container 的最后一个子节点后面（after）；
  • 如果鼠标在 container 中间，放到 container 内部（inside）。

这就是拖拽落点的三种位置：before / after / inside。

但还有约束：

  • 不能把一个节点拖到它自己的子孙里（会形成环）；
  • 非容器类型（text、button）不能作为 inside 的目标；
  • page 节点不能被拖动。

这些约束看起来简单，但每一条都对应一个常见的 bug。忽略任何一条，用户都可能拖出一个无法正常渲染的 Schema。设计器的价值就是在用户操作时拦住这些非法的操作，而不是等渲染报错。

原理拆解 ​

三种落点位置 ​

拖拽落点有三种：

目标节点: [ container ]

before:  [新节点] [ container ]   —— 放到目标前面
after:   [ container ] [新节点]   —— 放到目标后面
inside:  [ container [新节点] ]   —— 放到目标内部（作为子节点）

before 和 after 改变的是目标节点父节点的 children 数组；inside 改变的是目标节点自己的 children 数组。

canDrop 的判断逻辑 ​

canDrop(draggingId, targetId, position) 需要检查：

  1. 目标不是自己：不能拖到自己身上；
  2. 目标不是拖拽源的子孙：不能把父节点拖到子节点里（会形成环）；
  3. inside 时目标必须是容器：page 和 container 是容器，text/button/input 不是；
  4. 拖拽源不是 page：page 是根节点，不能移动。

判断"目标是不是拖拽源的子孙"需要遍历拖拽源的子树，如果目标在子树里，就禁止。这个判断是 O(n) 的，但因为 Schema 树通常不大，可以接受。

容器类型判断 ​

哪些节点可以作为 inside 的目标？只有"容器"——有 children 属性的节点。mini-lowcode 里 page 和 container 是容器，text/button/input 不是。

判断方式有两种：

  • 按 type 判断：type === "page" || type === "container"。简单但不灵活，加新容器类型要改代码。
  • 按能力判断：节点有 isContainer: true 属性。更灵活，加新容器只需设属性。

mini-lowcode 用按 type 判断，因为组件类型少。生产级引擎通常用能力判断——组件元数据里声明 isContainer，设计器读元数据判断。

dropNode 的实现 ​

dropNode(draggingId, targetId, position) 的步骤：

  1. 先把拖拽源从原来的位置移除（从父节点的 children 里删掉）；
  2. 根据 position，把拖拽源插入到目标的合适位置：
    • before：插入到目标在父节点 children 里的前一个位置；
    • after：插入到目标在父节点 children 里的后一个位置；
    • inside：追加到目标的 children 末尾。

关键点：先移除再插入。如果先插入再移除，当拖拽源和目标在同一个父节点下时，索引会乱。先移除保证了索引的正确性。

索引计算的细节 ​

before 和 after 需要知道目标在父节点 children 里的索引。假设父节点的 children 是 [A, B, C]，目标是 B（索引 1）：

  • before B：插入到索引 1，结果 [A, 新, B, C]；
  • after B：插入到索引 2，结果 [A, B, 新, C]。

如果拖拽源 A 也在这个数组里，先移除 A 得到 [B, C]，B 的索引变成 0。这时候 before B 插入到索引 0，结果 [新, B, C]——A 被放到了 B 前面，正确。

如果不先移除 A，直接 before B（索引 1）插入，得到 [A, 新, B, C]，然后移除 A（索引 0），得到 [新, B, C]——结果居然一样？这是巧合。但如果拖拽源在目标后面（比如拖拽 C 到 B 前面），先插入会出错：

  • 不先移除：before B（索引 1）插入 C，得到 [A, C, B, C]，然后移除原来的 C（现在索引变成 3），得到 [A, C, B]——C 到了 B 前面，正确？
  • 等等，这看起来也对。那问题出在哪？

问题出在"移除原来的拖拽源"时，它的索引可能已经变了。如果你记录的是插入前的索引，插入后索引就不对了。安全的做法是先按 id 找到并移除拖拽源，再按 id 找到目标并插入——不依赖索引，而是依赖 id 查找。

mini-lowcode 就是这么做的：removeNode(root, id) 按 id 移除，insertBefore(root, targetId, node) 按 id 找目标再插入。这样不管数组怎么变，都不会出错。

不可变性 ​

dropNode 返回新的 Schema 树，不修改原来的。这是为了配合 History 模块——每次修改都产生一个新快照，撤销时回到上一个快照。如果直接修改原对象，History 无法记录变化。

实现不可变性的方式是：深拷贝受影响的节点路径，其他节点共享引用。mini-lowcode 用简单的深拷贝（JSON.parse(JSON.stringify)），虽然性能不是最优，但代码简洁，适合教学。

动手实现 ​

1. 启动并看设计器演示 ​

bash
cd labs/mini-lowcode
pnpm dev          # http://localhost:5180

页面上有一棵树和一个画布。你可以在控制台调用 dropNode 函数测试拖拽效果。

2. 看 designer.ts ​

src/core/designer.ts 导出三个核心函数：

  • canDrop(schema, draggingId, targetId, position)：返回 boolean；
  • dropNode(schema, draggingId, targetId, position)：返回新 Schema；
  • isDescendant(root, ancestorId, descendantId)：判断 descendant 是否在 ancestor 的子树里。

isDescendant 是 canDrop 的核心辅助函数——它递归遍历 ancestor 的子树，看能不能找到 descendantId。

3. 跑 designer 测试 ​

bash
pnpm test -- designer

7 条用例覆盖：

  1. before 落点：拖拽源放到目标前面；
  2. after 落点：拖拽源放到目标后面；
  3. inside 落点：拖拽源放到容器内部；
  4. 禁止拖到子孙：把 container 拖到它自己的子节点里，返回原 Schema；
  5. 非容器不能 inside：把按钮拖到 text 内部，返回原 Schema；
  6. page 不能拖动：拖动 page，返回原 Schema；
  7. 原 Schema 不被修改：dropNode 后原 Schema 不变。

4. 手动测试环检测 ​

在控制台构造一个环：

ts
const schema = {
  root: {
    id: "p",
    type: "page",
    children: [{ id: "c", type: "container", children: [{ id: "b", type: "button" }] }],
  },
};
canDrop(schema, "c", "b", "inside");
// 返回 false——c 是 b 的祖先，不能拖进去

这就是"不能拖到子孙"的检测。

5. 扩展练习：加 maxChildren 限制 ​

试着给 container 加一个 maxChildren 属性，超过就不允许 inside。这需要在 canDrop 里加一条判断：如果 position 是 inside 且目标的 children.length >= maxChildren，返回 false。

这个练习会让你理解 canDrop 的可扩展性——加约束只需加一条判断。

6. 看 index 中的拖拽示例 ​

src/components/LowcodeRenderer.vue 里有简单的拖拽示例。实际的拖拽 UI（鼠标位置计算、高亮提示）比较复杂，mini-lowcode 只演示了核心的 dropNode 逻辑，UI 层留给你自己实现。

7. 实现一个简单的拖拽 UI（进阶） ​

试着在 LowcodeRenderer.vue 里加 HTML5 拖拽：

  1. 每个渲染的节点加 draggable="true" 和 @dragstart；
  2. 目标节点加 @dragover.prevent 和 @drop；
  3. drop 时根据鼠标在目标的位置（offsetY < targetHeight/3 → before，> 2*targetHeight/3 → after，否则 inside）调用 dropNode；
  4. 用响应式数据存储 Schema，dropNode 返回新树后赋值触发重渲染。

这是把纯函数 dropNode 接入实际 UI 的练习。核心逻辑已经写好，你只需要做"胶水层"。

跑不起来？ ​

症状可能原因排查步骤
dropNode 返回 undefined拖拽源或目标不存在检查 draggingId 和 targetId 是否在 Schema 里
拖拽后节点消失先插入后移除导致索引错乱确认是"先移除再插入"
canDrop 总是返回 falseisDescendant 判断有误检查 isDescendant 的递归终止条件
inside 到非容器成功canDrop 没检查容器类型确认 inside 时 target.type 是 page 或 container

避坑清单 ​

  1. 先移除再插入：拖拽源和目标在同一父节点下时，先插入会导致目标索引偏移，必须先移除。
  2. 不能拖到子孙：用 isDescendant 检测，否则会形成环，渲染时无限递归。
  3. 非容器不能 inside：text/button/input 没有 children 属性，inside 会导致数据结构错误。
  4. page 不能拖动：page 是根节点，拖动它会导致 Schema 没有根。
  5. 不可变性：dropNode 返回新树，不修改原树。否则 History 无法记录撤销。
  6. 深拷贝的性能：JSON.parse(JSON.stringify) 对大树有性能问题，生产环境用 immutable.js 或结构化克隆。

拖拽与撤销重做的配合 ​

每次 dropNode 都产生一个新 Schema，这正好是 History 模块需要的。设计器在调用 dropNode 后，把新 Schema 推给 History，History 记录一条命令。用户按 Ctrl+Z 时，History 执行 undo，回到上一个 Schema。

这里的关键是：设计器不直接修改 Schema，而是通过 History 执行命令。设计器调用 history.execute(new DropCommand(...))，History 负责执行命令、记录历史、触发渲染。这样设计器和 History 解耦——设计器只管产生命令，History 管执行和撤销。

如果设计器直接修改 Schema 而不经过 History，撤销就会失效。这是命令模式的核心价值：把"做什么"和"怎么做、怎么撤销"分开。

拖拽 UX 的细节 ​

实际的拖拽交互还有很多 UX 细节，mini-lowcode 没有实现，但你应该知道：

  • 落点指示器：拖拽时显示一条线或高亮区域，告诉用户松开后会放到哪里；
  • 鼠标位置判断：根据鼠标在目标节点的位置（上 1/3、中 1/3、下 1/3）决定 before/inside/after；
  • 滚动跟随：拖拽到画布边缘时自动滚动；
  • 拖拽预览：拖拽时显示一个半透明的组件预览。

这些细节不影响核心逻辑，但极大影响用户体验。lowcode-engine 的设计器花了大量精力在这些 UX 细节上。

小结与自测 ​

你应该记住的 ​

  • 拖拽落点三种位置：before（前）、after（后）、inside（内）
  • canDrop 四条规则：不是自己、不是子孙、inside 目标是容器、源不是 page
  • dropNode 两步走：先移除拖拽源，再按 position 插入
  • 不能拖到子孙，否则形成环导致渲染无限递归
  • dropNode 返回新 Schema（不可变），配合 History 实现撤销
  • 实际拖拽还有 UX 细节：落点指示器、鼠标位置判断、滚动跟随
  • 设计器通过 History 执行命令，不直接改 Schema，保证撤销有效

自测题 ​

  1. 选择题：拖拽落点有哪三种位置？（A）上、中、下；（B）before、after、inside；（C）left、right、center；（D）前、后、左。
  2. 选择题：为什么不能把一个节点拖到它的子孙里？（A）性能差；（B）会形成环，渲染时无限递归；（C）不美观；（D）浏览器限制。
  3. 思考题：dropNode 为什么要"先移除再插入"，而不是"先插入再移除"？

自测题参考答案 ​

  1. 答案 B。before 放到目标前面，after 放到目标后面，inside 放到目标内部作为子节点。这三种覆盖了所有拖拽场景。
  2. 答案 B。如果 A 拖到它的子节点 B 里，A 的 children 里有 B，B 的 children 里又有 A，形成环。渲染器递归遍历这棵树时会无限递归直到栈溢出。
  3. 当拖拽源和目标在同一个父节点下时，如果先插入，拖拽源会被插到目标附近，然后再移除时，目标的索引已经因为插入而偏移了，可能删错位置。先移除拖拽源，目标的索引不变，再插入就不会出错。这是一个经典的"修改数组时的索引问题"。更安全的做法是不依赖索引，而是按 id 查找和移除——mini-lowcode 的 removeNode 和 insertBefore 都是按 id 操作的。
